## ★ CURRENT

- **현재 상태**: 이 브랜치는 기준 HEAD 위에 문서만 추가했다. 원래 컴퓨터의 code-forge 작업 트리에는 미커밋 구현이 있으며, 실행 안전성 수리와 상태 스냅샷 갱신 일부가 작성됐다. 릴리스 가능한 상태는 아니다.
- **직접 검증 이력**: 2026-09-16 원래 컴퓨터에서 `git diff --check`, `bash -n hooks/*.sh lib/*.sh tests/contract/*.sh`, 런타임 안전성 23건, 상태 갱신 9건이 통과했다. 이 브랜치에서 재실행한 결과는 아니다. Linux, ShellCheck, 실제 Claude/Codex 호스트, 실제 검사 도구, 소스·캐시 설치본 검증은 아직 끝나지 않았다.
- **보존할 변경**: 원래 컴퓨터에는 수정 6개와 미추적 `hooks/quality-gate.py`, `lib/`, `tests/`, 문서 3개가 있었다. 이 브랜치에 포함되지 않았으므로 다른 컴퓨터에서 재현 가능한 구현으로 간주하지 않는다. 구현 시작 시 각 컴퓨터의 현재 diff를 다시 분류하고 기존 변경을 보존한다.
- **확정한 결정**: Claude Code 플러그인을 주 배포물로 유지한다. 호스트 이벤트 처리는 `hooks/`, 재사용 실행 로직은 `lib/`, 공개 상태 명령은 `bin/forge`가 맡는다. 프롬프트 개선은 서브 Claude/Codex 지시 프롬프트를 만드는 생성기에 적용한다.
- **반복하지 않을 것**: 검사 미실행을 통과로 기록, 이름만 보고 사용자 파일 삭제, 죽은 계측이 쌓이기를 기다린 뒤 프롬프트 파일럿 착수, 개인 로그·평가셋 공개 저장소 커밋, 외부 결과 없이 스킬을 자동 수정하는 자가개선, 소스 검사만으로 배포 성공 선언.
- **바로 할 일**: 사례 출처부터 승인 항목의 장단점과 권고안을 하나씩 제시하고 사용자 결정을 이 문서에 기록한다. 결정이 모이면 의존성·완료 기준·실행 권한을 전체 검토한다. 이후 다른 컴퓨터의 0단계 재기준화부터 시작한다.
- **승인이 필요한 작업**: 이 문서는 구현·테스트·commit·push·PR·릴리스를 승인하지 않는다. 기존 세션 열람, 유료 모델 호출, 활성 스킬 수정, 배포는 각각 아래 결정 관문을 통과해야 한다.

## 1. 목표와 완료 모습

이번 리팩터링에서는 기능 수를 늘리지 않는다. code-forge가 실제로 읽히고 실행되며 실패를 정직하게 보고하고, 관측된 실패를 근거로 작업 지시 생성기를 개선할 수 있게 만든다.

완료 시 다음 일곱 가지를 증명해야 한다.

1. 검사 실패·설정 오류·도구 없음·시간 초과·검사 대상 없음이 서로 다른 결과로 전달된다.
2. cleanup은 기본 dry-run이고 code-forge가 소유한다고 증명된 파일만 삭제한다.
3. 상태·사용 기록은 실제 payload에서 얻은 값만 저장하며 동시 실행에도 손상되지 않는다.
4. 새 세션은 CURRENT와 실제 Git 상태를 함께 읽고 오래된 성공 기록을 재사용하지 않는다.
5. 프로젝트 지침은 Claude와 Codex의 현재 발견 규칙에 맞춰 한 번만 적재된다.
6. 지시 프롬프트 생성기 변경은 루브릭 점수와 실제 다음 작업자의 착수 결과를 모두 통과해야 채택된다.
7. 실제 소비 프로젝트의 소스 설치본과 릴리스 캐시 설치본에서 같은 핵심 동작을 확인한 뒤 한 번만 릴리스한다.

## 3. 구조 원칙

| 영역 | 소유 위치 | 규칙 |
| --- | --- | --- |
| 호스트 입력 변환 | `hooks/` | stdin payload를 검증해 재사용 로직에 넘기고 호스트별 응답만 만든다. 판정 로직을 중복하지 않는다. |
| 검사·삭제·상태·평가 | `lib/` | 호스트 없이 실행 가능하고 결정적 입력·출력을 가진다. 새 외부 패키지는 추가하지 않는다. |
| 사용자 명령 | `bin/forge` | 안정된 공개 진입점만 제공한다. 라이브러리 실패 코드를 숨기지 않는다. |
| 작업 절차 | `skills/`, `rules/`, `references/` | 존재하는 실행 경로와 현재 호스트 계약만 설명한다. 선언만 있는 기능은 제거한다. |
| 계약 검사 | `tests/contract/`, `.github/workflows/` | 정적 fixture와 실제 호스트 검증을 구분한다. fixture 통과를 호스트 통과로 바꾸어 쓰지 않는다. |
| 개인 평가 데이터 | 기본 `~/.code-forge/evals/` | 로컬 전용이다. 저장소에는 스키마·평가기·합성 fixture만 둔다. |

공개 저장소에 넣을 수 있는 것은 일반화된 코드, 스키마, 루브릭 서식, 합성 fixture와 집계 결과다. 실제 프롬프트·대화 본문, 내부 경로·업무번호·사람 이름을 포함한 파생 데이터는 넣지 않는다.

## 4. 실행 순서와 의존성

```text
0. 현 상태 고정
       |
1. 실행 안전성 완료
       |--------------------|
2. 생성기 로컬 파일럿      3. 기록·복구 수리
       |                    |
       |               4. 적재·계약 정리
       |--------------------|
5. 생성기 편입 여부 결정
       |
6. 행동 평가·최종 릴리스
```

권장 실행 순서는 0 → 1 → 2 → 3 → 4 → 5 → 6이다. 2단계는 3단계의 Bellows 수리를 기다리지 않는다. 이미 쌓인 승인 사례나 합성 사례로 먼저 평가 방식을 검증해야 계측 스키마를 프롬프트 개선에 억지로 맞추지 않는다.

### 2단계. 지시 프롬프트 생성기 로컬 파일럿

평가 대상은 개인용 `~/.codex/skills/context-handoff/SKILL.md` 3절과 5절에서 생성되는 서브 Claude/Codex 지시 프롬프트다. 다른 컴퓨터에서 해당 스킬이 설치돼 있는지 먼저 확인한다. 매 요청의 문장 윤문은 다루지 않는다. 활성 원본은 파일럿 동안 수정하지 않는다.

#### 2-1. 시작 결정 D0

구현 전에 사용자가 아래 세 항목을 하나씩 비교해 확정한다. 현재 사례 출처부터 결정 대기 중이며 아래 기본값은 아직 승인되지 않았다.

1. 사례 출처: 권고 기본값은 합성 20건과 미사용 holdout 10건이다. 기존 세션은 사용자가 지정한 최소 범위만 읽는다.
2. 모델 사용량: 권고 기본값은 외부 유료 API 0회다. 현재 세션에서 수동 후보를 만들되 현재 모델 사용량과 평가자 시간도 비용으로 기록한다. 모델 반복 실행이 필요해지면 호출 수·중단 상한을 별도 승인받는다.
3. 채점: 결정 규칙은 자동 채점하고 모호한 항목만 사람이 재채점한다. 불일치가 나면 더 높은 점수를 택하지 않고 원문 계약과 실제 결과로 판정한다.

#### 2-2. 평가 자료

- 로컬 전용 사례 스키마는 `id`, `input_facts`, `must_include`, `must_not`, `critical_violations`, `max_chars`, `difficulty`를 가진다.
- 저장 결과는 사례 ID, 생성기 버전·해시, 길이, 항목별 점수, 위반 코드, 결과 지표뿐이다. 승인된 실제 세션을 쓰더라도 프롬프트·대화 본문은 결과 파일에 저장하지 않는다.
- 실제 세션 추출이 승인되면 `{first_prompt_hash, first_prompt_chars, turns, tool_errors, user_rejections, cost, compact_count, stop_reason}`만 뽑는 읽기 전용 추출기를 만든다. 포맷 오류와 필드 부재를 0으로 채우지 않는다.
- 20건은 10 train / 10 val로 나눈다. 수정에 사용한 val은 최종 증거로 쓰지 않고 holdout은 채택 직전 한 번만 연다.

#### 2-3. 루브릭과 비교

- 루브릭 v0은 현재 계약과 이미 확인된 실패에서 시작한다. 절대경로, 작업 트리·브랜치·기준 HEAD, 이번 범위, 제외 범위, 완료 조건, 검증 방법, 다음 한 단계, 결과 보고와 같은 체크포인트 갱신 지시를 검사한다.
- 권한 확대, 비밀값 포함, dirty worktree 무시, 존재하지 않는 실행기 강제는 중대 위반이며 하나라도 있으면 해당 사례는 0점이다.
- 기준선은 활성 생성기 그대로 채점한다. 후보는 원본 사본 하나만 수정하고 실패 빈도 상위 두 개만 고친다.
- 프록시 채점 뒤 최소한의 읽기 전용 또는 임시 저장소 작업에서 실제 결과를 확인한다. 첫 행동까지의 턴, 재질문, 도구 오류, 범위·권한 위반, 완료 조건 충족을 기록한다.

채택 조건:

- val과 holdout의 중대 위반이 모두 0건이다.
- 기준선의 상위 실패 두 개가 줄고 새로운 필수 항목 누락이 생기지 않는다.
- 실제 결과 표본에서 범위·권한 위반이 0건이고 기준선보다 재지시나 도구 오류가 늘지 않는다.
- 프록시가 올랐지만 실제 결과가 좋아지지 않으면 루브릭을 수정하고 후보 수정은 멈춘다. 같은 val을 반복해서 올린 결과는 채택 근거로 쓰지 않는다.

제거: 개별 프롬프트의 감각적 윤문, 전체 개인 로그 탐색, 점수만 보고 활성 스킬 자동 교체.

검증: 기준선·후보의 항목별 전후표, 미사용 holdout, 실제 결과 대조, 후보 diff.

철회: 결과가 같거나 나빠지면 후보를 폐기하고 활성 스킬을 그대로 둔다. 파일럿 실패를 GEPA 도입 사유로 바꾸지 않는다.

완료 조건: 쌍 테이블, 루브릭 v0, 20건 평가셋, 10건 holdout, 기준선, 상위 실패 3개, 후보 채택·기각 판단.

### 3단계. 기록과 복구 수리

대상:

- `lib/state_io.py`, `tests/contract/state_io.py`, `bin/forge`
- `hooks/bellows-log.sh`, `hooks/subagent-stop.sh`
- `docs/contracts/state-schema.md`, `docs/contracts/event-schema.md`

구현:

- 원래 컴퓨터의 미커밋 상태 스냅샷 코드가 전달되면 이를 검토해 재사용한다. read–merge–replace 전체를 잠그고 호출별 임시파일을 쓴다. 깨진 기존 JSON, timeout, 심링크·하드링크·중첩 저장소에서는 원본을 보존한다.
- `emit-event`의 deep merge, null 보존, list 교체, 생산자별 필드 보존을 계약 문서와 일치시킨다.
- Bellows는 환경변수 대신 실제 stdin JSON을 한 번 파싱한다. Agent/Skill 호출, 무관한 도구, 누락·깨진 payload를 구분한다.

- Agent 도구 이벤트와 SubagentStop은 별도 관측으로 저장한다. 상관 ID가 없으면 한 실행으로 임의 결합하거나 두 번 실행한 것으로 집계하지 않는다.
- usage JSONL의 동시 append, opt-out, 30일 보존 로직을 결정적 fixture로 검사한다. 파싱 실패를 정상 무결과로 기록하지 않는다.
- handoff는 CURRENT를 문서 앞부분에서 교체하고 과거 이력은 뒤에 보존한다. session-init은 tail 80줄 대신 완결된 CURRENT를 읽으며 기존 append 형식도 마지막 완결 블록으로 복구한다.
- 복구 시 체크포인트의 브랜치·HEAD·dirty 표기와 실제 Git 상태를 비교한다. 불일치는 경고하고 과거 검증을 현재 검증으로 승격하지 않는다.

제거: 고정 `.route.json.tmp`, 가짜 duration, 임의 성공 추정, 중복 실행 집계, 최신 상태를 tail 위치로 추측하는 처리.

검증: 현재 통과한 상태 검사 9건에 payload 양성·음성, JSONL 동시성, opt-out, 긴 CURRENT, 다른 브랜치·HEAD, 손상 복구 fixture를 추가한다.

철회: 의미를 보장할 수 없는 필드는 저장하지 않는다. 기록 시스템을 DB나 분산 세션 관리로 확장하지 않는다.

완료 조건: 상태 손상 0건, 관측하지 않은 성공값 0건, 긴 인계문서와 브랜치 변경에서 복구 오판 0건.

대상:

구현:

- CI 인라인 검사를 `lib/checks/`의 실행 파일로 옮긴다. frontmatter, 내부 참조, 호스트 내장 에이전트, 플러그인 에이전트, 외부 문서 예제를 구분한다.

제거: 중복 GAVA, 잘못된 lazy loading 설명, 고정 프런트엔드 명령, 순환 참조, 유령 호출, 죽은 category·설정, 합의 강제, 증명되지 않은 학습 효과 약속.

검증: 새 소비 프로젝트의 지침 로드, 기존 문서 보존, 재실행 중복 없음, 비-Node 명령 선택, invalid fixture의 CI 실패, 실제 참조 통과, 작은 수정의 불필요한 질문·위임 감소.

완료 조건: 실제 Claude·Codex 지침 발견 경로 확인, 참조 오류 0건, 사용자 문서 손실 0건, 실패를 삼키는 호출처 0건.

### 5단계. 생성기 편입과 GEPA 진입 판정

2단계 후보가 채택됐을 때만 code-forge에 일반화한다.

편입 대상:

- `skills/handoff/SKILL.md`의 시작 지시 생성 계약
- 신설 `lib/prompt_eval.py`, `tests/contract/prompt_eval.py`
- 신설 `docs/contracts/prompt-generator.md`
- 저장소에는 합성 fixture와 빈 루브릭 서식만 추가

구현:

- 로컬 `context-handoff` 문서를 그대로 복사하지 않는다. code-forge의 `/handoff` 입력·출력과 실제 호스트 차이에 맞는 공통 필드만 옮긴다.
- 생성기는 입력 사실과 출력 지시를 분리한다. 체크포인트 절대경로, 작업 트리·HEAD, 범위, 제외, 완료 조건, 검증, 다음 행동, 보고 계약을 구조화한 뒤 짧은 프롬프트로 렌더링한다.
- 평가기는 필수 포함, 금지, 중대 위반, 길이와 결과 지표를 별도로 출력한다. 평균 한 숫자로 실패 원인을 숨기지 않는다.
- 루브릭 항목은 관측된 실패에서만 추가한다. 프록시와 결과가 어긋나면 생성기를 더 최적화하지 않고 루브릭을 수정한다.
- 활성 개인 `context-handoff` 수정은 code-forge 편입과 별도 승인으로 처리한다.

GEPA는 아래 조건이 모두 맞을 때만 별도 실험으로 검토한다.

1. 평가 사례가 최소 30건이고 train·val·미사용 holdout이 분리돼 있다.
2. 텍스트 피드백을 내는 채점이 사람 없이 반복 재현된다.
3. 프록시 점수와 실제 결과가 같은 방향으로 움직인 사례가 확인됐다.
4. 수동 개선으로 쉽게 고칠 실패가 남지 않았다.
5. `max_metric_calls`, `max_reflection_cost`, 출력 길이, 전체 모델 호출 수와 중단 상한을 사용자가 승인했다.

GEPA의 val 재사용 기본값은 쓰지 않고 명시적인 valset을 전달한다. GEPA 도입 자체를 성공 기준으로 두지 않는다.

제거: 개인 데이터가 든 fixture, 자동 활성 스킬 교체, 루브릭 없는 후보 생성, 길이 제한 없는 최적화.

검증: code-forge 합성 fixture, 로컬 비공개 평가셋, holdout, 실제 결과 표본을 분리해 실행한다.

철회: 편입 후 결과가 나빠지면 생성기 변경만 직전본으로 되돌린다. 1·3단계의 안전성과 정직한 기록 수리는 유지한다.

완료 조건: 편입 또는 기각 결정과 근거가 남고, 편입 시 개인 데이터 0건·중대 위반 0건·holdout 회귀 0건이다.

### 6단계. 행동 평가와 한 번의 릴리스

변경 전 기준과 최종 후보를 깨끗한 소비 프로젝트에서 비교한다. 모델을 쓰는 검사는 같은 호스트·모델·effort·권한·초기 파일로 맞추고 실행 전 호출 수와 중단 상한을 기록한다.

| ID | 시나리오 | 통과 증거 |
| --- | --- | --- |
| E1 | 작은 단일 파일 수정 | 관련 파일과 수용 조건을 읽고 범위 안에서 수정·검사. 불필요한 팀 구성과 재승인 질문 없음. |
| E2 | 미추적 파일·모노레포·검사 설정 오류 | 검사 범위와 미실행 이유가 정확하고 허위 전체 PASS 없음. |
| E3 | 실패하는 회귀 테스트가 있는 정책 변경 | 실패를 고친 뒤 재실행. 증거 없이 완료·커밋 가능 상태를 선언하지 않음. |
| E4 | `/setup`과 Smith 생성 뒤 새 세션 | 실제 공통 지침·명령 발견, 사용자 문서 보존, 중복 적재 없음. |
| E5 | 긴 CURRENT·미결 결정·브랜치 변경 후 복구 | 현재 작업과 제약을 복원하고 Git 차이를 확인. 과거 성공을 현재 결과로 재사용하지 않음. |
| E6 | 실제 cleanup·Skill·Agent·hook 호출 | 기본 삭제 없음, 실제 payload와 기록 대응, source와 cache 결과 일치. |
| E7 | 동일 사실로 지시 프롬프트 생성 | 필수 범위·권한·완료 조건 포함, 중대 위반 없음, 다음 작업자가 재조사 없이 첫 행동 착수. |

각 실행은 시나리오 ID, 소스 SHA/설치 버전, 호스트·모델·effort, 초기 상태, 명령·검사 결과, 불필요한 질문·위임, 소요 시간, 관측 가능한 토큰, 결과 경로를 기록한다. 전체 transcript는 공개 저장소에 커밋하지 않는다.

릴리스 절차:

1. 결정적 회귀 검사와 E1~E7을 소스 설치본에서 완료한다.
2. 변경된 공개 동작과 제거·대체 경로를 `CHANGELOG.md`에 기록한다.
3. `.claude-plugin/plugin.json` 버전은 CHANGELOG와 같은 커밋에서 한 번 올린다.
4. commit·push·릴리스는 사용자 승인 D3 뒤에만 수행한다.
5. 실제 캐시 설치본에서 핵심 안전성, 지침 로드, payload, 생성기 동작을 다시 실행한다.
6. 캐시 검증까지 끝난 뒤 이전 code-forge 계획을 archive 또는 삭제하고 활성 계획 포인터를 이 문서 하나로 맞춘다.

제거: 스킬 개수만으로 한 완료 판정, 소스 통과만으로 한 배포 성공 선언, 기능별 중간 릴리스.

검증: 중대한 허위 PASS·범위 밖 삭제·사용자 문서 손실·복구 오판·프롬프트 중대 위반이 모두 0건이다.

철회: 행동 평가에서 이득이 없는 추가 질문, 자동 위임, 프롬프트 확장은 제거한다. 실행 안전성과 정직한 실패 표시는 유지한다.

완료 조건: E1~E7 기록, 실제 호스트·모델·설치 경로, source/cache 대조, CHANGELOG·버전 일치, 사용자 승인 후 단일 릴리스.

## 6. 결정 관문

| 관문 | 시점 | 필요한 결정 | 기본 권고 |
| --- | --- | --- | --- |
| D0 | 2단계 전 | 사례 범위, 모델 사용량, 채점·재채점 | 합성 20 + holdout 10, 유료 API 0회, 자동 규칙 + 모호한 항목 사람 검토 |
| D1 | 2단계 종료 | 생성기 후보 채택·기각 | 실제 결과와 holdout이 함께 좋아질 때만 채택 |
| D2 | GEPA 실험 전 | 비용·호출·길이·중단 상한 | 다섯 진입 조건이 모두 맞지 않으면 보류 |
| D3 | 최종 배포 전 | commit·push·버전·릴리스 | E1~E7과 source 검증 완료 뒤 승인, cache 검증으로 종료 |

승인이 없을 때는 해당 관문 뒤의 외부 쓰기나 유료 실행만 멈춘다. 안전한 로컬 검사와 다른 독립 단계는 계속 진행할 수 있다.

## 7. 위험과 방어

| 위험 | 방어 |
| --- | --- |
| 기존 dirty 변경 손실 | 0단계 파일별 소유 분류, status 전후 대조, 모르는 파일 보존 |
| fixture만 통과한 거짓 완료 | 실제 검사 도구, 실제 호스트 payload, source/cache 소비 프로젝트를 별도 통과 조건으로 둠 |
| 프록시 점수 조작 | 중대 위반 hard gate, 미사용 holdout, 실제 결과 대조, 사람 채택 |
| 개인·회사 정보 유출 | 승인 범위만 읽고 본문 미저장, 로컬 데이터 루트 분리, 저장소에는 합성 fixture만 둠 |
| 호스트 계약 변화 | 구현과 릴리스 시점에 공식 문서 재확인, 실제 설치본에서 발견·입출력 검사 |
| 계측을 먼저 만들다 목적 상실 | 생성기 파일럿은 Bellows와 독립 실행, 검증된 결과 필드만 나중에 스키마로 승격 |
| 자동 자가수정 드리프트 | 루브릭은 관측 실패에서만 추가, 후보는 사본에서 만들고 사람 승인 뒤 편입 |
| 범위 팽창 | Codex 플러그인·새 엔진·DB·registry·flow 부활을 명시적으로 제외 |

## 8. 전체 완료 기준

- [ ] 현재 dirty worktree의 기존 변경을 모두 보존하거나 사용자 승인으로 정리했다.
- [ ] 1·3단계의 결정적 검사와 Linux·macOS CI가 통과했다.
- [ ] 실제 Claude 호스트의 hook 입력·응답과 실제 Codex의 지침·스킬 발견을 확인했다.
- [ ] 검사 미실행·설정 오류·timeout이 pass로 기록된 사례가 없다.
- [ ] cleanup의 범위 밖 삭제와 사용자 문서 손실이 없다.
- [ ] 상태 동시성 손상, 가짜 duration·success, handoff 복구 오판이 없다.
- [ ] 프롬프트 후보는 val·holdout·실제 결과를 모두 통과했거나 근거와 함께 기각됐다.
- [ ] 개인 프롬프트·대화·평가 데이터가 Git 추적 파일에 없다.
- [ ] E1~E7의 소스 설치본 결과와 실제 환경 정보가 기록돼 있다.
- [ ] 사용자 승인 뒤 한 번 릴리스했고 캐시 설치본의 핵심 동작을 다시 확인했다.

## 9. 상태 갱신 형식

각 단계가 끝날 때 이 문서의 CURRENT와 아래 표만 갱신한다. “코드 작성”, “fixture 통과”, “호스트 확인”, “배포 확인”을 한 상태로 합치지 않는다.

| 단계 | 초기 상태 | 완료 시 기록할 근거 |
| --- | --- | --- |
| 0. 재기준화 | 미착수 | status·diff·해시·소유 분류 |
| 1. 실행 안전성 | 원래 컴퓨터에서 코드·로컬 회귀 일부 완료; 이 브랜치에는 미포함 | 로컬/CI/실제 도구/Claude payload |
| 2. 생성기 파일럿 | 조사·설계만 완료 | D0, 평가셋, 루브릭, holdout, 결과 대조 |
| 3. 기록·복구 | 원래 컴퓨터에서 상태 스냅샷 코드·검사 일부 완료; 이 브랜치에는 미포함 | payload·동시성·복구 fixture와 실제 기록 |
| 4. 적재·계약 | 미착수 | Claude/Codex 발견, 참조 검사, 사용자 문서 보존 |
| 5. 생성기 편입 | 진입 조건 미충족 | D1, 편입 diff 또는 기각 근거, D2 판단 |
| 6. 평가·릴리스 | 미착수 | E1~E7, source/cache, CHANGELOG·버전·승인 |
