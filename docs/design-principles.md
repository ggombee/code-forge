# code-forge 설계 원칙 (Design Principles)

> 이 문서는 code-forge의 모든 의사결정이 따라야 할 핵심 원칙을 기록한다.
> 새 기능 추가, 구조 변경, 에이전트 설계 시 이 원칙에 부합하는지 확인할 것.
> host pack과 새 실행 core의 전환은 [2026-10-18 최종 개선 계획](../plan/code-forge-final-improvement-plan-2026-10-18.md)을 따른다. 문서화와 구현·실호스트·배포 완료는 별도로 기록한다.

---

## 1. 본질적 목적

**"여러 모델이 공통 개인화 코어의 기억·판단 기준·경험을 활용해, 함께 일할수록 사용자에게 더 잘 맞는 개인 어시스턴트가 된다."**

개인 어시스턴트는 지속되는 사용자 경험이고, 실행 에이전트와 서브에이전트는 현재 일을 수행하는 구현 수단이다. 터미널·웹·모바일은 코어의 접점이다. 기존 CodeForge OSS는 재사용할 규칙·스킬·도구를 제공하며 독립 사용을 유지한다.

- **개인화의 정본**: 세션 밖의 비공개 저장 기반에서 출처·범위·버전·수명을 관리한다. 모델별 지시로 필요한 내용만 전달하고 개인/회사 권한을 분리한다. 명시 기억·수정·철회·끄기는 첫 제품에 포함한다.
- **근거로 배우기**: Reflexion은 실제 결과·교정에서 짧은 교훈 후보를 만들고 다음 적용으로 확인한다. 자기평가·저장량·사용 기간을 개선 증거로 삼지 않으며 잘못된 기억을 되돌린다. 평가·승격 기준은 서비스 계획 §4와 통합 계획 §5를 따른다.
- 사용자가 스킬 이름이나 호출 순서를 외울 필요가 없게 한다. 기본 모델의 직접 실행으로 충분하면 추가 agent·생성 단계를 만들지 않는다.
- 일관성은 프로젝트 계약·권한·예산·검사 근거·정확한 상태와 복구로 판단한다. 모든 모델의 동일한 답변·순서나 미검증 환경의 최적 동작을 보장하지 않는다.
- 범용 대응을 지향하되 초기 서비스는 제한된 스택·runtime 조합부터 검증한다. 현재 source·설치본·실호스트 검증과 계획을 구분한다.

## 2. 크로스플랫폼 (Claude + Codex)

**"Claude든 Codex든, 서브에이전트든 병렬 처리든 막힘 없이 동작한다."**

- **공통 정책, 호스트·모델별 특화**: 사고 원칙·권한·검증 기준을 공유하되 skill의 동일 본문이나 Claude 중심 구조를 강제하지 않는다. 호스트별 자동 적재 파일·설정과 평가로 채택한 모델별 절차·예시·본문을 별도 원본으로 둘 수 있다. 공통 저장소에서 시작하고 배포·의존성·소유권 문제를 실증하면 분리도 ADR로 결정한다. 장기 실행을 맡는 새 core와 구분한다.
- **재사용할 기능을 중심으로 구성**: 정책·지침 구성 compiler와 결정적 도구를 중심으로 발전시키고 native에는 최소 plugin/pack, managed에는 모듈·산출물을 제공하는 방향을 검증한다. plugin 유지와 제품 중심 구조 유지를 같은 결정으로 취급하지 않는다. 작은 plugin만으로 같은 효과가 나면 큰 전환을 생략한다. 비교·권한·소유권 경계는 통합 계획 §2를 따른다.
- **현재 상태를 과장하지 않는다**: Claude 플러그인 어댑터는 존재하지만 Codex는 `AGENTS.md`와 CLI 브리지 중심의 부분 지원이다. 선택한 plugin/project 설치 방식의 discovery·권한·hook·제거를 실증한 뒤 지원을 선언한다. 특정 출력 디렉터리 생성만으로 완료 처리하지 않는다.
- **`/code-forge:codex`는 호환 브리지일 뿐**: Claude가 공식 Codex plugin/CLI를 호출하는 교차 검증 경로와, Codex가 code-forge를 직접 호스트하는 네이티브 경로를 구분한다.
- **호스트별 능력 차이를 숨기지 않는다**: 모델명, reasoning effort, 권한, 훅 이벤트, 도구 이름은 각 어댑터가 해석한다. 공통 정책에 특정 호스트 문법을 넣지 않는다.
- **opt-in과 graceful degradation**: 어느 한 호스트나 외부 서비스가 없어도 공통 코어와 다른 호스트가 계속 동작해야 한다.

### 왜 Codex를 독립 호스트로 발전시키는가

- 다른 모델의 관점은 같은 모델의 역할극과 동일한 증거가 아니다.
- 사용자가 Claude와 Codex 중 하나를 주 실행기로 선택해도 같은 불변 제약과 검증 계약을 얻어야 한다. 동일한 답변·실행 순서를 보장한다는 뜻은 아니다.
- 공통 정책의 변경 전파를 유지하면서 각 호스트가 직접 적재할 파일과 필요한 특화 본문을 제공한다. 공용본·특화본의 품질·검증 완료당 총비용·유지 비용을 비교하고 유리한 쪽을 채택한다.

## 3. 토큰 최적화

**"프리셋/조합 방식으로 불필요한 토큰 소비를 최소화한다."**

- **얇은 척추(thin spine)**: 자동 적재 문서에는 불변 제약, 승인 경계, 검증 명령, 조건부 포인터만 둔다.
- **결정적 절차는 코드로**: 설정 판독·명시 옵션 정규화·기록·검사 결과 추출을 모델이 매번 재작성하게 하지 않는다. 필요한 짧은 지침과 구조화 결과를 전달하되 판단 원칙·개인 선호를 기계적 분기로 대체하지 않는다. 기존 shell·CLI에서 작은 경계부터 재사용하며 새 agent loop를 만들지 않는다.
- **포맷과 비용 구분**: plugin을 CLI·MCP로 바꿨다는 이유로 절감을 주장하지 않는다. 상시 목록·선택 본문·도구 schema·중간 출력·재시도·cache·유지 비용을 포함한 실제 검증 완료당 비용으로 판단한다. 추가 workflow가 이득 없는 작업은 host-native를 사용한다.
- **필수 계약은 직접 적재**: 다른 호스트 문서를 읽으라는 자연어 지시만으로 필수 정책을 전달하지 않는다. 호스트의 자동 적재·native import와 후속 Read를 구분하고 공존 파일의 중복·누락을 검사한다. 별도 파일의 개수를 세션의 token 비용으로 간주하지 않는다.
- **증거 기반 확장**: 처음부터 관련 문서를 모두 읽지 않는다. 대상 파일과 가장 가까운 기존 패턴에서 시작하고, 해결되지 않은 질문이 있을 때만 다음 참조를 연다.
- **progressive disclosure**: 스킬은 이름·설명으로 발견하고 선택된 스킬 본문과 필요한 reference만 읽는다. 선택되지 않은 스킬의 상세 절차는 주입하지 않는다. 최소 계약은 지원 환경·입출력·효과·권한·검사 근거·잔여 예산이며 전체 catalog SDK를 선행 구축하지 않는다.
- **CLAUDE.md 60줄 상한**: 매 턴마다 로드되므로 핵심 포인터만 유지
- **include와 포인터 구분**: `@` include는 해당 본문에 항상 필요한 계약에만 쓴다. 선택적 상세는 Markdown 링크로 두고 해당 phase에서 명시적으로 Read한다.
- **Smith 빌드타임 컴파일**: 필요한 역할의 효용이 확인되면 STATE+ACT를 정적 파일로 컴파일한다. 프로젝트 지식 전달만으로 충분하면 별도 agent를 생성하지 않는다. 컴파일 효율과 agent 자체의 작업 효과는 따로 검증한다.
- **에이전트별 도구 제한**: 불필요한 도구를 disallowedTools로 차단하여 도구 선택 오버헤드 감소
- **권한과 역할 구분**: agent 지침·도구 목록은 host sandbox와 같은 보장이 아니다. Codex custom agent의 부모 권한 상속 등 실제 제한을 adapter에서 확인한다.
- **프리셋**: 5개 모듈을 한 줄로 지정 (standard, modern-stack)
- **위임에도 비용 기준 적용**: 독립적인 read-heavy 작업이거나 메인 컨텍스트 오염을 실제로 줄일 때만 서브에이전트를 쓴다. 한 파일·한 판단을 병렬 에이전트로 쪼개지 않는다.

## 4. 독립성

**"외부 의존성 최소, CodeForge의 독립 사용만으로 가치 제공."**

- 로컬 지침·결정적 도구는 선택 connector와 관리형 서버 없이 사용할 수 있다. 모델 작업에는 선택한 모델/호스트가 필요하고, 원격 기억·관리형 실행은 해당 서비스에 의존한다. 연결 장애 시 지원 범위를 명시한다.
- MCP 연동은 전부 opt-in — 미설정 시 graceful degradation
- `session-init.sh`는 `CLAUDE_PLUGIN_ROOT`가 없으면 자신의 설치 경로를 기준으로 동작하고, 선택 기능의 의존성이 없으면 조용히 건너뛴다
- **레지스트리는 배포 채널, 런타임 의존 아님**: 설치된 로컬 기능은 매 실행에 레지스트리를 조회하지 않는다. 모델·선택 connector·원격 코어의 네트워크 의존성과 구분한다.
- **제품과 배포 포맷 구분**: 지침 구성·결정적 도구를 버전 있는 묶음과 host별 패키지로 제공한다. Claude plugin은 필요한 접점으로 유지하고 Codex 등은 지원되는 native 경로를 사용한다. 플러그인이 없는 host에는 대체 pack을 제공한다. managed는 모듈·산출물을 직접 소비하고 별도 CLI·daemon을 모든 사용자에게 강제하지 않는다.
- **직접 실행 보존**: 새 core 없이도 native pack을 사용할 수 있어야 한다. core 설치만으로 작은 작업에 원장·Inbox를 강제하지 않는다. managed Work의 결과가 불명확할 때 native로 자동 재실행하지 않는다.

- **범용 코어와 분야별 기능**: 개인화의 기억·권한·맥락·교정 계약은 CodeForge/Git/관리형 Work 없이 사용할 수 있어야 한다. 개발 스킬·검사와 실행 원장은 선택 모듈로 연결한다. 저장·검색·모델·호스트·접점은 어댑터 경계로 교체하되 처음부터 별도 서비스·저장소·공개 SDK를 만들지 않는다.

### 향후 스킬 레지스트리 통합 원칙

- 로컬에서만 쓸 수도, 레지스트리에 등록할 수도 있다
- 등록하면 다른 프로젝트/팀원이 검색 → 다운로드 → 로컬 세팅
- 런타임에 레지스트리 호출 제로 — 설치/업데이트 시에만 사용

## 5. 사용자 경험

**"설치 → 세팅 → 사용까지 매끄럽게."**

- **무소음 원칙**: session-init.sh는 버전 일치 시 아무 출력 없음. 불일치 시에만 한 줄 알림
- **최소 놀람 원칙**: 읽기 전용·가역적 검사는 조용히 수행할 수 있지만, 파일 변경·외부 쓰기·비용·파괴적 작업은 범위와 결과를 드러낸다
- **선택한 업데이트 정책**: CodeForge 자체 SessionStart는 기본적으로 네트워크를 호출하지 않는다. 현재 dev clone 갱신은 `FORGE_AUTO_UPDATE=1` opt-in이며 marketplace 설치물은 native manager가 맡는다. 계획하는 자동/수동·채널/범위 설정과 활성화·복구 검증은 통합 계획 §8을 따른다. 이미 허용된 호환 갱신을 매번 재승인받지 않는다.
- **갱신과 활성화 구분**: host manager와 공통 도구가 같은 설치물을 중복 갱신하지 않는다. 제공·설치·현재 세션·프로젝트 생성 버전을 구분하고 작업 중에는 고정한 조합을 유지한다. 사용자 수정 보존과 검증된 복구 경로를 확인하며 host의 미지원 기능은 표시한다. 현재 source·cache·설정 파일의 버전 일치만으로 모든 세션에 적용됐다고 주장하지 않는다.
- **Smith 온보딩**: 현재 setup은 사용자가 Smith를 켜면 생성·빌드를 이어 실행한다. 향후 신규 일반 역할 생성의 일괄 추천을 빼고 기본 실행·지식 전달·custom agent의 이득으로 선택하는 방향을 검증한다. 기존 활성 설정은 유지하고 허용한 호환 이관에 반복 승인을 요구하지 않는다. 현재 스킬 UI 수정은 별도 구현 단계다.
- **기존 사용자 전환**: 패키지 업데이트와 프로젝트 이관을 구분한다. 소유권·무수정·호환이 확인된 허용 범위만 백업·검증 후 자동 이관하고 사용자 수정·충돌은 해당 부분만 보류한다. 상태·변경점·복구를 안내하고 기존 명령은 최소 두 릴리스 유지한다. 상세 계약은 통합 계획 §8을 따른다.
- **음성 입력**: 웹·모바일은 녹음 → 전사 확인/수정 → 기존 작업에 전송하는 경로부터 검증한다. 텍스트 대안과 로컬 Voice를 보존한다. 질문 답변과 실제 반영 승인을 구분하고 음성으로 새 권한을 만들지 않는다. 처리 위치·보존·STT 비용과 GH/G3의 범위는 통합 계획 §5를 따른다.
- **hooks**: 위험 명령은 차단한다. 자동 lint/format은 프로젝트의 로컬 바이너리가 있을 때만 실행하며 패키지를 자동 다운로드하지 않는다. managed 후보는 변경 hook 종료 뒤 고정하고 이후 변경은 검사·승인 근거를 무효화한다.

## 6. 대장간 체계 (Forge Concept)

**"인지적 도제이론을 대장간 메타포로 구현한다."**

인지적 도제이론(Cognitive Apprenticeship)은 6단계로 구성된다: Modeling(시범) → Coaching(지도) → Scaffolding(발판) → Fading(제거) → Articulation(명료화) → Reflection(성찰). 대장간 메타포는 이 이론을 표현한 배경이며 제품의 필수 구성이나 고정 실행 순서를 결정하지 않는다.

| 대장간 | 역할 | 구현체 | 도제이론 |
|--------|------|--------|---------|
| **Forge** (대장간) | 전체 작업·학습 환경 | CodeForge 제품군. 기존 host pack과 계획 중인 실행 core | 학습 환경 |
| **Smith** (대장장이) | 선택적 지식·작업 profile 조합과 agent 컴파일 | `plugins/smith/` | Modeling (필요한 지식·행동을 근거로 정의) |
| **Anvil** (작업대) | 사용자 인터페이스 | CLI, 스킬, 커맨드 | Coaching (작업마다 가이드) |
| **Whetstone** (숫돌) | 서비스 범위 밖의 개인 코딩 연습 | 이미 독립된 `coding-practice` 저장소 | Scaffolding → Fading (점진적 힌트 → 힌트 제거) |
| **Blueprint** (설계도) | 사고모델 + 규칙 | `rules/` | Articulation (원칙 명료화) |
| **Bellows** (풀무) | 로깅/관찰 | `hooks/` | Reflection (사용 패턴 성찰) |
| **Assayer** (감정사) | 테스트 전략·BDD·테스트 작성 | `agents/assayer.md` | 검증할 기준의 명료화 |

이 체계는 코드에 강제하지 않는다. 기존 Claude 배포의 디렉토리는 호환을 유지하고 다른 host의 출력은 각 host 규격을 따른다. 대장간 이름은 문서와 커뮤니케이션에서만 사용한다.

Blueprint의 사고 guidance·개인 preference와 기계적으로 집행할 invariant·승인 경계를 구분한다. 새 core는 관리 중인 Work의 권한·독립 검증·승인·실행 원장을 소유한다. Assayer의 테스트 작성과 core verifier의 판정, Bellows 관찰과 core ledger의 권위 상태는 서로 대체하지 않는다. Attempt 안의 GAVA `APPLY`와 action의 실제 반영 `APPLY`도 namespace로 구분한다.

Glow는 session/live 표시, Hearth는 재채택할 경우 다중 source의 Markdown 보고서를 맡는다. Herdr는 제어 가능한 터미널 adapter이며 관찰 UI와 같은 권한으로 취급하지 않는다. core schema·DB를 UI가 직접 수정하지 않는다.

## 7. Smith (Agent Smith System) 설계 철학

**"STATE(지식)와 ACT(행동)를 분리하고, 별도 역할이 이득일 때 에이전트로 조합한다."**

- STATE class: 반복 작업에 필요한 근거 있는 지식. 일반 스택 지식이나 역할 선언만으로 전문성이 증가했다고 가정하지 않는다.
- ACT class: 필요한 행동·도구·산출물·검증 조건. 실제 권한 경계는 host/runtime에서 확인한다.
- instance: STATE + ACT의 별도 역할이 기본 agent·지식 전달보다 유익하면 컴파일한다. 결과가 0개여도 정상이다.
- 기본 profile: 검사 명령·수정 경계·고유 예외·근거 위치를 작은 계약으로 재사용하고 현재 모델의 직접 실행을 기본으로 둔다. 기존 지침이 충분하면 별도 profile 파일을 추가하지 않는다. profile 선택과 새 agent 생성은 분리하며 초기 생성·갱신·읽기 비용을 반복 탐색·교정 절감과 비교한다.
- 작업별 구성: 위임이 유익할 때 선택 skill·근거·작업 범위·검증 조건을 조립해 기본 subagent에 전달한다. 별도 실행 설정이 필요하면 host가 실제 지원하는 임시 정의를 사용한다. 매 작업에 새 페르소나를 생성하거나 영구 역할 파일을 썼다가 지우는 것을 기본 절차로 만들지 않는다.
- 생명주기: 결과·근거·미해결 인계를 회수한 뒤 일회 instance·작업용 정의를 종료·정리한다. 실패·취소·crash·재개에도 소유권·권한·증거를 보존한다. 파일 삭제는 사용한 token·host 기록 삭제가 아니며 반복 이득이 확인된 구성만 승인 후 재사용 후보로 남긴다.
- 유지 판단: 프로젝트 지식의 이득, custom agent 컨테이너의 이득, 위임·context 격리의 이득을 나눠 비교한다. 기존 Smith 정의는 호환을 보존하며 고도화·신규 추천 중단·후속 폐기는 작업 품질과 전체 비용에 근거한다.

### Smith STATE ↔ modules 경계

| 구분 | 역할 | 예시 |
|------|------|------|
| Smith STATE | 여러 역할/작업이 재사용할 근거 있는 지식 | 고유 도메인 예외·반복 실패 사례·검증에 필요한 지식 |
| modules | **프로젝트 컨벤션** 상세 | "이 프로젝트에서 React를 이렇게 쓴다" |

STATE는 선택된 작업의 지식 조합, modules는 프로젝트 컨벤션이다. 이 구분만으로 둘의 원문을 중복 주입하거나 영구 agent 생성의 필요성을 주장하지 않는다. 사실의 정본과 출처를 유지하고 필요한 내용만 선택한다. 제품 정체성은 역할 파일 수보다 프로젝트에 맞는 판단·검증 결과로 확인한다.

## 8. /start 원큐 워크플로우 원칙

**"목표 전달은 간단하게, 실제 실행 경로는 환경과 작업에 맞게 선택한다."**

- `/start`는 로컬의 호환 진입점이다. 검사만 필요한 작업이나 관리형 실행에 전체 구현·테스트·커밋 흐름을 강제하지 않는다.
- native의 guided checkpoint는 보존한다. managed의 직접 실행은 서브에이전트 없이 한 agent가 수행한다는 뜻이며 같은 Work의 권한·원장·검증 계약을 따른다. 질문·승인은 Inbox에 연결하고 기존 유효 허용 범위를 반복 확인하지 않는다.
- agent가 다음 스킬·도구·위임을 선택하고 host/core가 실제 효과·권한·예산·상태 전이를 집행한다. 하위 스킬의 수정 loop·질문·최종 판정을 두 번째 scheduler로 만들지 않는다.
- 기존 검사 실행, 테스트 생성, runner 설치는 다른 효과다. 필수 검사 부재·미실행을 통과로 표시하지 않고 전체 재시도 예산을 하위 호출과 공유한다.
- profile의 프로젝트 사실·승인된 개인 선호·고정 검사 recipe·작업 context를 구분하고 정본을 복제하지 않는다. 인계·정리 뒤에도 필요한 검사 증거와 미해결 상태를 보존한다.

## 9. 개인 코딩 연습의 범위 분리

개인 연습 Whetstone은 이미 별도 Git root와 원격 저장소를 가진 `coding-practice` 프로젝트다. CodeForge 서비스·필수 pack·설치·실행·출시 조건에 포함하지 않는다. 추가 저장소 생성이나 코드 이동을 전제하지 않으며 연습 내용과 교육 방식은 그 저장소에서 관리한다.

- 서비스의 개인 선호는 연습 저장소 없이 생성·승인·사용·철회·삭제할 수 있어야 한다.
- 기존 승인 profile은 사용자가 지정한 외부 source로 선택 연결할 수 있다. 기존 경로를 자동 변경하거나 연습 원문을 공개 pack에 번들·자동 수집하지 않는다.
- `forge whet`는 반복 패턴의 규칙 후보를 만드는 호환 명령이다. 서비스 개인화와 함께 사람 연습 기능과 구분하며 권한 있는 승인 전에는 정책 효력이 없다.

## 10. assayer (테스트 생성) 자립 원칙

**"테스트 작성 지식을 제공하되, 실행 환경과 독립 검증을 구분한다."**

- 테스트 전략·작성 지침은 CodeForge에서 제공한다. 실제 테스트 실행은 프로젝트 runner·의존성·환경에 의존하며 없으면 준비 필요 상태로 표시한다. 검사를 위해 패키지를 묵시적으로 설치하지 않는다.
- `docs/assayer-guide.md`에 상세 가이드 (선택자 우선순위, 모킹 사유 분류, Fail-First 전략 등)
- agents/assayer.md는 핵심 계약을 자체 보유하고, 막힌 단계에서만 가이드의 대응 절을 점진 적재
- TDD 모드: 소스 미존재 시 자동으로 Red-Green-Refactor 사이클 진입
- managed Work에서는 Assayer가 테스트를 제안·작성하고, core verifier가 고정된 RepositoryProfile·recipe로 독립 판정한다. 테스트·fixture·threshold 약화를 검출해야 한다.

- [ ] 역할·정본·수명을 구분하고 메타포 때문에 불필요한 기능이나 단계를 추가하지 않는가?

- [ ] 기존 명령·Voice·Glow·프로젝트 정본과 배포/복구 계약을 보존하는가?
