# code-forge 리팩터링 검토본

- 작성: 2026-09-17
- 구현 저장소: 이 `code-forge` 저장소
- 기준 브랜치·HEAD: `main` · `1779c8ac9638c755d341b16e708f7e44aaf15b75`
- 상태: 의사결정 전 검토용
- 상세 근거: [정본 계획](code-forge-refactoring-plan.md)

이 문서는 전체 계획을 빠르게 검토하기 위한 읽기용 버전이다. 구현 범위와 완료 기준은 유지하고 파일별 세부 작업과 반복되는 설명을 줄였다. 사용자 검토와 승인 항목 결정이 끝나면 [정본 계획](code-forge-refactoring-plan.md)에 반영한다. 이 브랜치에는 문서만 있으며 아래 미커밋 코드와 검사 결과는 원래 컴퓨터의 이력이다.

## 먼저 볼 결론

code-forge는 Claude Code 플러그인으로 유지한다. 호스트가 보내는 이벤트는 `hooks/`에서 받고 검사·삭제·상태 처리처럼 다시 쓸 수 있는 로직은 `lib/`로 옮긴다. 사용자 명령은 `bin/forge`가 제공한다.

이번 리팩터링은 세 가지 결과를 함께 만든다.

1. 검사와 cleanup이 실제 결과를 정확하게 보고하고 사용자 파일을 안전하게 보존한다.
2. 세션 상태·사용 기록·handoff가 손상되거나 과거 결과를 현재 결과로 오인하지 않는다.
3. 서브 Claude/Codex에 보내는 지시 프롬프트 생성기를 실제 실패와 평가 결과로 개선한다.

GEPA는 처음부터 넣지 않는다. 수동 파일럿으로 평가 방식이 작동한다고 확인하고 자동 채점과 비용 조건이 갖춰진 경우에만 후속 실험으로 검토한다.

## 현재 상태

원래 컴퓨터의 code-forge 작업 트리에는 기준 HEAD 이후의 미커밋 변경이 있다. 이 브랜치에는 포함되지 않았다. 다른 컴퓨터에서 구현을 시작할 때 현재 Git 상태와 실제 파일을 다시 확인한다.

2026-09-16 로컬 확인 결과:

- `git diff --check` 통과
- 배포 Bash 스크립트 구문 검사 통과
- 실행 안전성 회귀 검사 23건 통과
- 상태 갱신 회귀 검사 9건 통과

아직 확인하지 않은 항목:

- Linux와 실제 CI
- ShellCheck
- 실제 ESLint·tsc·테스트 러너
- 실제 Claude hook 입력과 응답
- 실제 Codex 지침·스킬 발견
- 소스 설치본과 릴리스 캐시 설치본의 동작 일치

이는 원래 컴퓨터의 일부 구현과 로컬 fixture 결과다. 이 브랜치의 코드나 다른 컴퓨터에서 통과한 결과로 취급하지 않는다.

## 진행 순서

```text
0. 현재 변경 보존과 분류
1. 검사·cleanup 안전성 완료
2. 지시 프롬프트 생성기 로컬 파일럿
3. 상태 기록과 handoff 복구 수리
4. Claude/Codex 지침 적재와 계약 정리
5. 검증된 생성기만 code-forge에 편입
6. 실제 행동 평가 후 한 번 릴리스
```

2단계 파일럿은 3단계의 Bellows 계측 수리를 기다리지 않는다. 먼저 검증된 평가 항목을 만든 뒤 필요한 결과 필드만 계측에 반영한다.

## 지시 프롬프트 생성기 파일럿

평가 대상은 개인용 `~/.codex/skills/context-handoff/SKILL.md` 3절과 5절에서 만드는 서브 Claude/Codex 지시 프롬프트다. 다른 컴퓨터에 해당 스킬이 있는지 먼저 확인한다. 활성 스킬은 파일럿 동안 수정하지 않고 사본으로 비교한다.

### 데이터 처리 권고안

1. 사용자가 지정한 실제 세션을 최대 5개까지 로컬 추출기로 읽는다.
2. 원문에서 프롬프트 해시·길이, 턴 수, 도구 오류, 사용자 거절, 비용, 중단 사유 같은 결과 필드만 추출한다.
3. 평가 사례로 옮길 때 사람·저장소·경로·업무번호·내부 URL을 일관된 가명으로 바꾼다. 비밀번호·토큰은 완전히 제거한다.
4. 같은 저장소인지, 절대경로인지, 별도 worktree인지처럼 결과에 영향을 주는 관계는 보존한다.
5. 평가 자료와 추출 결과를 확인한 뒤 이번 작업이 만든 원문 임시 파일과 치환표를 삭제한다. 기존 세션 원본은 수정하지 않는다.
6. 외부 모델을 쓰게 되면 익명화된 사례만 전달한다.

이 방식은 실제 실패를 평가에 반영하면서 평가셋이 다른 도구로 이동하거나 오래 남을 때의 노출을 줄인다. 익명화가 실패 원인까지 지우지 않도록 값과 구조를 구분해서 처리해야 한다.

### 평가 자료

- 실제 사례에서 확인한 실패와 합성 사례를 섞어 20건을 만든다.
- 10건은 후보를 만드는 데 사용하고 10건은 비교에 사용한다.
- 별도 holdout 10건은 후보 채택 직전에 한 번만 연다.
- 저장 결과에는 사례 ID, 생성기 해시, 길이, 항목별 점수, 위반 코드와 결과 지표만 남긴다.
- 실제 프롬프트와 대화 본문은 평가 결과에 저장하지 않는다.

### 평가 기준

지시 프롬프트에는 다음 정보가 필요한 경우 빠짐없이 들어가야 한다.

- 체크포인트 절대경로
- 작업 저장소와 세션을 여는 폴더
- 브랜치와 기준 HEAD
- 이번 수정 범위와 제외 범위
- 완료 조건과 검증 방법
- 바로 수행할 다음 한 단계
- 결과 보고와 같은 체크포인트 갱신 지시

권한 확대, 비밀값 포함, dirty worktree 무시, 존재하지 않는 실행기 강제는 중대 위반으로 처리한다. 하나라도 발생하면 해당 사례는 0점이다.

후보는 기준선에서 자주 나타난 실패 두 개만 고친다. 문서 점수가 올라도 실제 작업에서 재질문·도구 오류·범위 위반이 늘면 채택하지 않는다. 이 경우 루브릭을 먼저 수정한다.

## 상태·기록 수리

원래 컴퓨터에는 `lib/state_io.py`와 회귀 검사 9건이 선행 구현돼 있다. 이 브랜치에는 없으므로 코드를 별도로 가져와 검토한 경우에만 재사용한다. 동시 쓰기 잠금, 호출별 임시파일, 깨진 JSON과 심링크 보존을 확인한다.

Bellows는 실제 stdin JSON을 읽도록 바꾼다. 확인할 수 없는 모델·시간·성공 여부를 추정해서 채우지 않는다. Agent 호출과 SubagentStop 사이에 연결 ID가 없으면 하나의 실행으로 합치지 않는다.

handoff의 CURRENT는 문서 앞부분에서 갱신하고 과거 이력은 뒤에 둔다. 새 세션은 CURRENT의 브랜치·HEAD·dirty 상태를 실제 Git과 비교한다. 과거 세션의 성공을 현재 검증 결과로 사용하지 않는다.

## 지침과 계약 정리

프로젝트 공통 명령과 작업 규칙은 루트 `AGENTS.md`에 한 번 둔다. `CLAUDE.md`는 `@AGENTS.md`와 Claude 전용 내용만 가진다. 기존 사용자 문서는 통째로 다시 만들지 않고 필요한 부분만 병합한다.

GAVA는 실제 행동으로 검사한다. 관련 코드와 완료 조건을 읽은 뒤 범위 안에서 수정한다. 실제 명령으로 검증하고 실패 원인을 고쳐 재실행해야 한다. GAVA 용어를 출력한 사실은 완료 근거가 아니다.

CI 검사는 재사용 가능한 실행 파일로 옮긴다. 없는 testgen·critic·마스터플랜 참조는 현재 존재하는 역할과 작업으로 교체한다. Whetstone은 pass 이벤트를 개선 후보로 세지 않으며 알 수 없는 반복률은 미확인으로 남긴다.

## code-forge 편입과 GEPA

파일럿을 통과한 공통 항목만 `skills/handoff/SKILL.md`와 평가기에 반영한다. 개인용 `context-handoff` 전체를 복사하지 않는다. 저장소에는 일반화된 코드, 스키마, 빈 루브릭 서식과 합성 fixture만 둔다.

GEPA 실험은 아래 조건을 모두 충족해야 한다.

1. 평가 사례가 30건 이상이고 train·val·미사용 holdout이 분리돼 있다.
2. 텍스트 피드백을 내는 채점이 사람 없이 반복 재현된다.
3. 문서 점수와 실제 작업 결과가 같은 방향으로 움직인다.
4. 수동으로 쉽게 고칠 실패가 남지 않았다.
5. 모델 호출 수, 비용, 출력 길이와 중단 상한을 사용자가 승인했다.

조건이 부족하면 수동 평가 루프를 유지한다. GEPA를 사용하더라도 명시적인 valset을 전달하고 활성 스킬은 사람의 채택 결정 뒤에만 바꾼다.

## 실제 행동 평가

최종 후보는 깨끗한 소비 프로젝트에서 다음 일곱 상황으로 확인한다.

1. 작은 단일 파일 수정
2. 미추적 파일·모노레포·검사 설정 오류
3. 실패하는 회귀 테스트가 있는 정책 변경
4. `/setup`과 Smith 실행 후 새 세션의 지침 발견
5. 긴 CURRENT와 브랜치 변경 뒤 handoff 복구
6. 실제 cleanup·Skill·Agent·hook 호출
7. 같은 사실로 지시 프롬프트를 생성한 뒤 다음 작업자의 첫 행동

모델을 쓰는 비교는 같은 호스트·모델·effort·권한·초기 파일로 맞춘다. 전체 transcript는 공개 저장소에 넣지 않는다.

## 결정할 항목

결정은 아래 순서로 하나씩 진행한다. 결과를 보기 전에는 채택이나 배포를 미리 승인하지 않는다.

| 순서 | 결정 | 현재 권고 |
| --- | --- | --- |
| 1 | 사례 출처와 원문 처리 | 실제 세션 최대 5개 + 합성 사례, 파생 평가셋 익명화, 임시 원문·치환표 삭제 |
| 2 | 모델 사용량 | 외부 유료 API 없이 수동 후보 1개부터 시작, 반복 실행 전에 상한 결정 |
| 3 | 채점과 재채점 | 결정 규칙 자동 채점, 모호한 항목만 사람 검토 |
| 4 | 후보 채택과 적용 범위 | val·holdout·실제 결과가 함께 통과할 때 code-forge에 편입 |
| 5 | GEPA 실험 | 다섯 진입 조건을 모두 충족한 경우에만 비용 상한을 정해 실행 |
| 6 | commit·push·릴리스 | E1~E7 소스 검증 후 승인, 릴리스 캐시 재검증으로 종료 |

## 완료 기준

- 허위 PASS, 범위 밖 삭제, 사용자 문서 손실이 없다.
- 상태 동시성 손상, 가짜 duration·success, handoff 복구 오판이 없다.
- 실제 Claude hook과 Codex 지침·스킬 발견을 확인했다.
- 프롬프트 후보를 val·holdout·실제 결과로 채택하거나 근거와 함께 기각했다.
- 개인 프롬프트·대화·평가 데이터가 Git 추적 파일에 없다.
- E1~E7의 소스 설치본 결과를 기록했다.
- 사용자 승인 뒤 한 번 릴리스하고 캐시 설치본의 핵심 동작을 다시 확인했다.

## 이번 범위에서 만들지 않는 것

- Codex 전용 플러그인과 별도 실행 엔진
- flow-toolkit 부활과 새 마켓플레이스
- 세션 DB, 멀티레포 동기화, 상시 registry
- 자동 규칙 승격과 자동 스킬 수정
- 개인 데이터가 든 공개 fixture
- 기능별 중간 릴리스
