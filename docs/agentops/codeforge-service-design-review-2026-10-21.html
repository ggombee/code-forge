Product ecosystem / 추가 설계 제안

공개 부품은 독립적으로, 새 제품은 완성된 경험으로

기존 사용자는 CodeForge만 설치해 계속 쓴다. 새 제품은 같은 도구를 가져와 개인화된 작업을 연결한다. 제품명과 저장소를 분리해도 기존 기능을 축소할 필요는 없다.

01 · KEEP기존 사용 경험 유지

기존 설치·명령·설정을 보호하고 공개 도구를 계속 업데이트한다.

02 · CONNECT작은 소비 예제로 검증

새 제품이 CodeForge의 고정 버전을 사용하도록 연결한다. 사본을 따로 수정하지 않는다.

03 · PACKAGE새 제품을 별도로 제공

독립 설치·릴리스가 가능해지면 제품 레포와 배포를 분리한다. 공개 범위는 모듈별로 결정한다.

Naming / 작업실과 제작 도구

메타포는 이해를 돕고 이름은 책임을 드러낸다

전체 서비스는 ‘나의 작업실’, CodeForge는 그 안에서 사용하는 ‘개발 도구’, Blueprint는 ‘판단 기준’으로 설명한다. 화면 메뉴는 기억·작업·검증·승인처럼 쉬운 말로 유지한다.

Atelier · 나의 작업실

새 제품명 가칭. 기억과 도구, 진행 중인 작업을 한 화면에서 연결한다. CodeForge 외 다른 작업 도구도 추후 연결할 수 있다.

CodeForge · 개발 도구

기존 공개 제품의 이름을 유지한다. 규칙·스킬·구성·연결 기능이 함께 있어 전체를 Blueprint로 개명하면 역할이 좁게 보인다.

Blueprint · 판단 기준

멘탈모델·규칙·승인된 선호를 표현하는 형식과 공용 템플릿. 사용자의 실제 프로필은 개인·조직 저장소에 둔다.

Library · 기억과 근거

결정 이유·출처·교정 이력·승인 상태를 관리한다. Blueprint가 정의한 형식에 맞는 관련 기억을 작업에 전달한다.

Workbench · 작업 관리

목표·질문·진행 상태·재시작·취소를 관리한다. 작업 원장은 하나가 책임지고 화면은 허용된 상태를 보여 준다.

Inspector · 독립 검증

고정된 검사 기준으로 결과를 판정하고 반영 결과를 확인한다. 기존 테스트 작성자 Assayer와 최종 판정의 책임을 구분한다.

기존 개념과 연결: Smith는 에이전트 구성·컴파일, Blueprint는 판단 기준, Anvil은 사용자 접점이라는 기존 의미를 유지한다. Workbench는 작업 관리 책임을 설명하는 가칭으로 Anvil의 이름을 바꾸는 제안은 아니다. 에이전트의 ‘도제’ 성격은 교정받고 제한된 권한으로 배우는 동작 원칙으로 사용한다.

프롬프트 생성·평가·개선은 새 제품의 별도 책임으로 둔다. Smith의 정적 에이전트 구성과 runtime 프롬프트 생성을 혼동하지 않는다. Bellows의 관찰 기록은 작업 결과에 연결해 평가 근거로 사용하되 관찰 로그 자체를 성공 판정으로 쓰지 않는다. Library·Workbench·Inspector 역시 설명용 명칭이다. 실제 패키지명·폴더명·제품명은 구현 전에 기존 명칭과의 충돌을 확인한다.

Value & ownership / 공개 코드와 서비스

무료 도구, 유료 운영, 비공개 데이터를 구분한다

CodeForge는 무료 사용자에게도 독립적인 가치를 제공한다. 새 제품의 수익은 관리형 실행·모델 사용·운영·조직 지원에서 검증한다. 고객의 실제 기억은 코드 라이선스와 별도로 보호한다.

기존 로컬 메모리 조회·수정·삭제·내보내기와 기본 안전성은 무료 제공 방향을 유지한다. 관리형 환경의 저장·실행 비용은 구독과 사용량에 포함한다. 새 제품 코드의 공개 범위는 미정이다.

실제 프로필·지식·키는 제품 코드에 포함하지 않는다

공개하는 것은 메모리를 다루는 형식·기능·합성 예제다. 사용자의 판단 기록, 프로젝트 문서, 회사 자료, API 키는 개인·조직별 저장소에 둔다. 엔진의 공개 여부와 데이터 접근 권한은 별도 결정이다.

두 레포로 나눌 때 지킬 연결 규칙
  • 기존 code-forge는 공개 도구를 소유한다. 새 제품 레포는 UI·작업 관리·서비스 구성을 소유하는 후보로 둔다.
  • 새 제품은 태그·버전·digest가 고정된 패키지나 배포물을 가져온다. 다른 레포의 내부 파일 경로를 직접 API로 쓰지 않는다.
  • 공용 규칙 수정은 원본 CodeForge에 반영한다. 비슷한 사본을 새 제품에서 별도로 관리하지 않는다.
  • 호환표와 통합 검사를 두고 버전 불일치 시 해당 연결을 명확히 중단한다. 기존 독립 사용은 유지한다.
  • 레포 분리 전 독립 설치·제거·업데이트를 시험한다. 새 레포 생성·공개·라이선스 변경은 이번 HTML 편집에 포함하지 않는다.

에이전트를 실행하는 환경

서비스가 모델·격리 실행기·작업 상태·메모리·복구를 관리한다. 사용자 PC가 꺼져도 예산 안에서 작업을 이어 간다. 사용자마다 상시 VM을 켜두는 대신 작업 시 실행하고 승인 대기 중에는 체크포인트를 남기고 중지한다.

메모리와 작업 상태의 영속성은 실행기 상시 가동과 분리한다. 중지·재개·스냅샷 기능과 요금은 공급자별로 검증한다. [20] [21]

만든 앱을 배포하는 환경

초기는 인증된 임시 미리보기와 고객이 연결한 호스팅 계정으로의 배포를 지원한다. 앱의 상시 서버·DB·트래픽·도메인 비용은 에이전트 실행 비용과 분리한다.

“한 번에 배포”는 승인된 대상·환경·비밀정보를 재사용하는 UX다. 운영 데이터 마이그레이션, 공개 전환, 유료 리소스 생성은 별도 확인한다. preview URL이 자동으로 비공개가 된다고 가정하지 않는다. [23]

실행 중인 코드에는 관리 서버 자격증명과 다른 고객의 저장소 접근 권한을 주지 않는다
  • 온보딩은 승인된 템플릿·고정 이미지로 지원 스택을 좁힌다. 임의 repo의 모든 빌드·배포를 첫날부터 보장하지 않는다. 환경 설치 스크립트도 비신뢰 코드로 취급한다.
  • GitHub App처럼 선택 repo와 최소 permission을 부여할 수 있는 연결을 우선 검토한다. 읽기·PR 생성·merge·배포 권한은 구분한다. 토큰은 실행 시 제한적으로 발급하고 철회·만료 시 재확인한다. [22]
  • tenant별 실행·스토리지·cache 접근을 격리한다. 비공개 의존 패키지와 빌드 캐시를 다른 고객에게 노출하지 않는다. 임의 egress·채굴·스팸·대량 스캔을 제한하고 체험 계정에 동시성·시간·비용 상한을 둔다.
  • worker 수·재시도·모델 호출·다운로드·디스크·출력·preview TTL에 상한을 둔다. 예산은 실행 전에 예약하고 실제 청구와 정산한다. 공급자 사용량 지연과 취소 중 진행 중인 호출 비용을 감안한다.
  • 시작 지연, 저장소 연결 실패, 첫 검증 성공까지의 시간, 수동 환경 수정 횟수, 연결 철회 성공률을 측정한다. 연결 계정·region·데이터 전송을 사용자가 확인할 수 있어야 한다.
  • 배포 전 tested SHA·환경·대상을 고정한다. 실패 시 무조건 재실행하지 않고 외부 상태를 조회한다. 웹 롤백과 DB 변경 복구는 별도 절차로 둔다.

공급자는 E2B·Modal 같은 외부 sandbox 후보를 먼저 비교한다. CPU 단위·격리·부팅·지속시간·중지·region·egress·삭제 조건을 같은 작업으로 시험한 뒤 고른다. 관리형 worker를 직접 운영하면 고정비·보안 대응 부담이 커지므로 처음부터 VM 관리 플랫폼을 재구현하지 않는다. [19] [20]

보안 설명의 변경: 완전관리형 실행에서는 코드·프롬프트·메모리 일부가 서버와 승인된 모델에서 처리된다. 로컬 전용의 “원문이 기기 밖으로 나가지 않는다”는 설명을 이 상품에 적용하지 않는다. 암호화·접근 통제·보존 제한·지원자 접근 승인을 제공하고 서버가 복호화해 처리하는 범위에 대해 서버 비가시 E2EE를 약속하지 않는다.
Learning loop / 제품의 기본 데이터 흐름

긴 요청과 위임 프롬프트를 다음 작업의 개선 근거로

사용자가 직접 쓴 요청, 메인 에이전트가 Herdr로 전달한 업무 지시, 실행 결과와 사용자 교정을 하나의 작업 사례로 연결한다. 사용자 판단을 기억하는 과정과 지시 프롬프트를 개선하는 과정을 나눠 관리한다.

01 · CAPTURE동의한 기록만 수집

사용자 원문·위임 지시·실제 실행 입력·수정 요청을 구분하고 Work/Attempt ID로 연결한다.

02 · INTERPRET의도와 범위를 분리

상시 선호, 이번 작업의 조건, 프로젝트 정책, 단순 배경을 나눠 후보로 만든다.

03 · GENERATE모델에 맞춰 지시 생성

승인된 기준과 관련 근거만 선택해 모델·호스트별 프롬프트를 만든다. 최종 전달본도 기록한다.

04 · VERIFY행동 결과와 교정 연결

검사 결과·의도 이탈·재작업·질문·시간·비용을 기록한다. 종료 코드만으로 성공 처리하지 않는다.

05 · OPTIMIZE생성기 개선 후보 비교

GEPA 등으로 생성 지침·예시 선택·구성 후보를 만들고 분리된 평가 작업에서 비교한다.

06 · RELEASE검증된 버전만 적용

제한된 시험 적용 후 승인·버전 고정·롤백을 거친다. 다음 작업에서 효과가 유지되는지 측정한다.

두 종류의 갱신: Library/Blueprint에는 “사용자가 무엇을 원했는가”를 승인된 기억으로 반영한다. 프롬프트 생성기에는 “그 의도를 어떤 방식으로 전달했을 때 실제 작업이 잘됐는가”를 평가된 버전으로 반영한다. GEPA는 모델 가중치 학습과 구분되는 텍스트 후보 최적화 도구다. [16] [17]
Herdr 로그 연결, 기억 승격, GEPA 검증 설계

프롬프트 파일 수보다 원인과 결과의 연결이 중요하다

user_request → approved_intent → delegation_prompt → delivered_prompt → runtime/model/version → result/evidence → user_correction
함께 기록할 값: source/author, realm, Work/Attempt/parent ID, source revision, profile/generator 버전, 정책 digest, 실행 환경, 비용, 수집 동의와 보존 기한.

Herdr는 지시를 전달하는 선택형 adapter다. 프롬프트가 전송됐다는 기록과 실제 runtime이 받은 입력을 구분한다. 실제 입력을 확인할 수 없는 경로는 delivery_unverified로 남기고 학습 근거의 신뢰도를 낮춘다. 모델의 비공개 내부 추론을 수집할 필요는 없다. 허용된 요청·도구 결과·최종 결과·검증 증거를 사용한다.

AI가 작성한 위임 지시를 사용자 원문으로 취급하지 않는다. 반복된 AI 표현만으로 “사용자 취향”을 만들면 에이전트의 편향이 강화될 수 있다. 사용자 직접 교정·승인과 단순 무응답도 구분한다. 실패·취소·결과 미확인 사례를 삭제해 성공 사례만 남기지 않는다.

입력 예시 · 합성 사례추출 후보적용 범위
“이번 시제품은 외부 서비스 없이 빨리 확인해줘.”외부 서비스 제한·빠른 확인해당 작업의 제약. 모든 작업의 영구 규칙으로 승격하지 않음.
“설계를 바꾸면 대안과 이유를 함께 보여줘.”선택 이유 설명 선호사용자 확인 후 프로젝트 또는 개인 선호로 승인. 정책은 우회하지 못함.
메인 에이전트가 “테스트는 생략”이라고 위임생성기의 누락·정책 충돌 후보사용자 취향이 아님. 검사 생략은 안전 실패로 평가.

수집은 초기에, 자동 최적화는 평가가 준비된 뒤

첫 버전부터 스키마·출처·교정·동의·삭제 연결을 만든다. 로그가 적을 때는 공용 기준과 사용자 승인 기억으로 생성한다. 수집을 시작했다고 매 요청마다 GEPA를 실행하지 않는다. 같은 실패가 반복되거나 일정한 평가 단위가 쌓였을 때 제한된 배치로 실행한다.

  • 최적화 대상은 우선 “메인 에이전트가 하위 에이전트에게 보내는 지시를 만드는 생성기”로 좁힌다. 한 작업의 문장만 예쁘게 다듬는 최적화와 구별한다.
  • 평가기는 생성된 프롬프트의 문체만 보지 않고 하위 runtime의 실제 작업을 검사한다. 테스트·요구 충족·사용자 교정 시간을 함께 사용하고 모델 자체 평가만으로 승격하지 않는다.
  • 학습·후보 선택용 검증·최종 holdout을 명시적으로 분리한다. 같은 작업의 재시도·관련 대화·수정본은 같은 그룹에 둬 평가셋 누출을 막는다. 시간·프로젝트·모델 단위로도 일반화를 확인한다.
  • 승인 정책·검사 기준·권한은 최적화 대상에서 제외한다. 품질·정책 준수를 만족한 후보끼리 완료당 비용·지연·사용자 교정·불필요한 질문을 비교한다. 토큰 수만 줄이는 후보는 선택하지 않는다.
  • 평가셋 오염·자동 테스트 약화·형식 오류·비용 초과·품질 하락은 실패로 남긴다. 후보별 호출·reflection·전체 실행 시간·동시성·지출 상한을 둔다.
  • 활성 지침을 실시간으로 덮어쓰지 않는다. 후보 → shadow → 제한된 canary → 승격/rollback 순서를 사용한다. 사용자 기억·권한·공개 규칙 변경은 별도 승인한다. 표현 최적화는 사전에 동의한 자동 승격 범위 안에서만 허용한다.

기존 09번 문서는 사례 30건, 11번 문서는 50건을 내부 시작 조건으로 제안했다. 두 수치를 GEPA의 보편적 최소 요건으로 해석하지 않는다. 적용 버전·작업 유형별 표본 계획과 독립 평가 신뢰도를 새로 합의한다. DSPy 문서는 valset 생략 시 trainset을 사용한다고 설명하므로 분리를 명시해야 한다. [18]

개인화 수집과 공급자 학습을 분리한다

원문 장기 보관은 별도 opt-in으로 받는다. 사용자가 켜면 허용한 환경의 요청·위임·교정 기록을 자동 축적하되 민감정보 제거·TTL·열람·내보내기·삭제를 제공한다. 관리형 실행에 필요한 일시 처리, 개인화 저장, 모델 제공자의 보존/학습 조건을 각각 안내한다. 다른 고객의 학습이나 공개 CodeForge 규칙으로의 전환은 기본 금지한다.

삭제·권한 철회는 원문뿐 아니라 파생 기억·인덱스·평가 사례·그 사례로 만든 프롬프트 후보까지 추적한다. 영향받은 버전을 비활성화하거나 허용 자료만으로 재평가한다. 백업 삭제 지연과 이미 외부 모델에서 처리된 내용의 회수 한계도 명시한다. 조직 원문을 개인 모델로 최적화하는 자동 fallback은 허용하지 않는다.

이번 문서는 구조를 설계한 것이다. 실제 로컬 Herdr 로그 파일의 수집 상태·형식·성공 라벨은 확인하지 않았고 개인·회사 로그 원문을 읽거나 전송하지 않았다. 메모리나 활성 프롬프트를 실제로 자동 갱신한 상태도 아니다.

Portable intent / 모델별 최적화

사용자의 의도는 공통으로, 전달 방식은 모델별로

모든 모델에 같은 긴 프롬프트를 붙이기보다 승인된 의도·정책·기억을 공통 형식으로 보관한다. 실행할 모델과 호스트의 능력에 맞춰 필요한 내용을 선택하고 출력 형식을 바꾼다.

검증된 작업 유형만 지원

모델·버전·호스트·작업 유형별로 검증 기록을 남긴다. 모델이 바뀌면 이전 프롬프트를 무조건 재사용하지 않고 최소 회귀 평가를 다시 수행한다. 지원하지 않는 도구나 승인 기능은 명시적으로 거부하거나 사람에게 넘긴다.

목표는 “어떤 모델에서도 항상 최적”이라는 보장이 아니다. 지원하는 조합에서 사용자 의도를 보존하면서 품질을 유지하고 완료당 비용·교정 시간을 줄였는지 측정하는 것이다. 일반 프롬프트 최적화는 모델 가중치 파인튜닝과 별개이며 후자는 데이터 권리·비용·이식성 검토 후 선택한다.

GEPA의 evaluator 기반 후보 탐색과 다중 텍스트 구성요소 최적화를 참고하되, 모델 간 성능 전이는 이 서비스의 평가로 입증해야 한다. [17] [24] [25]

Context on demand / 최소 접근

맥락은 이어가되, 세션에는 필요한 정보만 전달한다

지식베이스 전체를 매번 프롬프트에 넣지 않는다. 세션의 환경·사용자·장비·작업 권한을 먼저 고정하고 그 안에서 관련된 근거만 선택한다. 개인 세션에 회사 자료를 넣은 뒤 출력만 막는 방식은 사용하지 않는다.

1 · AUTHORIZE읽을 수 있는 범위 결정

현재 realm·장비·작업·자료 등급으로 검색 가능 source를 제한한다. 로그인이 같아도 다른 조직 자료는 열리지 않는다.

2 · SELECT허용된 자료 안에서 정제

관련 문서·승인 기억·최신 작업 상태만 검색한다. 중복과 만료된 정보를 제외하고 출처를 붙인다.

3 · BUDGET이번 호출의 맥락 구성

정책·목표·핵심 근거·미해결 질문을 작은 Context Envelope에 담는다. 추가 근거는 필요할 때 같은 권한으로 조회한다.

개인 세션에서의 요청표시 가능성설계 조건
“업무용 환경에 진행 중인 일이 있어?”조직이 허용한 상태 요약이 있을 때만 “진행 중인 작업이 있음”.기본 비공유. 조직이 허용한 필드·수신자·장비·유효기간의 별도 projection만 조회.
“회사에서 어떤 프로젝트를 하고 있지?”프로젝트명·고객명·일정은 업무 존재 자체보다 민감할 수 있어 기본 차단.포괄적 “업무 요약” 동의로 원문 접근을 열지 않음.
“그 프로젝트 설계가 어떻게 돼?”개인 세션에서는 조회 불가. 승인된 업무 환경에서 확인하도록 안내.회사 코드·설계·회의록·벡터 인덱스는 검색 대상에 들어오지 않음.
“그럼 키워드나 조금만 더 알려줘.”마찬가지로 허용된 필드만 반환.반복 질의·도구 호출·에러·캐시·인용 링크로 상세 내용을 복원하지 못하도록 검사.
업무 존재도 민감정보일 수 있다. 외부 표시를 허용할 권한은 조직 정책에 따른다. 조직이 공유를 금지하면 “회사 업무가 있다”는 정보도 보내지 않는다. 프롬프트나 사용자의 개인 계정 설정이 이 정책을 완화할 수 없다.
승인된 상태 요약과 계정 탈취 대응

외부 표시용 상태는 별도 자료로 발행한다

조직 내부의 정책 집행기가 허용된 작업 상태에서 realm_alias · coarse_status · observed_at · expires_at 같은 필드만 추출한다. 실제 필드는 관리자 정책으로 더 줄일 수 있다. 작업 제목·경로·고객명·프롬프트·오류 내용·설계 요약은 기본 제외한다. 주기와 시각 정보도 업무 패턴을 드러내므로 최소화한다.

원문 접근 권한은 그대로 유지하고 별도 승인된 projection만 개인 화면에 전달한다. 개인 서비스가 회사 원문을 조회해 요약하는 구조는 금지한다. 자연어 요약이 필요해도 회사 안에서 생성한 뒤 허용 필드 검증을 거쳐야 한다. 원문에서 만든 일반 요약·임베딩은 이런 공개 승인과 동일하지 않다.

projection에는 출처·발행자·정책 버전·수신 범위·만료를 기록한다. 만료·권한 철회 시 새 조회와 캐시 사용을 중단한다. 이미 사람이 본 화면이나 캡처까지 회수할 수 있다고 약속하지 않는다. 개인 화면의 상태 요약에는 회사 자료로 들어가는 권한이나 실행 토큰을 포함하지 않는다.

모든 세션이 같은 기억을 갖지 않게 한다

전체 맥락은 해당 환경의 승인된 저장소와 작업 원장에 남긴다. 각 세션에는 목표·현재 상태·적용 정책·관련 기억·필요 근거·다음 질문만 전달한다. 세션 전환 시 전체 채팅 대신 출처 포인터와 결정·미해결 항목을 인계하고 새 세션이 현재 권한으로 다시 조회한다.

모델의 입력 한도에서 응답과 도구 결과를 위한 여유를 뺀 뒤 맥락 예산을 배정한다. 길이를 줄일 때 낮은 관련성의 사례와 중복을 먼저 제거한다. 필수 정책·승인 조건·실패 근거를 압축 과정에서 누락하지 않는다. 모호하면 더 많은 자료를 무조건 가져오기보다 질문하거나 허용된 근거를 단계적으로 조회한다.

공용 캐시에 개인·조직의 비공개 맥락을 섞지 않는다. 캐시 키에는 realm·ACL·source revision·policy version을 포함한다. 조회 전 필터링과 사용 직전 권한 확인을 모두 적용한다. 컨텍스트 토큰 감소, 근거 검색 성공, 누락 때문에 생긴 재작업을 함께 측정한다.

편의 기능이 침해 통로가 되지 않도록

  • 개인 계정 탈취가 조직 세션으로 이어지지 않도록 조직 인증·기기 조건·검색 권한·키를 분리한다. 단순 UI 전환으로 인증 영역을 합치지 않는다.
  • 기기별 짧은 세션, 즉시 철회, 민감 열람·배포의 추가 인증, 이상 다운로드·대량 실행 제한을 둔다. 2FA만으로 조직 자료의 외부 접근을 허용하지 않는다.
  • 연동 계정은 source별·action별 최소 권한으로 연결한다. 문서를 읽는 도구와 외부로 전송·배포하는 도구의 권한을 분리하고 문서 속 지시가 권한을 추가하지 못하게 한다.
  • 코딩 sandbox에서 관리 서버·키 저장소·다른 tenant로 접근할 수 없도록 분리한다. 제어 서버 침해·공급망 변조·조직 관리자 계정 탈취도 별도 위협으로 검사한다.
  • 실행을 멈추는 기능, 기기 철회, 고객별 사고 범위 추적과 통지를 준비한다. 연결 단절 시 확인할 수 없는 신규 고위험 작업은 보류한다.

최소 맥락은 토큰 비용과 노출 범위를 줄일 수 있지만 완전한 보안을 보장하지는 않는다. 권한 있는 단말 침해·스크린샷·관리자 오용·구현 결함은 남는다. 조직별 위협 모델과 실제 침투·격리 검사가 필요하다. [1]

숨은 외부 연결 제거

  • 외부 폰트·CDN·분석 SDK·오류 보고·업데이트 확인을 끈다.
  • 모델 자동 다운로드·원격 tokenizer·패키지 설치·테스트 중 다운로드를 차단한다.
  • 내부 Git·패키지·컨테이너 미러와 내부 검색 문서를 사용한다.
  • 모델 장애 시 외부 API로 자동 전환하지 않는다. 미지원 상태로 보고한다.
  • 외부 OCSP·CRL, 시간 서버, 라이선스 확인 의존성도 점검한다.

Ollama에는 cloud 기능 비활성화 설정이 있고 Transformers에는 사전 다운로드·offline 모드가 있다. 설정만으로 전체 시스템의 무외부통신이 보장되지는 않는다. [2] [5]

폐쇄망 지원 선언 전 통과할 검사

  1. 빈 장비에서 인터넷 없이 설치·로그인·모델 로드·메모리 검색·작업·검증·재시작을 수행한다.
  2. DNS·TCP·UDP 등 외부 통신 시도를 계측한다. 방화벽 차단뿐 아니라 앱의 실패·재시도와 로그도 확인한다.
  3. 악성 또는 변조된 반입 번들을 거부하고 서명 유효하지만 취약한 구버전의 재설치 정책을 검사한다.
