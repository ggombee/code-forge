## 당시 최종 판정 — 현재는 폐기됨

### 2026-10-15 재판정

초기 판정은 사용자가 원하는 제품을 “읽기 전용 상태 화면”과 “PR 검증기 시장성”으로 지나치게 좁혔다. 세션 순회 제거, 비동기 질문, 교차 기기 승인, 24시간 준비, 지식 연속성이 북극성의 핵심 효용이다. 엔티티 수가 많다는 사실만으로 과잉설계를 판정할 수도 없다. Attempt, Decision, Approval, Evidence, Knowledge는 수명주기와 권한이 달라 구분할 이유가 있다.

따라서 아래 `OVERENGINEERED`와 기능 동결 판정은 **당시 검토 결과**로만 읽는다. run별 파일과 읽기 전용 status는 빠른 UX 실험에 사용할 수 있지만, durable queue와 승인·복구를 포함한 제품의 저장 구조가 될 수 없다. 첫 실제 제품은 SQLite WAL과 비동기 Decision/Approval 계약을 포함한 완전한 수직 단면으로 만든다.

아래 표와 결론은 2026-10-14 당시 판정이다. 현재 구현 기준이 아니며 2026-10-15 재판정으로 veto 효력을 잃었다.

| 대상 | 판정 | 신뢰도 | 이유 |
|---|---:|---:|---|
| 09번 전체 Control Plane | **OVERENGINEERED** | 75/100 | 7개 엔티티, KB, 추가 runner, 메시징, GEPA, 팀 서버를 실제 임계값보다 먼저 약속한다. |
| 2주 Thin Coordinator | **PROPORTIONATE** | 70/100 | 이미 존재하는 다중 세션의 부모 관계, 업무 참조, 검증 여부를 최소 권위 필드만으로 보여 준다. |

당시에는 CodeForge를 바로 플랫폼으로 재구축하지 않고 **run별 단일 writer 파일, 읽기 전용 관찰 adapter, 권위 필드 4개, 검증 receipt, 한 화면 status**만 만든다는 가설을 먼저 검증한다고 결론냈다. 검증 전에는 ForgeGlow 개편, KB, 모델 라우터, Hermes, OMP/Qwen, GEPA, Postgres를 구현 범위에 넣지 않는 실험안이었다.

## 검증에 사용한 근거

### 확인된 사실

1. 사용자는 업무별 메인 Claude/Codex 세션과 그 아래 작업 세션을 운영하며, 창을 순회해 goal·handoff·완료·병목·승인을 확인하는 비용을 실제로 겪고 있다.
2. 2026-10-14 Herdr 조회 시 여러 워크스페이스에 Claude/Codex 세션이 동시에 존재했고, 현재 작업도 같은 Herdr 안에서 별도 세션으로 진행 중이었다. “복수 세션”이 이미 현재 상태임을 확인했다.
3. CodeForge 개선계획에는 고정 임시파일을 공유하던 `emit-event`가 임시 저장소의 동시 12회 쓰기에서 빈 JSON·오류를 만들었다는 재현 기록이 있다. 같은 문서는 현재 기록·복구 작업이 미착수라고 구분한다.
4. CodeForge의 cross-agent event 계약은 `Phase 0 SHADOW`이고, append-only event ledger는 실제 두 번째 소비자가 생길 때까지 보류하도록 적혀 있다. 설계 자산은 있지만 작동하는 Control Plane은 아니다.
5. OpenHands Agent Canvas는 이미 로컬·원격 backend와 ACP 기반 외부 에이전트 화면을 제공하고, Herdr는 기존 터미널 에이전트의 관찰·자동화를 제공한다. Codex도 app-server 프로토콜을 공개한다. 따라서 새 범용 실행 UI를 만드는 것은 중복 가능성이 높다.

### 설계 추론

1. `verify + guard + status + receipts.jsonl`도 실행 상태와 검증 결과의 정본을 가지는 순간 작은 Control Plane이다. 이름을 스크립트로 바꿔도 권위와 복구 책임은 사라지지 않는다.
2. 복잡성을 만드는 것은 테이블 수 자체보다 **다른 곳에서 복구할 수 없는 권위 필드의 수**다. 외부 시스템에서 재관찰 가능한 값은 projection으로 두고, Coordinator가 처음 기록해야 하는 값만 최소화해야 한다.
3. 이슈·PR·레포 계획이 작업 내용의 정본이므로 Coordinator에는 참조와 revision을 기록한다. 부모/자식 세션 관계와 검증 여부는 최소 원장에서 관리한다.
4. 공유 JSONL 한 파일보다 run별 단일 writer 파일이 현재 범위에 작다. SQLite WAL은 읽기/쓰기 동시성을 높이지만 한 번에 writer는 하나이며 로컬 host 전제도 있다. 다중 writer와 원자적 handoff 필요가 실제로 생겼을 때 도입하는 편이 낫다.

### 아직 가정인 것

- Claude/Codex 앱이나 원격 세션에서 `waiting_input`과 `waiting_approval`을 안정적으로 관찰할 수 있는지
- 사용자가 `goal_line`, `work_ref`, `handoff_ref`를 세션당 한 번 입력할 만큼 이득을 느끼는지
- 한 화면이 창 순회와 반복 설명을 실제로 절반가량 줄이는지
- run별 파일이 2주 사용량에서 충분한지

이 가정들을 확인하는 것이 MVP의 목적이다. 제품 확장성을 증명하는 실험이 아니다.

## 당시 2주 MVP 기능 — 역사적 실험안

### 1. run별 단일 writer 저장

```text
runs/<run_id>/state.json
runs/<run_id>/receipts/<head_sha>-<timestamp>.json
```

- 한 파일은 한 writer만 수정한다.
- 고유 임시파일에 쓴 뒤 `fsync`하고 같은 파일시스템에서 atomic replace한다.
- 공유 인덱스와 데몬은 두지 않는다. `status`가 매번 projection을 계산한다.
- 과거 문제와 같은 12개 동시 writer 조건을 반복해 손상·빈 파일 0건이어야 한다.

### 2. 읽기 전용 관찰 adapter

- Herdr 세션을 우선 관찰한다.
- Claude/Codex는 공식 hook/API로 확인 가능한 값만 읽는다.
- 읽지 못한 세션은 추정하지 않고 `unobserved`, 오래된 값은 `stale`, 계정을 확인하지 못하면 `unknown`으로 표시한다.
- 기존 guard는 유지하지만 새 통합 guard는 만들지 않는다. 보안은 기존 guard와 각 실행기의 권한 설정이 강제한다.

### 3. 권위 필드 4개

| 필드 | 이유 |
|---|---|
| `parent_run_id` | 메인 세션과 작업 세션의 계층은 host가 보존하지 않을 수 있다. |
| `work_ref` | 이슈·PR·계획 문서를 연결하되 본문은 복제하지 않는다. |
| `goal_line` | 창을 열지 않고 목적을 확인하는 120자 이하 한 줄이다. |
| `handoff_ref` | 기존 체크포인트 경로만 가리킨다. 내용은 저장하지 않는다. |

재관찰 가능한 `host_session_ref`, `repo`, `branch`, `head_sha`, `state`, `last_seen_at`, `account_alias/account_source`는 projection 값이다.

### 4. 불변 verify receipt

```json
{
  "run_id": "...",
  "head_sha": "...",
  "command": "...",
  "exit": 0,
  "log_ref": "...",
  "verified_at": "..."
}
```

- `verified`는 receipt에서만 파생한다.
- 현재 HEAD와 receipt SHA가 다르면 검증 표시는 자동 해제한다.
- 에이전트의 완료 주장은 `claims_done`일 뿐이다.

### 5. 한 화면 `cf status`

```text
$ cf status                      관찰: herdr✓ claude-hook✓ codex-hook? remote✗
나를 기다림 2 · 완료주장/미검증 1 · 진행 2 · 경고 2

M1 목록 페이지네이션        work:TASK-001  handoff: plan/checkpoint-a.md
 ├ W1 ⏸ 승인대기 12m         PR 리뷰 필요        team·guard     → pane 3
 ├ W2 ◐ 완료주장             receipt 없음        team·guard     → pane 4
 └ W3 ▶ 진행 3m              테스트 보강         team·observed
M2 콘솔 개선                 work:TASK-002
 └ W4 ✗ 검증실패             lint exit=1          realm-b·observed

경고
 ! W3 last_seen 41m 전 — stale
 ! 부모 없는 세션 1개 · account unknown
```

첫 화면은 창을 열지 않고 다음 세 질문에 답한다.

1. 지금 나를 기다리는 작업은 무엇인가?
2. 완료를 주장했지만 검증되지 않은 작업은 무엇인가?
3. 각 작업의 goal과 handoff는 어디에 있는가?

## 당시 구현 보류와 재검토 조건

| 보류 항목 | 다시 여는 조건 |
|---|---|
| Work 엔티티와 업무 본문·대화·diff 저장 | `work_ref`로 맥락을 되찾지 못하는 사례가 반복될 때. 그래도 먼저 read-through cache를 검토한다. |
| Approval 엔티티와 화면 내 승인 | 성공한 관찰 MVP 뒤 남은 창 이동의 주원인이 승인이고 감사 기록까지 필요할 때 |
| 세션 시작·중지·메시지 주입 | 남은 창 이동의 다수가 지시 전달일 때 |
| SQLite WAL | 다중 writer, 원자적 handoff, 중복 제거 실패, run 파일 수천 개 또는 status 1초 초과, 2주 내 고아/부분 상태 2회 중 하나가 발생할 때 |
| 전체 cross-agent event stream | state와 receipt만으로 답할 수 없는 사후 분석 질문이 반복될 때 |
| LLM goal/handoff 자동 요약 | 수동 `goal_line` 기입률이 절반 미만이고 원인이 입력 부담일 때 |
| KB·KnowledgeCandidate | 문서가 있는데도 같은 실수가 3회 이상 반복될 때 |
| GEPA | 비교 가능한 라벨 사례 약 50건과 미사용 holdout이 생길 때 |
| OMP·Qwen·로컬 runner | 해당 runner를 실제 업무에 주 1회 이상 사용할 때 |
| Hermes·Slack 알림 | 사용자가 다른 장소에 있는 동안 승인 대기로 실제 지연된 사례가 반복될 때 |
| Postgres·RBAC·SSO | 본인 외 2명 이상이 같은 관제를 실제로 사용할 때 |
| ForgeGlow 연동 | CLI MVP가 성공한 뒤 같은 projection을 읽는 UI로만 추가 |
| Paperthin port | 특정 반복 실패와 skill 하나가 1:1로 대응될 때 |

## 측정과 판정

첫 2~3일에는 구현 전 기준선을 잡는다.

- 상태 확인을 위해 다른 창을 연 횟수
- goal을 다시 설명한 횟수
- handoff 문서를 다시 찾은 횟수
- 검증 없이 완료로 받아들일 뻔한 횟수

자기 기록이라 정밀한 백분율보다 큰 방향을 본다.

### 성공 — 모두 필요

- 손상·빈 run/receipt 파일 0건
- receipt 없이 `verified`로 표시된 경우 0건
- 실제 진행 세션 대부분이 보이며 `unobserved`는 소수
- 2주차의 창 확인과 goal/handoff 반복이 기준선의 대략 절반 이하
- adapter 유지보수가 주당 반나절 미만

### 당시 실험의 실패 기준

- 상태 파일 손상 1건: 원인 해결 전 사용 중단
- `unobserved`가 과반: Coordinator 확장 중단, host 관찰 인터페이스부터 확보
- 창 순회와 반복 설명이 줄지 않음: 원장·UI 확대 금지
- 권위 필드 기입률이 절반 미만: 입력 UX를 줄이거나 coordinator 폐기
- adapter 수리에 주당 반나절 이상: 지원 host를 Herdr 하나로 축소

### 당시 확장 기준

위 보류 표의 증거가 관찰된 기능만 하나씩 연다. 동시에 두 기능을 확장하지 않는다. 기능을 추가할 때는 어떤 관찰이 조건을 충족했는지 남긴다.

## 파일 방식에서 SQLite로 넘어가는 이유

run별 파일을 선택한 이유는 데이터 규모보다 소유권이 단순하기 때문이다. 각 state에 writer가 하나고 status는 읽기만 하므로 DB transaction이 아직 필요 없다.

다음 상황에서는 SQLite가 더 단순해진다.

- 관찰 adapter와 사용자가 같은 run을 갱신한다.
- 두 adapter가 같은 세션을 중복 발견해 idempotent UPSERT가 필요하다.
- 이전 run 종료와 다음 run 시작을 한 transaction으로 묶어야 한다.
- 파일 순회가 실제 지연이나 복구 문제를 만든다.

SQLite 공식 문서상 WAL은 reader와 writer가 동시에 진행할 수 있지만 writer는 한 번에 하나이며 같은 host의 공유 메모리를 전제로 한다. 이 실험에서는 **로컬 transaction과 복구가 필요해지는 시점의 다음 저장 방식**으로 평가했다.

## 최종 위험과 완화

| 위험 | 완화 |
|---|---|
| 앱·원격 세션을 관찰하지 못함 | 초기에 capability probe. 모르는 값은 `unobserved`; 과반이면 방향 전환 |
| stale·검증 상태가 거짓말함 | TTL, receipt SHA와 HEAD 비교, 12 writer 회귀 검사 |
| goal 입력 부담으로 데이터가 빔 | 세션 시작 시 한 번, 120자 제한, 미입력 허용 및 기입률 측정 |
| 기존 큰 설계가 범위를 끌어당김 | 당시에는 09번을 장기 참고로 강등했으나, 이 완화책은 2026-10-15 재판정으로 폐기됐다. |
| 관제 화면을 보안 장치로 착각 | 기존 guard 유지, `account_source` 노출, 본문·대화·인증정보·개인정보 저장 금지 |

## 이 기록을 앞으로 사용하는 방법

**2주 실험은 창 순회, 반복 설명, 관찰 정확도와 adapter 유지비를 측정하는 보조 실험으로 사용한다.** 실패하면 해당 관찰 방식과 UX를 수정한다. Control Plane 전체, 비동기 승인, 지식 연속성, 24시간 운영의 추진 여부를 이 실험 하나에 종속시키지 않는다. 제품 저장은 첫날부터 SQLite WAL과 transaction outbox를 사용하고, run별 JSON은 사람이 읽는 projection이나 내보내기 형식으로만 쓴다.
