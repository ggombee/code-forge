## 요약 판정

**CodeForge는 AI가 빠르게 만든 소프트웨어를 저장소의 실제 기준으로 측정하고, 근본 원인을 찾아 최소 변경으로 개선하며, 같은 품질을 더 적은 토큰·비용으로 재현하는 로컬 우선 검증·최적화 제품으로 발전시킨다. 여러 실행기를 조율하고 24시간 일하게 하는 기능은 이 개선 루프를 지속하는 운영 기반이다.**

제품 구조는 **D안: 직접 소유하는 신뢰 커널 + 기존 실행 생태계 조합**으로 결정한다.

| 순위 | 안 | 판정 |
|---:|---|---|
| 1 | D — 신뢰 커널은 소유하고 실행은 조합 | 채택. 검증·정책·예산·realm·영수증·승인 계약을 소유하고 실행·전송·cron·메신저는 연동한다. |
| 2 | B — 모든 것을 소유하는 중립 core | 방향은 맞지만 모델 gateway, scheduler, runtime까지 만들 가능성이 커서 D보다 위험하다. |
| 3 | A — 얇은 관제 coordinator | 빠른 실증에는 쓰되 Codex app, Agent HQ, OpenHands와 겹쳐 장기 차별점이 약하다. |
| 4 | C — Hermes/OpenHands 등을 fork한 플랫폼 | upstream 종속, 보안 책임, adapter 유지비를 함께 떠안으므로 기반으로 삼지 않는다. |

허용할 오버엔지니어링은 **나중에 바꾸면 사고·데이터 유출·호환성 파괴로 이어지는 계약**과 사용자가 처음부터 얻어야 할 핵심 경험에 한정한다. 첫 구현은 작지만 끝까지 동작하는 수직 단면으로 만든다.

- 처음부터 견고하게: 판정 의미, 상태 전이, stable ID, idempotency, schema version, receipt, 예산 원장, realm, provenance, adapter capability, migration, `doctor`, 비동기 질문·승인 계약.
- 첫 사용 흐름에 포함: durable queue, structured runtime 한 종류, worktree와 sandbox, 독립 검증, 반응형 Attention Inbox, 최소 지식 출처 기록, 별도 apply executor.
- 실증 뒤에 확장: 팀 Hub, native 모바일 앱, 지식 그래프, 자동 프롬프트 최적화, 다수 adapter와 고급 routing.
- 계속 만들지 않음: 자체 LLM gateway, 자체 PTY·IDE, 자체 cron·메신저, OpenHands/Hermes hard fork, 범용 workflow DSL, 자체 분산 scheduler, 처음부터 모든 protocol 구현.

## 먼저 읽을 이야기

생성형 코딩 도구 덕분에 기능과 서비스의 첫 버전은 빠르게 만들 수 있다. 이후 더 희소한 일은 생성된 코드를 실제 사용자와 장기 운영에 견딜 수 있게 만드는 것이다. 중복·취약한 경계·느린 hot path·과도한 dependency·불안정한 테스트·비싼 context를 찾아도, 현재는 사람이 여러 Claude·Codex 세션과 CI를 직접 순회하며 다음을 처리한다.

1. 어떤 품질·성능·비용 문제가 실제 병목인가
2. 어느 변경이 증상을 가리는 대신 근본 원인을 줄이는가
3. 에이전트가 말한 개선을 독립 측정으로 믿어도 되는가
4. 같은 품질을 더 적은 context·token·재시도로 재현할 수 있는가
5. 무엇을 실제 저장소나 운영 환경에 반영해도 되는가

CodeForge는 이 다섯 가지를 한 흐름으로 묶는다.

```text
자연어로 작업을 맡긴다
  → 저장소 규칙, baseline과 개선 조건을 고정한다
  → 기존 AI 실행기가 병목 가설별 최소 후보를 만든다
  → CodeForge가 기능·성능·비용을 독립적으로 다시 측정한다
  → 질문·검토 후보·승인할 동작만 한곳에 모은다
```

질문이 생기면 그 답에 의존하는 작업만 멈춘다. 다른 작업과 메인 coordinator는 계속 움직인다. 실행이 끝나면 diff, 검사 결과, 위험, 미확인 항목, 되돌리는 방법을 하나의 `CandidatePackage`로 보여 준다. 사람은 이 묶음을 검토하고 정확한 변경과 동작만 승인한다.

사용자가 처음 만나는 제품은 작은 흐름으로 시작하되 끝까지 완결된다. 첫 버전은 **작업 접수, durable 원장, AI 실행기 한 종류, worktree와 sandbox, 독립 검증, 비동기 질문, 반응형 검토·승인함, 별도 반영 실행기와 readback**을 하나의 흐름으로 제공한다. 아래의 장기 객체와 protocol은 이후 기능이 붙어도 이 핵심 의미가 바뀌지 않도록 미리 정한 계약이다.

### 도구는 선택형 연결점이다

| 도구 | 채택 이유 | 제품에서의 위치 | 첫 버전 |
|---|---|---|---|
| CodeForge | 여러 실행기 사이에서 작업 기준·권한·검증 기록을 잃지 않기 위해 | 직접 소유하는 코어 | 필수 |
| Claude·Codex | 실제 분석과 코딩을 이미 잘 수행하기 때문에 | 교체 가능한 실행 adapter | 하나만 연결 |
| Herdr | 사용자가 이미 여러 터미널 세션을 운영하므로 새 UI 없이 현재 세션을 관찰·제어하기 위해 | 선택형 터미널 surface | 없어도 동작 |
| Hermes | 예약 실행, 원격 backend, 메신저 연결을 다시 만들지 않기 위해 | 선택형 wake·전송 adapter | `launchd`·`cron`으로 대체 |
| Obsidian | 개인 지식을 사람이 읽고 고치는 로컬 Markdown 화면이 필요하기 때문에 | 선택형 지식 편집기 | Markdown 폴더로 시작 |
| 문서·이슈 시스템 | 원래 자료 위치와 권한을 유지하기 위해 | realm별 source adapter | 필요한 realm만 연결 |
| ForgeGlow | 상태와 비용을 기존 터미널에서 가볍게 보기 위해 | 읽기 전용 HUD | 코어 검증 뒤 연결 |

Obsidian vault는 제품 DB로 쓰지 않는다. 제품 계약은 Markdown과 출처 metadata에 두고, Obsidian은 사람이 편집할 때 편한 화면으로만 쓴다. 그래프 탐색이나 vector DB는 검색 품질이 실제로 좋아진다는 증거가 생긴 뒤에 추가한다.

Hermes에는 queue와 권한을 저장하지 않는다. CodeForge daemon을 정해진 시간에 깨우고, 허용된 원격 장비에서 실행하고, 질문·결과를 메신저로 전달하는 통로로만 쓴다. 단일 Mac이나 데스크톱에서는 운영체제 scheduler로 충분하므로 Hermes 없이 먼저 출시할 수 있다.

Herdr와 ForgeGlow도 같은 원칙을 따른다. 둘은 사용자가 상태를 보는 surface이며 완료를 판정하거나 실행 권한을 만들지 않는다. 각 도구가 없어도 CodeForge의 검증과 원장은 그대로 동작해야 한다.

### 복잡성 판정

장기 설계를 한 번에 구현하면 과잉설계다. 현재 권고안은 구현 순서로 이를 제한한다.

| 첫 수직 단면 | 이후 확장 | 만들지 않을 것 |
|---|---|---|
| durable Work, 단일 structured runtime, worktree·sandbox, 독립 검증, 비동기 질문·승인, 출처 기록, apply/readback | 여러 adapter, Hermes 알림, Markdown·문서 검색, 저비용 모델 routing, 팀 Hub | 자체 터미널, 자체 메신저, 자체 cron, 범용 LLM gateway, 자체 agent loop, 범용 workflow DSL |

복잡한 schema와 상태 이름은 사용자 화면에 그대로 노출하지 않는다. 사용자는 `진행 중`, `질문 필요`, `검토 가능`, `승인 필요`, `반영 완료`, `실패`만 보면 된다. 세부 상태는 복구와 감사가 필요한 내부 구현에 남긴다.

## 확인된 사실, 설계 판단, 남은 가정

### 확인된 사실

1. Codex app, GitHub Agent HQ, OpenHands Agent Canvas는 이미 병렬 에이전트 실행, worktree, review, 원격·모바일 또는 local/cloud UI를 제공한다. 일반적인 “멀티에이전트 관제 화면”만으로는 차별화하기 어렵다.
2. Hermes는 cron, 여러 메시징 채널, local·Docker·SSH·cloud backend, provider fallback과 custom OpenAI endpoint를 제공한다. LiteLLM은 provider 통합, retry, fallback, 비용·rate·latency routing을 제공한다. 전송과 cron을 다시 만들 이유가 약하다.
3. ACP는 client와 agent 사이의 session·permission·capability, MCP는 tool·data 연결, A2A는 독립 agent 사이의 상호운용을 맡는다. 같은 문제를 다루는 단일 protocol이 아니다.
4. in-toto, SLSA, CDEvents, OpenTelemetry는 provenance·build·pipeline·trace export에 쓸 수 있지만, 저장소별 acceptance와 인간 승인, agent의 검증 약화까지 대신 정의하지 않는다.
5. 현재 CodeForge v4.11.0은 MIT인 Claude Code plugin이다. 로컬 계획에는 macOS Bash 3.2, 실패를 pass로 오판한 경로, concurrent event 기록 손상과 같은 출시 차단 결함이 기록되어 있다. 기존 event 문서는 아직 `Phase 0 SHADOW`다.
6. CodeForge의 기존 continuity 제안에는 versioned core, host adapter, project manifest와 lock, SQLite WAL, stable repo·checkout·worktree identity, protocol handshake, `doctor`, offline 동작, credential·retention 분리 방식이 이미 설계되어 있다.
7. ForgeGlow v0.9.0은 MIT인 session-local HUD다. core나 팀 원장의 역할을 하지 않는다.
8. 12GB급 소비자 GPU는 일부 양자화 모델의 로컬 실행 후보가 될 수 있다. Qwen 계열은 Apache-2.0 open weights와 local runtime을 제공하지만 실제 모델별 context·tool-use·속도는 별도 평가가 필요하다.
9. Claude Managed Agents는 persistent session/event, hosted·self-hosted sandbox, permission pause, webhook과 multi-agent 실행을 제공한다. OpenAI Agents API는 managed Codex harness, durable session, compaction, recovery, sandbox와 multi-agent orchestration을 제공한다. 두 제품 모두 beta 또는 빠르게 변하는 surface이므로 versioned adapter와 realm별 데이터 정책 확인이 필요하다.
10. Codex App Server는 thread lifecycle, 양방향 event와 approval request를 제공한다. Herdr의 `working/blocked/done` 관찰은 유용하지만 `done/idle`만으로 작업 검증을 증명하지 않으며 개별 turn 완료와 직접 대응하지 않는다.

### 설계 판단

- 최초 상품은 **AI가 만든 저장소를 실제 기준으로 검사하고, 근거가 있는 개선 후보와 정확한 반영 승인을 돌려주는 개인용 소프트웨어 견고화 시스템**이다. 여러 실행기 조율, 검증 CLI·GitHub Action과 Attention Inbox가 이 경험을 지탱한다.
- 사용자가 원하는 “자는 동안에도 준비하고 나중에 확인”은 두 번째 상품 면이다. 작업 위험도가 아니라 준비와 반영의 권한을 나누며, 고위험 작업도 격리된 후보·dry-run·rollback 작성까지 진행할 수 있다.
- CodeForge와 별도로 host-neutral core 저장소를 만든다. 기존 CodeForge는 Claude·Codex의 native pack과 공통 policy/skill 원본을 유지하며 core 없이도 사용할 수 있다.
- 새 저장소는 core·execution·공식 adapter·CLI·웹 검토함·conformance를 함께 버전 관리하는 모노레포로 시작한다. 모듈은 나누되 하나의 제품 배포 단위로 개발한다.
- ForgeGlow는 별도 client로 유지하고 공개 상태 API를 읽는다.
- 지식은 하나처럼 보이되 사용자·workspace·tenant별 realm을 물리적·논리적으로 분리한다.

### 아직 검증할 가정

- 작은 팀이 검증 약화나 false pass를 실제 비용으로 느낀다.
- 저가·로컬 모델이 만든 후보 중 사람이 채택할 비율이 충분하다.
- 서로 다른 provider를 쓰는 사용자가 portability와 receipt에 비용을 지불한다.
- 로컬 데스크톱이 무인 runner로 90% 이상 완주한다.
- provider가 공식 사용량·한도 정보를 충분히 제공해 자동 예산을 안전하게 운영할 수 있다.

## 제품 정의와 시장 진입 순서

### 한 문장 제품 정의

**AI가 만든 소프트웨어의 기능·구조·성능을 독립적으로 검증하고 최소 변경으로 개선하며, 품질을 유지한 채 에이전트의 token·비용·재작업까지 줄이는 오픈소스 신뢰·최적화 계층.**

### 서로 연결된 두 최적화 루프

CodeForge는 코드와 에이전트 사용량을 같은 숫자로 섞지 않는다. 두 루프는 공통 `WorkSpec`, `VerificationRecipe`, `Evidence`, `Receipt`를 사용하지만 각각 독립된 gate를 가진다.

1. **Software loop**: correctness, architecture boundary, dependency, security, bundle·binary, latency, allocation, build·test time 같은 저장소 지표를 측정한다. profile evidence에서 병목을 정하고, 가설 하나당 최소 candidate를 만들어 기능 비퇴행과 개선 재현을 확인한다.
2. **Agent loop**: 주입 context, model·tool 선택, prompt·skill, retry와 handoff를 비교한다. token 총량보다 `verified completion`당 비용, 사람 수정 시간, 재작업, 정책 위반과 latency를 함께 본다.

토큰 절감은 독립 성공 조건이 아니다. 기능·안전·유지보수 gate를 통과한 후보 사이에서 더 적은 비용을 쓴 경로만 개선으로 채택한다. 짧은 prompt가 실패와 재시도를 늘리면 최적화가 아니다.

### 초기 beachhead

개인 개발자가 여러 실제 작업을 맡기면 CodeForge가 다음 흐름을 끝까지 이어 준다.

1. base revision에 고정된 acceptance spec과 repository policy snapshot
2. structured runtime 한 종류의 격리 실행과 durable progress
3. 다른 작업을 멈추지 않는 비동기 질문
4. `pass | fail | measured | error | not_run | unavailable | blocked | n_a`를 보존하는 독립 검증과 weakening 탐지
5. diff·검사·spec·policy·base·환경을 묶은 review package와 정확한 action approval
6. 별도 apply executor의 target 재확인, 실행, readback과 application receipt
7. 고정 baseline에서 기능 비퇴행과 코드·에이전트 비용 개선을 분리해 보여 주는 optimization report

검증 CLI와 GitHub Action은 runtime 없이도 쓸 수 있게 병행 제공한다. 외부 저장소에서 weakening을 많이 찾지 못해도 조율 제품 전체를 폐기하지 않는다. 그 결과는 verifier 포장과 탐지 규칙을 조정하는 근거다.

### 첫 확장

단일 사용자가 넣은 모든 허용 작업 유형을 local daemon이 24시간 처리한다. 코드·문서는 검증된 변경 후보와 선택형 draft PR, DB·인프라·외부 동작은 dry-run과 실행 계획까지 준비한다. 실제 반영 전에는 다음 순서로 한 화면에 보여 준다.

1. 권한·정책 승인 필요
2. 사용자 질문 없이는 진행 불가
3. 검증 통과 후보
4. 실패·예산 초과·충돌

### 장기 category

장기적으로는 **Verified Software Optimization / Agent Efficiency Control Plane**이다. 에이전트를 직접 만드는 제품보다, 여러 에이전트가 만든 소프트웨어를 지속적으로 측정·개선하고 더 적은 비용으로 같은 품질을 재현하는 계층을 소유한다.

Managed runtime의 session·checkpoint·recovery는 Attempt 내부 실행 상태다. 재연결 뒤 CodeForge는 spec·policy·artifact·effect를 다시 대조하며 provider의 done/approval만으로 Work outcome이나 외부 반영 권한을 만들지 않는다.

## 처음부터 고정할 최소 계약

### 핵심 객체

| 객체 | 최소 의미 |
|---|---|
| `WorkSpec` | goal, scope, base ref, acceptance, risk, realm, 허용 side effect |
| `PolicySnapshot` | 해석된 repo·org rule과 digest, 적용 순서, waiver |
| `RepositoryProfile` | 저장소가 제공하는 명령·시나리오·metric·readback 참조와 적용 범위 |
| `VerificationRecipe` | 현재 Work에서 실행할 check, 기준 SHA, fixture·환경 digest, gate·재시도 정책 |
| `Attempt` | runner, model, sandbox/worktree, budget reservation, deadline |
| `CheckResult` | check별 `pass/fail/measured/error/not_run/unavailable/blocked/n_a`, command, exit, evidence ref와 reason |
| `Evidence` | 원시 로그·diff·metric·readback의 위치, digest, producer와 수집 환경 |
| `Receipt` | immutable verdict, spec/base/policy digest, diff·artifact·cost·provenance |
| `CandidatePackage` | 변경 artifact, AC 대응표, 검사·미확인, 위험 지점, PR·실행 preview, rollback |
| `ApprovalGrant` | 승인 action·target, artifact digest, base SHA, policy digest, realm authority, account profile, 승인자, 만료 시각, idempotency key |
| `ApplicationReceipt` | 실제 반영 동작, 대상, 결과, 반영 뒤 검증과 rollback 상태 |
| `DecisionRequest` | 질문·선택지·권장안, 차단 범위, spec version, 만료 시각, 허용 응답자 |
| `DecisionReceipt` | 선택·보충 답변, 응답자 출처, 대상 request/version, 시각, 무결성 참조 |
| `ActionRequest` | 승인, 예산 증액, 권한 요청, 외부 side effect와 만료 시각 |

내부 event는 `event_id`, `schema_version`, `work_id`, `attempt_id`, `causation_id`, `idempotency_key`, `occurred_at`, `producer`를 갖는 append-only envelope로 만든다. 외부 도구는 DB를 직접 읽지 않고 versioned JSON/API를 사용한다.

### 판정 원칙

- acceptance spec은 작업 실행자가 바꿀 수 없는 base에 고정한다.
- 검사 실행 실패·timeout·파싱 실패는 `error`, 미실행은 원인에 따라 `not_run`, `unavailable`, `blocked`, 비적용은 이유가 있는 `n_a`로 기록한다. legacy `skipped`는 원인 없이 자동 통과로 변환하지 않는다.
- 모델의 “완료했다”는 문장은 evidence가 아니다.
- spec 변경과 waiver는 별도 권한과 audit를 요구한다.
- receipt는 우선 in-toto predicate로 내보내고, build provenance는 SLSA, pipeline event는 CDEvents, trace는 OpenTelemetry로 export한다. 내부 의미를 이 표준에 억지로 맞추지 않는다.

### 메인 실행을 막지 않는 의사결정 사이드카

질문이 생길 때마다 메인 coordinator를 대화 대기 상태로 만들면 밤샘 실행과 여러 Work의 병렬성이 사라진다. 반대로 답이 필요한 경로까지 추측으로 계속 진행하면 재작업과 위험한 side effect가 생긴다. 따라서 **coordinator는 계속 돌고, 결정에 종속된 노드만 멈추는 구조**를 기본으로 한다.

```text
Main Coordinator / Work DAG
  ├─ 독립 노드 A ───────────────────────→ 계속 실행
  ├─ 노드 B ─→ WAITING_DECISION ─┐
  └─ B 의존 노드 C ─→ 대기        │
                                  ▼
                 DecisionRequest + context capsule
                                  │
        Decision Concierge (별도 pane/thread/mobile card)
                                  │ 사용자 답변
                                  ▼
                 versioned DecisionReceipt
                                  │ event publish
                                  └──────────────→ B만 재개
```

realm마다 하나의 지속형 Decision Concierge를 두고, 요청마다 짧은 thread나 Herdr pane을 열어 사용자가 현재 메인 세션을 찾아다니지 않게 한다. host가 독립 세션을 요구하면 context capsule만 가진 임시 질문 세션을 생성하고, receipt가 원장에 반영되면 닫는다. 채널은 Web·CLI·Slack·Discord·Telegram 중 선택하며, 같은 request가 여러 채널에 보이더라도 첫 유효 응답 하나만 원자적으로 채택한다.

`DecisionRequest`에는 `decision_id`, `work_id`, `attempt_id`, `spec_digest`, 질문, 2~3개 선택지와 권장안, 영향, 차단된 node IDs, 만료 시각을 넣는다. `DecisionReceipt`는 정확히 같은 request와 spec version을 가리켜야 한다. stale·중복·권한 없는 응답은 실행 상태를 바꾸지 못한다. 답이 없거나 만료되면 기본값은 **아무 side effect도 하지 않고 대기 또는 안전 종료**다.

Decision Concierge는 질문을 설명하고 답을 구조화할 수 있지만, 작업 파일 수정·모델 재배정·권한 확대를 직접 수행하지 않는다. coordinator는 receipt를 받은 뒤 최신 policy와 repo 상태를 다시 확인하고 해당 노드만 재개한다. 질문과 답은 realm 밖으로 복제하지 않고, 긴 원문 대신 필요한 최소 context capsule만 전달한다.

긴급하지 않은 질문은 묶어 승인함에 보여 주고, 작업 진행을 실제로 막는 질문만 즉시 알린다. 초기 성공 지표는 메인 coordinator uptime, 결정 때문에 멈춘 node 비율, 질문당 응답 시간, stale 응답 거절률, 답변 뒤 재작업률이다.

### 준비와 반영을 나누는 3단계 계약

시간대는 실행 권한을 바꾸지 않는다. 시스템은 허용된 모든 작업 유형을 받되, 각 작업을 다음 단계로 나눈다.

1. **Prepare**: 격리된 worktree·sandbox에서 조사, 구현, 테스트, 보안·정책 검사, 독립 review, dry-run과 rollback 작성을 수행한다.
2. **Propose**: `CandidatePackage`를 만든다. 코드 작업은 PR 제목·본문과 diff를 포함한다. repo policy가 미리 허용한 경우에만 자동 draft PR을 열고, 그 외에는 같은 내용을 로컬 검토 후보로 남긴다.
3. **Apply**: 인간이 `artifact_digest + base_sha + policy_digest + target + account_profile_id + action`을 승인하면 현재 base·policy·CI를 다시 확인한 뒤 승인된 push·PR 공개·merge·deploy·운영 변경만 실행한다. 반영 뒤 별도 `ApplicationReceipt`를 만든다.

PR 생성은 CI 비용, 알림, webhook과 코드 공개 범위를 바꾸므로 독립된 publication 권한으로 다룬다. 각 저장소의 repo policy가 명시한 bot 계정·브랜치·label·CI 범위 안에서만 `auto_draft_pr`을 허용한다.

모든 작업이 PR로 끝나지도 않는다. DB·인프라는 migration과 dry-run·rollback package, 비밀정보·결제는 placeholder 기반 변경안과 실행 절차, 외부 메시지는 정확한 발송 preview가 검토 후보가 된다. 실제 환경에서만 가능한 검증은 `unverified_external_effect`로 남기며 완료로 포장하지 않는다.

사람 확인을 항상 마지막으로 미루면 요구사항이나 아키텍처를 잘못 선택해 비용을 낭비할 수 있다. 선택에 따라 재작업이 필요하면 Decision Concierge가 먼저 묻고, 답과 무관한 준비 작업만 계속한다.

## 24시간 무인 준비 루프와 인간 반영 게이트

```text
INTAKE
  → CLASSIFIED ── 부적격 ──→ HUMAN_QUEUE
  → ROUTED
  → PREPARED (isolated worktree/sandbox + budget reservation)
  → EXECUTING
  → VERIFYING
      ├─ pass + weakening 없음 → CANDIDATE_READY
      ├─ fail + retry 가능     → RETRY / model escalation
      ├─ 질문 필요              → WAITING_DECISION (다른 노드는 계속)
      ├─ error/한도 초과        → BLOCKED 또는 FAILED
      └─ 실제 환경 확인 필요    → REVIEW_REQUIRED
  → PROPOSING (CandidatePackage, optional draft PR)
  → AWAITING_APPLY_APPROVAL
  → APPLYING (승인된 digest와 action만)
  → POST_APPLY_VERIFY
  → RECEIPTED
```

여기서 `부적격`은 위험도가 높다는 뜻이 아니다. 정책상 금지된 작업, 허용되지 않은 data realm, 필요한 권한이나 검증 수단이 없는 작업을 가리킨다. 위험도가 높은 허용 작업도 격리된 준비와 검증은 계속하고, 외부 반영 직전에 멈춘다.

자동 `DONE` 상태를 두지 않는다. 사용자나 팀 정책이 review·merge·external write까지 위임한 경우에도 해당 side effect의 별도 receipt를 남긴다.

### 위험 등급

| 등급 | 무인 준비 | 실제 반영 |
|---|---|---|
| R0 읽기·분류·요약 | 자동 실행하고 근거를 남긴다. | 별도 외부 쓰기가 없으면 즉시 확정할 수 있다. |
| R1 격리된 branch/worktree의 되돌릴 수 있는 수정 | 구현·검사·독립 review와 `CandidatePackage`까지 진행한다. | pre-authorized repo에서는 draft PR까지 가능하다. merge는 별도 승인이다. |
| R2 새 dependency, push, PR 공개, 네트워크 쓰기 | 변경·호환성·비용을 검증하고 정확한 publication preview를 만든다. | repo·realm 정책의 사전 허용 또는 action-bound 승인이 있어야 한다. |
| R3 secret, auth, 결제, prod, DB migration, merge·deploy, 메시지 발송 | placeholder·dry-run·영향 분석·rollback·실행안을 준비한다. | artifact digest와 실제 action에 묶인 인간 승인 뒤에만 실행한다. 필요하면 2인 승인을 요구한다. |

AGENTS.md·CLAUDE.md와 같은 문서는 지침의 정본이 될 수 있지만 보안을 강제하지는 못한다. 실제 강제는 sandbox, network allowlist, scoped credential, protected branch, CI와 host permission이 맡는다.

### hard limits

- attempt·wall time·tier 상향 한도는 작업 유형별 `RunPolicy` 기본값으로 둔다. 전역 고정값 3회·60분으로 장시간 작업을 자르지 않는다.
- 같은 diff hash나 failure signature가 반복되고 검사·artifact·진행 지표가 개선되지 않으면 해당 경로를 중단한다.
- 작업별·무인 실행 구간 전체 비용을 호출 전에 예약하고 종료 뒤 정산.
- 공식 잔여 quota를 알 수 없다는 이유만으로 전부 금지하지 않는다. metered API는 보수적 비용 예약, opaque subscription은 요청 수·동시성·wall time 상한을 사용한다. 반드시 지켜야 하는 금액 한도를 강제할 수 없는 경로만 차단한다.
- 연속 5개 작업이 실패하면 해당 realm·runner의 circuit breaker를 작동하고, 사람이 해제하거나 정책상 cooldown이 끝날 때까지 새 작업을 시작하지 않는다.
- 동시성, tool call, diff 크기, 파일 수, 디스크, context, network egress 상한.
- 운영 credential을 sandbox에 넣지 않고 repo 범위 token과 endpoint allowlist만 전달.
- 기본 자동 side effect는 isolated patch/local commit과 `CandidatePackage`까지다. push·draft PR은 realm·repo policy가 열어야 하고 merge·deploy는 action-bound 승인이 필요하다.
- 자동 draft PR은 전용 bot branch와 최소 권한 token을 사용한다. AI가 workflow·CI 설정을 바꾼 후보에는 운영 secret이나 privileged self-hosted runner를 승인 전 연결하지 않는다.
- kill switch와 daemon heartbeat를 제공한다. hard limit을 뚫은 사고가 생기면 무인 실행 전체를 자동 비활성화한다.
- worker는 lease를 갱신한다. crash 뒤 lease가 만료되어도 기존 worktree와 attempt를 확인하기 전 새 작업이 덮어쓰지 않는다.

### 실제 24시간 배치

개인 alpha에서는 데스크톱 한 대에서 authority service와 worker를 별도 프로세스·데이터 디렉터리로 띄울 수 있다. 다만 재부팅·고장 중에도 모바일 질문과 승인을 받아야 한다면 작은 항상 켜진 authority host를 GPU worker와 분리한다. realm마다 writable authority는 하나이며 live SQLite 파일을 iCloud·Dropbox 같은 파일 동기화로 복제하지 않는다. 노트북이나 집 데스크톱이 꺼져 있으면 작업은 대기하거나 허용된 managed/cloud runner로만 이동한다.

서로 다른 realm은 별도 ledger, artifact store, credential, provider allowlist와 service identity를 사용한다. 통합 화면은 허용된 status projection만 합친다. 팀 제품에서는 Hub가 durable authority를 맡고 runner가 outbound로 연결한다.

선택형 GPU workstation은 필요할 때만 local model worker를 띄운다. 저전력 laptop은 가벼운 daemon·승인 UI·wake relay 후보지만 칩·RAM·상시 전원 조건을 확인하기 전 책임을 고정하지 않는다. 로컬 GPU 하나의 가동 여부가 전체 queue의 정본이나 scheduler가 되어서는 안 된다.

## 모델·계정·비용 라우팅

라우팅 순서는 **realm 허용 목록 → 데이터 민감도 → 작업 위험도 → 필요한 capability → 과거 검증 성과 → 비용·quota**다. 비용 절감 때문에 데이터 분리 규칙을 위반해서는 안 된다.

| tier | 후보 | 맡길 일 | 승격 조건 |
|---|---|---|---|
| T0 Local | 평가를 통과한 Qwen·기타 open weight, llama.cpp/Ollama/Hermes local endpoint | 분류, 요약, 로그 구조화, KB 후보, review brief, 단순 lint·문서 초안 | tool use·context·repo eval을 통과한 유형에만 코드 수정 허용 |
| T1 Free API | OpenRouter free 등 | 공개 저장소의 비민감 보조 작업, batch 실험 | SLA와 quota를 전제하지 않으며 실패 시 핵심 경로를 막지 않음 |
| T2 Low-cost/plan | GLM Coding Plan, Qwen API, 저가 endpoint | 검증 recipe가 있는 저·중위험 구현 | capability·data policy 확인, realm 허용, 가격·quota는 값 또는 `unknown`으로 명시하고 강제 가능한 비용 reservation이나 요청·동시성·wall-time 상한 충족 |
| T3 Frontier | Claude, Codex 등 | 복잡한 구현, 보안·설계, 낮은 tier의 의미 있는 실패, 독립 최종 review | 별도 무인 실행 예산과 승인 정책 적용 |

12GB급 GPU에는 7~14B급 양자화 모델이 후보가 될 수 있지만 이는 메모리 적합성에 관한 가정일 뿐 품질 보장이 아니다. 실제 task suite로 정확도, tool-call 성공, context 길이, tokens/sec, 전력비, 승인률을 함께 측정한다. 더 큰 모델의 offload는 가능 여부보다 처리량과 안정성이 먼저 문제이므로 기본 경로로 두지 않는다.

### 공식 계정과 보수적 quota 처리

- 사용자가 해당 realm 용도로 정당하게 보유한 공식 API·CLI·구독만 사용한다.
- provider가 공식 usage endpoint나 CLI를 제공할 때만 남은 양을 자동 판단한다. 모르면 `unknown`으로 기록하되, 강제 가능한 요청·동시성·wall time·비용 reservation 안에서 실행할 수 있다.
- 계정 공유, 다계정 rotation으로 제한 우회, usage 화면 scraping을 제공하지 않는다. 계정 이름 대신 realm·data class·device·action별 allowlist로 허용 여부를 판정한다.
- provider별 automation, coding-plan endpoint, output의 상업 이용 약관을 지원 매트릭스의 출시 gate로 둔다.
- 실행 receipt에 provider, model, account alias, capability snapshot hash, price snapshot과 실제 비용 또는 `unknown`을 남긴다.

초기 router는 사람이 읽을 수 있는 정적 규칙이다. 학습형 router는 `(task type, model)` 조합별 승인률과 비용 사례가 충분히 쌓인 뒤에만 shadow로 평가한다. LiteLLM의 transport·fallback은 재사용하되 LiteLLM의 선택 결과를 제품의 정책 판정으로 간주하지 않는다.

## Adapter와 protocol 전략

### capability matrix

adapter는 선형 L0~L3 등급 대신 아래 능력을 각각 선언한다. 관찰은 잘하지만 취소나 identity 증거가 약한 adapter를 높은 등급 하나로 과장하지 않는다.

| capability | 예시 값 |
|---|---|
| invocation | none · prompt · structured-session |
| observation | screen-hint · event-stream · durable-event |
| lifecycle | start · pause · resume · cancel · reconnect |
| permission | none · native-request · scoped-confirmation |
| identity evidence | process-hint · session-id · signed/provider record |
| artifacts | diff · file · sandbox snapshot · external receipt |
| recovery | none · reconnect · provider checkpoint · reconciled effect |

adapter는 startup handshake에서 capability, limitation과 protocol version을 선언한다. 지원하지 않는 기능을 추정하지 않고 `unsupported`로 반환한다. 새 버전에서 contract test가 깨지면 영향을 받은 capability만 비활성화한다.

### 도구별 역할

| 도구 | 역할 | 피할 것 |
|---|---|---|
| Herdr | 사용자가 이미 연 터미널 session의 observe·link, 선택적 command bridge | Herdr 내부 상태를 Work 정본으로 삼기, hard fork |
| Hermes | cron trigger, 메시징 gateway, remote backend, Forge MCP·CLI 호출 | Hermes memory·router를 제품 정본으로 삼기 |
| OMP | multi-provider/local-model invocation과 확인된 session·artifact capability | provider routing 정책을 OMP 안에만 숨기기, 지원하지 않는 capability 추정 |
| Claude Code | structured/headless invocation, 지원되는 환경의 Agent SDK native permission event | Claude 전용 상태를 중립 core에 넣기 |
| Codex | App Server의 structured session·event·approval, `exec` fallback | private UI scraping, fallback을 native approval과 동급으로 표시하기 |
| Claude Managed Agents·OpenAI Agents API | 허용 realm의 managed session·sandbox·event·checkpoint 실행 | provider session을 Work·Approval·Receipt 정본으로 삼기, provider 권한을 cross-system 승인으로 간주하기 |
| OpenHands | 선택형 CLI/ACP runtime과 배포 surface | Canvas 전체 fork |

### protocol 배치

- MCP: `verify`, `enqueue`, `get_work`, `get_receipt`, `request_approval`처럼 Forge 기능을 다른 agent와 client에 노출한다.
- ACP: Forge가 runtime client가 되어 session·permission을 다룰 때 쓴다.
- A2A: 원격 독립 agent끼리 직접 협상할 실제 요구가 생긴 뒤에만 넣는다. 초기 내부 queue protocol로 쓰지 않는다.
- OTel/in-toto/SLSA/CDEvents: 외부 관측·감사·CI ecosystem으로 export한다.

공식 지원은 처음에 Claude Code·Codex의 검증된 capability 조합과 Git-only verification을 둔다. Herdr·Hermes·OMP·OpenHands는 integration 또는 community adapter로 시작한다. 최신과 직전 버전을 conformance CI로 검사한다.

## CodeForge와 ForgeGlow 이행안

### 새 host-neutral core 저장소

새 저장소를 만드는 편이 낫다. 기존 code-forge의 Claude 전용 lifecycle과 unreleased dirty work를 깨뜨리지 않고 contract·license·release를 명확하게 시작할 수 있다.

```text
codeforge-platform/
├── cmd/
│   ├── forged/              # Go authority daemon
│   └── forge/               # Go CLI
├── internal/
│   ├── controller/          # state machine, lease, hard limits
│   ├── kernel/              # spec, verdict, weakening, receipt
│   ├── ledger/              # SQLite WAL, migration, outbox
│   ├── policy/              # realm/data/account/device/action
│   ├── verification/
│   └── knowledge/
├── protocol/                # JSON Schema, OpenAPI, IDs, compatibility
├── adapters/
│   ├── claude/
│   ├── codex/
│   ├── herdr/
│   ├── local-openai/
│   └── git/
├── web/                     # TypeScript responsive PWA
├── sdk/                     # adapter·client SDK
├── exporters/               # in-toto, SLSA, CDEvents, OTel
└── conformance/             # recovery, security, adapter, migration
```

위 디렉터리와 **Go daemon·CLI + TypeScript PWA**는 10월 15일 설계 후보로 보존한다. 현재 이름·언어·배포 방식은 통합 계획의 G0b에서 TypeScript 단일 구현 후보와 설치·취소·복구·SQLite·SDK 실험으로 비교해 ADR로 확정한다. schema와 API는 언어 중립으로 유지한다.

### 기존 code-forge

- v4.x는 현재 출시 차단 결함과 실제 host 검증을 먼저 끝낸다.
- 다음 주요 버전은 공통 원본에서 Claude·Codex host pack을 생성한다. managed 실행만 새 core CLI에 연결하고 native 사용은 독립적으로 유지한다.
- 기존 `AGENTS.md`, `CLAUDE.md`, skills, Smith/사고 모델은 project pack compiler의 입력 후보가 된다.
- 기존 alias·status v1 reader는 통합 계획에 따라 최소 두 릴리스 유지하고, consumer 호환·복구 검증 후 전환한다.
- 기존 MIT license는 유지한다.

### ForgeGlow

- 별도 MIT client로 유지한다.
- session-local HUD를 유지한다. daemon의 versioned status projection 연결은 선택형 adapter로 별도 검증한다. 기존 `parse-forge.sh`가 제거된 WIP를 현재 consumer로 가정하지 않는다.
- 상태·완료·비용을 직접 판정하지 않는다. 팀 review inbox와 제품 surface가 겹친다는 증거가 생길 때만 Hub UI와 통합한다.

## 지식베이스와 “나의 복제”

사용자에게는 하나의 기억처럼 보이되 내부는 realm별로 분리한다.

| realm | 허용 지식·실행 | 기본 금지 |
|---|---|---|
| Personal | 개인 vault·repo와 이 realm에 명시적으로 허용된 provider·계정·장비 | 다른 workspace·tenant context 검색 |
| Workspace-A | 해당 workspace의 repo·문서와 정책이 허용한 계정·장비·endpoint | 허용되지 않은 장비·provider로 전송 |
| Customer/Tenant | 해당 tenant repo·KB·retention | 다른 tenant의 prompt·embedding·eval 재사용 |
| Public | 공개 문서·공개 repo | 비공개 source의 파생 정보 포함 |

repo는 realm 판정의 강한 입력이지만 유일한 기준은 아니다. router는 data class, action, account, device와 현재 정책을 함께 평가한다. 예를 들어 조직이 승인한 provider profile이 작업 유형마다 다를 수 있다. 이름이나 폴더만 보고 허용 계정을 추측하지 않는다. 조직 정책이 개인 장비 사용을 명시적으로 허용하지 않으면 비용이 낮더라도 그 장비로 조직 작업을 보내지 않는다.

### 정본과 저장 방식

- 개인 지식: Markdown/Obsidian vault를 사람이 편집하는 정본으로 사용할 수 있다.
- 프로젝트 지식: `AGENTS.md`, `CLAUDE.md`, ADR, docs, policy pack을 Git 정본으로 둔다.
- 문서·이슈 시스템: 원래 시스템을 정본으로 두고 stable link·revision·snapshot만 인덱싱한다.
- 로컬 검색: SQLite FTS에서 시작한다. embedding과 graph는 출처 필터 뒤에 붙인다.

각 knowledge item은 `source`, `realm`, `owner`, `version`, `verified_at`, `expires_at`, `trust`, `ACL`, `supersedes`를 가진다. 오래된 대화 요약이 프로젝트 정책을 덮지 못하도록 authority 순서를 고정한다.

### prompt log와 개선 루프

raw prompt 수집은 기본 off다. realm별 opt-in, secret·PII redaction, TTL, export, 작업·realm 단위 삭제를 제공한다. hosted Hub에는 기본적으로 receipt와 최소 운영 metadata만 동기화하고 코드·prompt는 올리지 않는다.

GEPA와 유사한 최적화는 실시간 active prompt 수정에 쓰지 않는다.

```text
receipt·선택적 trajectory
  → task별 정규화와 failure clustering
  → prompt/skill 후보
  → 고정 eval + holdout
  → shadow/canary
  → 사람이 승인하는 versioned PR
```

자동 최적화는 작업 계보별로 분리된 독립 holdout과 승인된 표본 계획을 갖춘 뒤 시작한다. 과거 50건 기준은 수집 이정표이지 자동 승격 요건이 아니다. 로컬 T0 모델은 log 분류와 후보 생성에 쓸 수 있고, 중요한 판정은 receipt와 독립 evaluator로 확인한다. Obsidian·Lark·그래프 도구는 authoring·source adapter이며 제품의 단일 필수 DB가 아니다.

### 범용 검증 계약과 측정 기반 코드 최적화 recipe

CodeForge core는 특정 저장소의 테스트 명령, 프론트엔드 지표나 benchmark 도구를 알아서는 안 된다. Core는 `VerificationRecipe → CheckResult → Evidence → Receipt` 계약과 독립 실행만 소유한다. 실제 명령·시나리오·metric·remote readback은 versioned `RepositoryProfile`이 제공한다.

검증 종류는 `command`, `scenario`, `metric_compare`, `policy`, `external_readback`으로 시작한다. 임계값 없이 수집한 metric은 `measured`이며 `pass`가 아니다. 실행하지 못한 검사는 원인에 따라 `not_run`, `unavailable`, `blocked`로 남기고 `n_a`에는 이유가 필요하다. Core는 결과를 숨기거나 하나의 종합 점수로 압축하지 않는다.

Gungraun식 baseline → 가설 → 격리 수정 → CI 재측정 → 성공 후보만 PR 흐름은 이 범용 계약 위의 `MeasuredOptimizationRecipe`로 표현한다. 각 metric check는 metric ID, 방향, harness command, base SHA, baseline·fixture·환경 digest, 상대·절대 gate, correctness command와 시도 한도를 가진다. Gungraun의 **Ir**은 Callgrind가 기록하는 실행 명령어 수이므로 Rust·Valgrind 환경의 profile에서만 사용한다. Go는 `go test -bench`와 benchstat, TypeScript·Python은 해당 저장소 benchmark나 별도 adapter를 사용할 수 있다.

~~~text
고정된 base·fixture·benchmark
  → baseline과 profile evidence
  → 격리 worktree에서 가설별 candidate
  → 기능 검사 + 로컬 metric 선별
  → repo policy가 허용한 bot branch push
  → 동일 CI 환경에서 base와 candidate 재측정
  → 모든 gate 통과 시 PR 승격, 실패 시 receipt만 보존
~~~

agent가 benchmark, fixture, baseline, threshold, CI workflow를 같은 candidate에서 바꾸면 자동 성공시키지 않고 REVIEW_REQUIRED로 보낸다. 명령어 수가 줄어도 cache, allocation, latency, output equivalence나 비용이 나빠질 수 있으므로 저장소가 정한 보조 metric의 비퇴행도 요구한다. P1 신뢰 커널을 먼저 완성한 뒤 첫 전문 recipe 중 하나로 실제 hotspot 한 곳에서 시험한다.

첫 profile 하나의 편의를 core 추상화로 굳히지 않는다. 성격이 다른 두 공개 저장소에서 같은 verifier 계약을 실행해 보고 공통인 부분만 SDK로 승격한다. 조직 전용 profile은 비공개 policy pack으로 유지하며 공개 저장소에는 이름·URL·계정·업무 fixture를 넣지 않는다.

## 언어·표현 아키텍처

### 판정

에이전트가 읽는 자료를 기계가 안정적으로 해석할 수 있는 형태로 작성한다는 방향은 맞다. OpenAI와 Anthropic의 공식 지침은 특정 자연어보다 명확한 목표, 관련 맥락, 일관된 구분자, 구체적인 제약, 예시와 평가를 강조한다. 자연어별 성능과 토큰 비용은 모델·버전·작업에 따라 달라지므로 모든 자료를 영어로 고정하지 않는다.

언어와 표현을 세 층으로 분리한다.

1. **Canonical source:** 사실과 규칙을 가장 정확하게 유지할 수 있는 언어로 저장한다. 한국 업무 용어와 조직 정책은 한국어 정본을 허용하고, API·schema·CLI·event identifier는 영어를 정본으로 삼는다.
2. **Agent pack compiler:** 정본 전체를 번역하지 않고 현재 작업에 필요한 지시, 제약, 예시, 출력 계약만 추출한다. 모델별 profile에 따라 Markdown, XML 또는 구조화 데이터로 컴파일한다.
3. **Presentation renderer:** 사용자에게 보이는 한국어는 한국어 윤문을 거친다. 영어는 영어 독자의 목적과 문맥에 맞춰 다시 쓴다.

### 문서별 기본 정책

| 대상 | 정본 언어 | 보조본·출력 정책 |
|---|---|---|
| protocol, schema, API, CLI, event, error code | 영어 | 식별자는 번역하지 않고 설명만 현지화 |
| 공개 OSS `README.md` | 자연스러운 영어 | 완결된 `README.ko.md`를 별도 집필하고 상단에서 상호 연결 |
| 공개 architecture·RFC | 주요 독자 언어 | 중요한 문서만 다른 언어의 결정 요약 제공 |
| 한국어 계획·핸드오프·작업 보고 | 한국어 | 게시 전에 한국어 윤문 |
| `AGENTS.md`, `CLAUDE.md`, skill | 의미가 가장 정확한 원문 | 모델별 compile 결과를 평가해 선택 |
| 사용자·workspace KB | 출처의 원래 언어 | 검색 결과를 사용자 locale에 맞게 작성 |

모든 문서의 한·영 전체 사본을 매 요청에 함께 넣지 않는다. 토큰 중복과 버전 불일치를 피하기 위해 정본 하나, 필요한 용어표, 출력 locale만 전달한다. companion 문서에는 `canonical_revision`, `source_language`, `translation_status`, `reviewed_at`을 기록한다. CI는 오래된 번역을 알리되, 보안·정책·첫 온보딩처럼 잘못된 번역의 영향이 큰 문서만 차단한다.

### LanguageProfile과 평가

각 skill·model 조합에 다음 세 후보를 비교한다.

- 원래 한국어로 작성한 지시문
- 영어 독자를 기준으로 새로 작성한 지시문
- 정본에서 작업별로 컴파일한 혼합형 지시문

평가 항목은 기능 성공률, tool 선택·argument 정확도, 정책 위반, 사람이 수정하는 시간, 전체 token·비용, latency다. 비교 결과는 versioned `LanguageProfile`로 저장하고 model revision이 바뀌면 다시 평가한다. 평가 전 기본값은 source-preserving이다. 자동 직역이나 영어 강제는 하지 않는다.

이 구조는 한국어 사용성을 유지하면서 공개 OSS와 여러 모델을 지원한다. 동시에 skill 내부 표현과 사람에게 보여 주는 문체를 분리하므로, 모델 최적화가 사용자 문서의 가독성을 해치지 않는다.

## 오픈소스와 유료 서비스

### 라이선스 권고

- 새 core·schema·SDK·공식 adapter: Apache-2.0 후보. 명시적 patent grant와 기업 도입성을 얻는다.
- 기존 CodeForge·ForgeGlow: 현재 MIT 유지.
- Hosted Hub: 별도 상용 코드로 시작할 수 있다.

기존 기여자 권리, 코드의 출처·귀속, MIT 코드를 새 Apache 프로젝트로 가져오는 방식, CLA/DCO, 상표, 모델·provider 약관은 출시 전에 별도 검토한다.

### 영구 무료로 둘 것

- trust kernel, CLI, schema, receipt와 exporter
- GitHub Action과 verification correctness
- 단일 사용자 local daemon·무인 준비 runner·review brief
- routing policy와 budget hard limits
- adapter SDK, MCP server, 핵심 official adapters
- local ledger·KB source adapter·데이터 export와 삭제

안전과 검증 정확성을 유료 기능으로 막지 않는다.

### 유료 전환 시점

사용자가 **공유된 통제와 기록**을 필요로 할 때 과금한다. 더 좋은 모델 제공만으로 과금하지 않는다.

- 두 번째 사람이 같은 queue·approval inbox를 사용
- 여러 repo에 조직 정책을 배포·강제
- PR 작성자가 우회할 수 없는 required check
- 역할 기반 approval·waiver와 사유 기록
- 여러 저장소 receipt의 보존·감사·검색
- SSO/RBAC, 조직 budget, team analytics
- 노트북이 꺼져 있어도 작동하는 hosted inbox와 이후 managed sandbox

## 단계별 출시 계획

아래 P0~P6는 기존 설계의 분류다. 실행 순서는 통합 계획의 G0a/G0b → G1a/G1b → G2 → G3 → G4와 이후 수요별 확장을 따른다. 단일 장비 무인 준비·복구는 G2, 원격 모바일·별도 authority/worker는 G4다.

기간은 목표이지 아키텍처 중단 조건이 아니다. 각 단계는 광고한 범위 안에서 복구·권한·마이그레이션까지 완성한다.

| 단계 | 쓸 수 있는 결과 | 통과 gate |
|---|---|---|
| P0 계약과 신뢰 가능한 검사 | 새 core monorepo, schema·migration, receipt CLI, compatibility `doctor`, legacy read-only import | unknown이 pass가 되는 경로 0, policy conflict 노출, export·restore 성공 |
| P1 매일 쓰는 로컬 최적화 수직 단면 | structured runtime 1개, 공개 저장소 profile 1개, baseline·병목·최소 candidate·독립 검증, Decision/Approval Inbox, narrow apply executor | 질문 대기가 다른 Work를 막지 않음, 재시작 뒤 후보·결정 복구, stale grant 적용 0, 기능 비퇴행과 개선을 CI에서 재현 |
| P2 여러 runtime과 범용성 검증 | Claude/Codex 두 계열, 성격이 다른 두 번째 공개 저장소 profile, Herdr 관찰, 명시적 session adopt/handoff, capability·profile conformance | 두 runtime과 두 profile이 같은 계약을 통과, observed/controlled 구분, adapter failure가 권한을 넓히지 않음 |
| P3 24시간·교차 기기 | realm authority, 선택형 GPU worker, 모바일 웹 검토, managed backend 하나 | 절전·power loss·중복 응답·지연 취소 fault test, 중복 승인된 외부 effect 0 |
| P4 지식 연속성 | source adapter, provenance 검색, 결정·절차, revocation·deletion | 모든 retrieved claim의 출처 추적, revoke 뒤 future retrieval 제외, cross-realm isolation 통과 |
| P5 라우팅과 개선 | local·GLM·Qwen qualified path, prompt/skill 후보, eval·rollback | unseen work에서 품질·attention 비퇴행, 자동 권한 확대 0 |
| P6 팀·유료 hosting | Postgres, object storage, Temporal, org·team approval, audit/export | tenant isolation, membership revoke, restore, upgrade, worker disconnect 운영 시험 통과 |

Hosted에서도 domain transition과 Approval/Receipt 정본은 Postgres ledger 하나다. Temporal은 상태 기계를 깨우고 activity를 재시도하는 orchestration runtime이며 제품 정본이 아니다. Postgres commit과 activity 사이 부분 실패는 idempotency key와 reconciliation으로 복구한다.

### 기능별 중단·격리 기준

- setup/spec 작성이 반복적으로 오래 걸리면 compiler와 UX를 단순화한다. 제품 전체를 consulting으로 단정하지 않는다.
- 무인 결과 채택률이 낮으면 해당 task class·model·adapter를 제한하고 routing과 evidence package를 고친다.
- hard limit이 막지 못한 무단 side effect나 realm 유출이 한 건이라도 발생하면 **영향받은 unattended capability**를 즉시 중단하고 enforcement 결함을 고친다.
- adapter가 반복적으로 깨지면 해당 capability와 지원 버전을 축소한다. 다른 runtime과 core는 계속 운영한다.
- verifier 판매가 약하면 packaging과 market entry를 바꾼다. durable approval·work·knowledge 계약의 필요성과 혼동하지 않는다.
- 결제·LOI가 없으면 Hosted Hub 투자와 가격 전략을 재검토한다. Solo Local OSS와 개인용 제품 목표는 유지할 수 있다.
- 외부 플랫폼이 계약을 충족하면 그 구현을 재사용하고 겹치는 surface를 줄인다. CodeForge가 소유해야 할 의미보다 자체 코드량을 지키지 않는다.

## 가장 큰 반론과 반증 실험

| 반론 | 가장 싼 반증 실험 |
|---|---|
| 저가·로컬 모델의 무인 결과가 검토 노동만 늘린다. | 같은 유형 백로그 50건에서 승인률, 검토 분, verified completion당 비용을 T0/T2/T3로 비교한다. |
| verification weakening은 드물어 핵심 가치가 아니다. | 공개된 bot/agent PR 200건을 taxonomy v0로 스캔하고 실제 사례와 팀 반응을 기록한다. |
| 사람들은 provider 하나면 충분해 portability에 돈을 내지 않는다. | design partner의 2개 이상 provider 사용 비율과 가격을 표시한 landing page·인터뷰의 지불 의사를 측정한다. |
| 로컬 PC는 절전·업데이트·GPU 경합 때문에 무인 worker로 신뢰할 수 없다. | 5개 환경에서 2주간 완주율·복구율·전력비를 측정하고 90% 미만이면 cloud runner 일정을 재평가한다. |
| 공식 quota 정보가 불완전해 budget router가 무용하다. | provider capability·usage matrix와 reservation simulation을 만들고 `unknown`은 보수적 요청·동시성·wall time 한도로 운용한다. 강제 금액 한도가 필요한 경로만 제외한다. |
| CI·in-toto·OPA를 포장한 것뿐이다. | 동일 PR에서 기존 CI만으로 놓친 weakening/waiver/agent provenance를 kernel이 추가로 잡는지 측정한다. 추가 정보가 없으면 verification-weakening 차별화 가설과 해당 판매 포장을 폐기하되, 조율·승인·지식 연속성의 북극성은 별도 지표로 평가한다. |

## 최종 결정

1. **아키텍처는 크게 설계한다.** schema, truth semantics, realm, budget, adapter compatibility는 공개 서비스 수준으로 만든다.
2. **기능은 완전한 수직 단면으로 순서대로 연다.** P1부터 durable Work, 비동기 질문, 검토·승인, apply/readback을 포함한다. verifier 판매 성과를 unattended runner의 선행 조건으로 두지 않는다.
3. **24시간 자율성은 핵심 경험으로 유지한다.** 검증된 `CandidatePackage`와 사람이 채택한 비율을 성공 지표로 삼는다.
4. **기존 CodeForge를 개선한다.** 기존 plugin을 수리하고 Claude·Codex native pack과 공통 policy 원본을 유지한다. 중립 kernel은 새 저장소에서 시작한다.
5. **ForgeGlow를 합치지 않는다.** 공개 API를 소비하는 별도 HUD로 두어 두 번째 실제 consumer와 호환성 시험대 역할을 맡긴다.
6. **Hermes·Herdr·OMP·OpenHands를 fork하지 않는다.** 각 도구의 강점을 adapter 뒤에서 사용한다.
7. **기본 지식 연속성은 초기에 포함하고 고급 검색과 prompt 개선은 뒤에 연다.** realm·provenance·retention·revocation과 실제 사용 context는 첫날부터 남기고, graph·GEPA 구현은 데이터와 평가가 생긴 뒤 연다.
8. **시퀀서는 자체 합성 fixture로 검증한다.** `/start`는 Work Compiler, Codex Goal은 attempt 단위 지속 계약으로 제한한다.
9. **언어는 문서의 독자와 실제 평가로 선택한다.** 기계용 skill은 모델별로 컴파일하고, 한국어 결과는 윤문하며, 영어 결과는 직역하지 않고 영어 독자를 위해 별도로 집필한다.
10. **managed runtime을 적극 재사용한다.** Claude Managed Agents·OpenAI Agents API의 세션·복구·sandbox와 Claude Agent SDK·Codex App Server의 로컬 event/approval을 adapter로 사용한다. CodeForge는 cross-provider work·policy·approval·evidence·knowledge 계약을 소유한다.
11. **realm마다 별도 authority를 운영한다.** ledger·artifact·credential·provider allowlist를 분리하고, 통합 화면에는 허용된 status projection만 모은다.
