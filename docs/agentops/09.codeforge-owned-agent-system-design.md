# CodeForge 중심 개인·팀 AI 통합관제 시스템 최종 설계

> 작성일: 2026-10-14

> 대상: 여러 AI 코딩 세션을 쓰는 개인 개발자와 소규모 팀. 이후 기업·비개발 업무로 확장한다.

## 한 문장 결론

**CodeForge를 작업·정책·지식·검증의 정본을 소유하는 벤더 중립 Control Plane으로 발전시키고, Herdr·Hermes·OMP·Qwen·Claude·Codex·로컬 모델은 교체 가능한 어댑터로 붙인다.** ForgeGlow는 이 정본을 읽는 관제 화면으로 만든다. Paperthin의 좋은 사고 절차는 선별해 내장하되, 전체를 상시 실행하거나 외부 저장소와 실시간 동기화하지 않는다.

이 문장은 도달 가능한 장기 구조다. 현재 승인 가능한 구현 범위는 아니다. 먼저 run별 상태·검증 영수증·읽기 전용 관제만 가진 Thin Coordinator가 실제 창 순회와 goal/handoff 반복을 줄이는지 2주간 검증한다.

이 구조의 가칭은 **CodeForge Control Plane**이다. 제품명이 필요해지면 별도로 정하되, 지금은 새 브랜드보다 안정적인 계약과 실증이 우선이다.

## 왜 이전 조합을 그대로 쓰면 안 되는가

이전의 `Hermes 상위 에이전트 + Herdr 실행 감독 + OMP 기본 실행기`는 빠른 개인용 프로토타입에는 합리적이다. 그러나 최종 제품의 중심으로 삼으면 다음 문제가 생긴다.

1. 작업 상태는 Herdr, 기억은 Hermes·OMP, 라우팅은 OMP, 룰은 각 저장소, 완료 판단은 또 다른 스크립트가 소유한다. 같은 개념의 정본이 여러 곳으로 갈라진다.
2. 외부 도구의 세션·메모리·플러그인 형식이 제품 데이터 모델이 된다. 도구를 교체하는 순간 마이그레이션 비용이 커진다.
3. 다수 도구의 자동 라우팅과 자기개선이 겹치면 “왜 이 모델이 이 정보로 이 결정을 했는지” 설명하기 어렵다.
4. 사용자가 이미 만든 CodeForge의 정책·상태·사고 모델과 ForgeGlow의 관찰 기능이 주변부로 밀린다. 오픈소스·유료 제품의 차별점도 약해진다.
5. 항상 켜 둔 Hermes·OMP·Qwen·Herdr를 한꺼번에 운영하면 세션, 인덱스, 데몬, 로그가 중복되어 자원과 운영 부담이 늘어난다.

따라서 외부 도구는 **실행 능력을 빌리는 부품**이어야 한다. 작업의 의미, 승인, 지식, 완료 증거는 CodeForge가 소유해야 한다.

OpenHands Agent Canvas까지 포함하면 이 판단은 더 강해진다. Agent Canvas는 이미 로컬·원격·클라우드 backend와 ACP를 통한 Claude Code·Codex·Gemini 실행, 프로필, 자동화, 화면을 제공한다. 이제 단순한 “여러 에이전트를 한 화면에서 실행”은 충분한 제품 차별점이 아니다. 첫 제품 쐐기는 **서로 다른 기존 세션에도 적용되는 저장소 정책과 검증 증거 게이트**여야 한다. Agent Canvas는 필요하면 좋은 실행·표시 adapter지만, 이를 fork해 전체 제품의 데이터 모델로 삼으면 사용자가 이미 Herdr나 터미널에서 시작한 세션을 수용하기 어렵고 upstream UI·backend 변화까지 떠안는다.

## 제품의 핵심 경험

사용자는 어느 기기에서든 “이 작업을 끝내 줘”라고 말한다. 시스템은 저장소 룰과 계정 경계를 먼저 확인하고, 필요한 모델과 실행 환경을 고른 뒤 세션을 시작한다. 사용자가 계속 들여다볼 필요가 없는 동안에는 실행을 이어 가고, 다음 네 경우에만 Attention Queue로 호출한다.

- 정책·비용·권한 승인이 필요할 때
- 질문 없이는 의미 있는 진행이 불가능할 때
- 검증 가능한 완료 후보가 생겼을 때
- 실패·예산 초과·충돌 위험이 생겼을 때

사용자가 보는 기본 단위는 채팅방이나 터미널 pane이 아니라 **Work**다. 한 Work 아래에 여러 실행과 모델 토론이 달리고, 마지막에는 결과·근거·검증·비용·남은 위험이 하나의 Receipt로 모인다. 모바일에서는 승인과 결과만 보고, 노트북에서는 diff와 세션으로 내려갈 수 있다.

중간에 사람의 판단이 필요해도 coordinator 전체가 사용자 답을 기다리며 멈추지 않는다. 결정에 종속된 노드와 그 하위 노드만 `WAITING_DECISION`으로 바꾸고, 나머지 runnable work는 계속 실행한다. 질문은 realm별로 하나인 **Decision Concierge**가 별도 Herdr pane, 웹 스레드, Slack·Discord·Telegram 카드로 전달한다. 답은 채팅 복사가 아니라 `decision_id`, 대상 spec version과 응답자 출처를 가진 `DecisionReceipt`로 원장에 기록되어 메인 실행으로 돌아간다.

## 목표 구조

```text
 Web / Mobile / CLI / Slack·Discord / ChatGPT dot·MCP
                         │
       Decision Concierge + CodeForge Gateway
             HTTP + MCP + local socket
                         │
┌──────────────── CodeForge Owned Core ────────────────┐
│ Work Ledger │ Policy & Approval │ Router             │
│ Context/KB  │ Evidence Verifier │ Eval/Learning      │
└───────────────────────┬───────────────────────────────┘
                        │ versioned Adapter Contract
        ┌───────────────┼────────────────┬──────────────┐
 Runtime adapters   Runner adapters   Source adapters  UI projection
 direct process     Claude/Codex      Git/Obsidian     ForgeGlow
 Herdr              OMP/Qwen/Hermes   Dooray/Lark      Web console
 remote worker      local/GLM/API     Slack/Notion     notifications
```

### CodeForge가 반드시 소유할 것

- Work·Execution·Run·Event·Artifact·Decision·Approval의 스키마와 상태 전이
- 저장소별 정책, 계정·데이터 경계, 승인 규칙의 스냅샷
- 모델과 실행기를 고르는 라우팅 규칙과 선택 근거
- 지식의 출처·권한·버전·유효기간·상충 관계
- “에이전트가 끝났다고 말함”과 “증거로 검증됨”을 분리하는 완료 판정
- 비용, 인간 개입, 재작업, 품질을 비교하는 평가 데이터
- 플러그인·어댑터 SDK와 호환성 테스트

### 초기에 직접 만들지 않을 것

- 터미널 에뮬레이터와 PTY 복구 엔진: Herdr 또는 직접 프로세스 어댑터를 사용한다.
- 모든 모델 공급자의 인증·스트리밍 SDK: OMP, LiteLLM 계열 또는 각 공식 CLI를 어댑터 뒤에 둔다.
- Slack·Discord·Telegram의 전체 게이트웨이: Hermes나 공식 봇 어댑터를 사용한다.
- 벡터 데이터베이스 엔진: SQLite FTS에서 시작하고 실제 규모가 증명될 때 교체한다.
- 새로운 범용 에이전트 루프: Claude·Codex·Qwen·Hermes 등 기존 실행기의 루프를 이용한다.

이 선을 지켜야 CodeForge가 또 하나의 거대한 에이전트 프레임워크로 변하지 않는다.

## 실행 계약

모든 실행기는 아래 개념을 주고받는다. 공급자 고유 세션 ID는 부가 정보이며 정본 키가 아니다.

### RunEnvelope

```yaml
work_id: work_...
goal: "사용자 결과 중심 목표"
acceptance_criteria: [...]
scope:
  repo_id: ...
  checkout_id: ...
  worktree_id: ...
  base_sha: ...
policy_refs: [...]
context_refs: [...]
account_profile_id: company-codex
capability_tier: standard
budget:
  money: ...
  tokens: ...
  wall_time: ...
permissions: [...]
approval_rules: [...]
```

### RunReceipt

```yaml
status: completed_candidate | blocked | failed
summary: ...
artifacts: [...]
evidence:
  diffs: [...]
  checks: [...]
  external_readbacks: [...]
cost: ...
blockers: [...]
next_action: ...
```

정상 상태는 `queued → running → completed_candidate → verified`다. 중간에 `waiting_decision`, `waiting_approval`, `blocked`, `failed`, `cancelled`로 갈 수 있다. `waiting_decision`은 해당 결정에 의존하는 노드만 멈추며, 부모 coordinator와 독립 노드는 계속 실행한다. **모델의 완료 메시지만으로 `verified`가 되지 않는다.** 저장소 테스트, 원격 상태 재조회, 문서 readback처럼 작업 유형별 Evidence Recipe가 통과해야 한다.

CodeForge에 이미 있는 cross-agent event 계약은 이 구조의 씨앗이다. 기존 문서는 두 번째 실소비자가 생길 때 append-only 원장을 재개하라고 했다. Control Plane과 ForgeGlow가 그 실소비자가 되므로, 이제 SQLite WAL 기반 이벤트 원장을 도입할 명분이 생긴다.

## “나의 복제 시스템”을 위한 지식 구조

하나의 거대한 벡터 저장소에 모든 대화를 넣는 방식은 피한다. 개인 정보와 회사 정보가 섞이고, 오래된 추정이 정책처럼 재사용될 위험이 크다. 사용자에게는 하나의 두뇌처럼 보이되 내부에서는 범위가 분리된 **federated knowledge fabric**으로 만든다.

### 지식 단위

| 종류 | 의미 | 예시 |
|---|---|---|
| Evidence | 원본 사실과 관측 | 코드, 로그, URL, 테스트 결과 |
| Claim | Evidence에서 도출한 주장 | “이 스크립트는 Bash 3.2에서 실패한다” |
| Decision | 선택과 이유·대안·유효기간 | “Herdr를 런타임 어댑터로 사용” |
| Procedure | 반복 가능한 작업법 | 핸드오프, 윤문, 배포 검증 skill |
| Preference | 사용자 취향과 상호작용 방식 | 한국어, 승인 호출 조건 |
| Work State | 현재 목표·차단·다음 행동 | Work Ledger의 projection |

각 항목은 `source`, `scope`, `owner`, `version`, `verified_at`, `expires_at`, `trust`, `ACL`을 가진다. 관계는 `supports`, `contradicts`, `supersedes`, `applies_to`, `produced_by`, `verified_by`로 표현한다.

### 물리 저장

- 개인/로컬: Markdown 또는 Obsidian vault를 사람이 편집하는 정본으로 쓰고 SQLite가 검색 인덱스와 작업 원장을 가진다.
- 프로젝트: `AGENTS.md`, `CLAUDE.md`, ADR, 계획, skill처럼 Git에 들어가야 할 협업 지식은 저장소가 정본이다.
- 회사 시스템: Dooray·Lark·Notion 등 조직이 정한 시스템을 정본으로 두고 CodeForge는 링크·스냅샷·권한 정보를 인덱싱한다.
- 팀/서버: Postgres와 객체 저장소로 같은 논리 스키마를 확장한다.

검색은 **ACL과 계정 범위를 먼저 필터링**한 뒤 FTS/BM25와 embedding을 결합하고, 필요한 경우에만 관계 그래프를 한두 hop 확장한다. 매 실행에는 원문 전체가 아니라 출처가 달린 작은 Context Envelope를 주입한다.

### 지식 갱신 파이프라인

```text
대화·코드·문서·로그
  → raw evidence
  → 후보 Claim/Decision/Procedure 추출
  → 중복·상충·민감정보 검사
  → 사용자 승인 또는 repo PR/정책 gate
  → canonical knowledge
  → 검색 사용성과 결과 피드백
  → 갱신·폐기·supersede
```

모든 채팅을 자동 기억시키지 않는다. 사용자 수정, 반복 성공, 검증된 근거처럼 승격 조건을 만족한 후보만 정본으로 올린다. Obsidian은 좋은 편집·탐색 UI이고, Lark 글에서 강조한 수집→정리→배포→피드백 순환과 검색 성공률·만족도 같은 KPI는 유용하다. 그러나 특정 SaaS를 제품 정본으로 고정할 이유는 없다.

## 기존 도구를 어떻게 짬뽕할 것인가

| 도구 | 채택 방식 | 보류·거부하는 부분 |
|---|---|---|
| CodeForge | Core, 정책 팩, skill, adapter SDK의 제품 기반 | 현재 결함을 고치기 전에 기능을 계속 쌓지 않음 |
| ForgeGlow | Work/Attention/Evidence의 읽기 전용 projection | 상태를 직접 소유하거나 임의로 완료 처리하지 않음 |
| Herdr | 로컬 PTY·세션·워크트리 실행 어댑터 | 제품의 Work/KB 정본으로 삼지 않음, 초기 hard fork 금지 |
| OpenHands Agent Canvas | 선택형 self-hosted 실행 화면과 ACP runtime adapter | 전체 제품 fork, Work·Evidence 정본 소유 |
| Hermes | 모바일·메신저·cron·원격 위임 게이트웨이 | 기억·라우팅을 Core 정본으로 삼지 않음 |
| OMP | 다중 공급자·로컬 모델을 쓰는 runner adapter | 전체 시스템의 기본 전제나 정책 소유자로 고정하지 않음 |
| Qwen Code | 저비용 독립 실행·교차검증·ACP/daemon 후보 | OMP와 겹치는 기능을 동시에 상시 운영하지 않음 |
| Claude/Codex | 고난도 구현·검토 runner | 대화 세션을 Work 정본으로 쓰지 않음 |
| ChatGPT dot | OpenAI 안에서의 선택적 진입 UI/MCP client | 멀티벤더 제품의 중심으로 삼지 않음 |
| 로컬/GLM 계열 | 민감도·비용·반복 작업용 runner | 품질이 검증되지 않은 작업을 자동 승격하지 않음 |

외부 프로젝트들은 MIT 또는 Apache-2.0 계열이라 조합·수정·상용화 여지가 크지만, 라이선스 공지와 변경 고지는 지켜야 한다. 기능이 필요하다는 이유만으로 fork하지 않는다. 먼저 공개 API·CLI·Python library를 어댑터로 감싸고, upstream 유지보수가 불가능하거나 핵심 계약을 반복해서 깨뜨릴 때만 작은 범위의 port를 검토한다.

## Paperthin 적용안

Paperthin은 실행 엔진이 아니라 22개 정도의 이식 가능한 작업 skill 모음이다. 구조가 단순하고 MIT라 참고하기 좋지만, 저장소의 검사는 frontmatter·링크·카탈로그 무결성 중심이다. 작업 속도나 비용을 낮춘다는 통제 실험 근거는 확인되지 않았다. 특히 `macrothink`, `prism`, `re0-loop`를 항상 실행하면 모델 호출과 지연이 늘 수 있다.

따라서 전체 설치와 자동 symlink 갱신 대신 특정 commit을 고정하고 다음 패턴만 CodeForge식으로 이식한다.

- `modelchk` → 라우팅 결정 전에 쓰는 **조언자**. 실제 모델 전환은 Router만 수행한다.
- `hate` → 큰 설계·출시에서 가장 강한 반대 하나와 가장 싼 반증 실험을 찾는 gate.
- `prism` → 실패 비용이 큰 변경에서만 여러 독립 관점을 쓰는 고비용 review recipe.
- `re0-memo` → 실행 결과에서 Evidence 기반 학습 후보를 추출하는 worker.
- `nba` → Attention Queue에서 사용자가 지금 할 한 행동을 고른다.
- `ssotize` → KB 중복·상충·정본 승격 절차.
- `sip` → 변경 유형별 완료 검증 recipe.

이식된 skill에는 `upstream.yaml`로 원본 URL, commit, license, 변경점을 기록한다. upstream 갱신은 자동 반영하지 않고 diff·테스트·평가 후 PR로 받는다.

## 모델·계정·비용 라우팅

모델명에 업무를 박아 두지 않는다. Router는 작업을 먼저 capability와 risk로 분류한다.

1. `cheap`: 요약, 분류, 로그 구조화, 후보 검색. 로컬 4070 Super 또는 저가 API/GLM 계열 우선.
2. `standard`: 일반 구현, 문서, 테스트 수정. Codex/Claude/Qwen/OMP profile 중 검증된 경로.
3. `frontier`: 아키텍처, 난해한 디버깅, 보안·마이그레이션, 최종 critic.
4. `independent_review`: 원 실행과 다른 공급자·모델 계열로 교차검증.

계정 비밀은 CodeForge DB에 넣지 않는다. `account_profile_id`, 허용 데이터 범위, 실행 가능한 adapter, 예산 정책만 기록하고 credential은 OS keychain·도구별 격리 프로필·회사 승인 저장소가 소유한다. 회사 Work가 개인 계정이나 개인 KB로 넘어가는 경로는 기본 거부한다.

RTX 4070 Super는 작은·중간 규모의 양자화 모델을 반복 분류, 로그 요약, embedding, 저위험 초안, 후보 평가에 활용할 수 있다. 실제 VRAM·RAM·OS를 확인하기 전에는 특정 모델 크기나 처리량을 제품 계약으로 고정하지 않는다. 고난도 코딩 품질이 필요한 경로는 유료 frontier 모델과 혼합한다.

## Prompt/Eval/GEPA 학습 루프

실시간 로그 수집은 프롬프트를 바로 덮어쓰는 자동개선이 아니라 **측정과 후보 생성**에 사용한다.

수집 항목은 task type, model/runner, context refs, cost, duration, 사람 개입 횟수, 사용자 수정, 테스트·readback, 재작업 여부다. 원문 로그는 계정·프로젝트 범위별로 격리하고, 학습용 데이터는 민감정보 제거와 승인을 거친다.

```text
실행 로그 → task별 사례 정규화 → 실패/수정 원인 라벨
         → prompt/skill 후보 생성 → train/validation/holdout 평가
         → 비용·길이·회수 제한 → 사람이 보는 PR
         → 일부 profile에 canary → 유지/rollback
```

최소 30개 이상의 비교 가능한 사례, 분리된 holdout, 반복 가능한 scorer가 생기기 전에는 GEPA식 최적화를 돌리지 않는다. active skill을 자동 수정하지 않으며, 개선 결과는 항상 버전이 있는 후보 PR이다. Hermes self-evolution 프로젝트의 DSPy+GEPA 구조는 참고할 만하지만 현재는 skill 단계 중심의 초기 구현이고 issue/PR에서 end-to-end 신뢰성 문제도 보여 제품 핵심 의존성으로 두지 않는다.

중요한 지표는 토큰 수가 아니라 다음이다.

- 검증 완료 1건당 비용과 소요 시간
- 검증 완료 1건당 사용자의 attention minutes
- 승인 외 인간 개입 횟수와 재작업률
- 세션 전환 뒤 맥락 복구 시간
- 출처가 있는 KB hit가 실제로 도움 된 비율
- 회사·개인 데이터 경계 위반 0건

## 배포 형태와 사업 확장

같은 Core를 세 가지 형태로 제공한다.

| 제품 | 구성 | 수익화 포인트 |
|---|---|---|
| Solo Local | SQLite, local socket, CLI/MCP, ForgeGlow, 로컬 runner | 오픈소스 진입과 개인 신뢰 확보 |
| Team Self-hosted | Postgres, 공유 Work/KB, RBAC, audit, policy pack | 좌석·지원·관리 기능 |
| Managed Cloud | 호스팅 control plane, 원격 runner, SSO, 사용량·비용 분석 | 구독·사용량 과금·기업 운영 |

오픈소스 차별점은 “여러 모델을 한 채팅에서 쓴다”가 아니다. **에이전트·모델·기기를 바꿔도 작업, 정책, 지식, 완료 증거가 이어지고 사람은 결정할 때만 호출되는 것**이다.

회사 전용 harness와 비공개 룰은 공개 CodeForge에 합치지 않는다. 공개 Core 위에 별도 policy pack과 adapter로 연결한다. 현재 회사 harness-kit의 공통 실행·상태·결과 계약도 이 방식으로 접목할 수 있지만, 그 저장소의 정책과 업무 데이터가 개인 제품 KB로 복제되어서는 안 된다.

## 현실적인 구현 순서

### Phase 0 — 기반 정리

- 현재 CodeForge의 macOS Bash 3.2 quality gate 오류, ESLint exit 2 오판, concurrent event temp-file 충돌을 먼저 해결한다.
- dirty 작업과 미구현 로드맵을 실제 release 상태와 분리한다.
- Work/Event/Receipt/Policy 계약을 문서와 contract test로 고정한다.

### Phase 1 — 최소 Control Plane

- SQLite WAL Work Ledger와 reducer, local socket/CLI/MCP를 구현한다.
- 직접 프로세스 runner 하나와 Claude 또는 Codex adapter 하나만 연결한다.
- `submit`, `status`, `attention`, `approve`, `receipt`, `resume`의 수직 흐름을 완성한다.
- ForgeGlow가 읽는 두 번째 consumer가 생긴 뒤 append-only event를 켠다.

### Phase 2 — 지식과 정책

- 개인/회사 두 scope의 격리, 출처가 있는 Context Envelope, Obsidian/Git authoring을 넣는다.
- 저장소 AGENTS/CLAUDE 룰을 Policy Snapshot으로 캡처한다.
- 자동 기억은 후보 상태까지만 허용한다.

### Phase 3 — 교체 가능성 증명

- Herdr runtime adapter와 OMP 또는 Qwen runner 중 하나를 추가한다.
- 같은 Work가 두 runner에서 같은 Envelope/Receipt를 지키는지 contract test한다.
- 로컬 모델은 분류·요약·평가부터 연결한다.

### Phase 4 — 관제 경험

- ForgeGlow를 Work/Attention/Evidence 중심으로 개편한다.
- Hermes 또는 공식 Slack/Discord adapter 하나를 붙여 모바일 승인·완료 알림을 제공한다.
- pane 목록이 아니라 “지금 내가 결정할 것”을 첫 화면에 둔다.

### Phase 5 — 평가와 학습

- Paperthin 선별 recipe와 고비용 review gate를 추가한다.
- 충분한 사례가 쌓인 뒤 GEPA 후보 생성과 canary를 시작한다.
- 모델·prompt 변경 전후를 verified completion 기준으로 비교한다.

### Phase 6 — 팀 제품

- Postgres, multi-tenant RBAC, audit, SSO, remote runner, policy marketplace를 추가한다.
- local-first Core와 동일한 adapter contract를 유지한다.

## 가장 위험한 반론과 가장 싼 검증

가장 강한 반론은 명확하다. **이 시스템이 세션을 관리하려다 또 하나의 복잡한 세션이 되어, 사용자의 주의와 유지보수 비용을 오히려 늘릴 수 있다.** 기능이 많거나 UI가 멋진 것으로는 반박할 수 없다.

가장 싼 검증은 실제 업무 10건으로 하는 A/B다.

- A: 지금의 Herdr + 수동 메인 세션 + 핸드오프 방식
- B: Phase 1의 Work Ledger + Attention Queue + Receipt 방식
- 기록: verified completion 여부, attention minutes, 세션 전환 횟수, 재작업, 비용
- 제안 중단 기준: B가 완료율을 떨어뜨리거나 attention minutes를 의미 있게 줄이지 못하면 범위를 축소한다.

초기 목표로 attention minutes 30% 절감을 둘 수 있지만 이는 현재 증거가 아니라 검증용 가설이다.

## 자기 토론 요약

- 주제: 외부 도구 조합을 제품 중심으로 둘 것인가, CodeForge가 정본을 소유할 것인가
- 모드: self-debate, 3라운드

| 입장 | 가장 강한 주장 |
|---|---|
| A — Hermes+Herdr+OMP 조립 | 이미 있는 세션·메신저·모델 라우팅을 써서 가장 빨리 개인 효용을 확인할 수 있다. 새 플랫폼을 먼저 만들면 영원히 제품을 못 쓸 수 있다. |
| B — CodeForge Core+adapter | 장기 제품은 작업·정책·지식·검증을 직접 소유해야 한다. 외부 도구 상태를 정본으로 삼으면 교체 가능성, 보안 경계, 사업 차별성이 사라진다. |

1라운드에서는 A가 시간과 기능 폭에서 이겼다. 2라운드에서는 여러 도구가 기억·라우팅·상태를 중복 소유하는 문제가 드러나 B가 이겼다. 3라운드에서는 “기능을 재구현하지 말고 계약만 소유한다”는 절충안이 가장 강했다.

최종 판정은 **B를 제품 구조로 채택하고 A를 adapter 기반 프로토타입 재료로 사용**하는 것이다. 즉 CodeForge는 얇지만 단단한 kernel을 만들고, Herdr·Hermes·OMP는 필요할 때 빌려 쓴다.

## 당장 결정된 것과 아직 결정하지 않을 것

결정된 것:

- CodeForge Core가 정본이고 외부 런타임은 adapter다.
- ForgeGlow는 읽기 중심 관제·Attention UI다.
- KB는 논리적으로 하나지만 개인/회사/프로젝트 scope와 ACL로 격리한다.
- Paperthin은 선별 port하고 GEPA는 평가 gate 뒤에서만 쓴다.
- 판매용 첫 쐐기는 범용 대시보드가 아니라 저장소 정책을 지키는 Evidence Gate다.
- 최초 고객은 여러 AI 코딩 세션을 쓰는 개인 개발자와 소규모 팀이다.

구현 실증 뒤 결정할 것:

- Herdr를 기본 runtime adapter로 둘지 direct process를 기본으로 둘지
- OMP와 Qwen 중 첫 다중 모델 runner
- Hermes를 메시징 gateway로 포함할지 공식 Slack/Discord adapter를 직접 둘지
- 오픈소스 범위와 상용 라이선스 경계
- 최종 제품명과 hosted architecture

## 근거와 한계

- CodeForge 로컬 설계 원칙과 미구현 continuity proposal, event contract를 확인했다. proposal과 SHADOW spec은 현재 동작 사실이 아니라 설계 자산이다.
- Paperthin은 2026-10-14 기준 commit `7d5dc6235990230e45a24a25c527d81701da5458`을 검토했다. 생산성 주장은 통제 실험으로 검증되지 않았다.
- 외부 프로젝트의 기능과 라이선스는 공식 저장소·공식 문서를 우선했다. 실제 Herdr 연동 안정성, 로컬 모델 처리량, 계정 전환 안전성은 별도 prototype에서 검증해야 한다.
- Lark 글은 KB 생명주기와 KPI 아이디어의 참고 자료이며 독립적인 기술 검증 자료는 아니다.
