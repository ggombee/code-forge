## 결론

하네스킷 Autopilot은 사용자의 소유 자산으로 계산하지 않는다. 범용 CodeForge의 기반이나 의존성으로도 채택하지 않는다. 다만 **큐가 사라지거나 상태를 못 읽은 상황을 완료로 오판하지 않는 법**, **실행·대기·검증을 서로 다른 상태로 다루는 법**을 실제 결함과 회귀 테스트로 남긴 참고 구현으로는 가치가 있다.

야간 실행기는 세 요소를 조립하되 각각의 역할을 제한한다.

1. **CodeForge `/start`**는 자유 텍스트·티켓·문서를 실행 가능한 `WorkSpec`으로 만드는 작업 컴파일러다.
2. **Codex Goal**은 한 에이전트 스레드가 증거가 생길 때까지 계속 작업하게 하는 시도 단위 계약이다.
3. **Autopilot에서 배운 규칙**은 제품이 직접 소유하는 durable sequencer와 fail-closed 상태 전이에 다시 구현한다.

어느 하나도 전체 관제 시스템의 정본이 아니다. 사용자 의도, 권한, 예산, realm, 검증 결과의 정본은 CodeForge 신뢰 커널과 로컬 원장이다.

## 감사 범위와 증거

### Harness-kit Autopilot

- 검토 대상: 비공개 harness-kit의 Autopilot 참고 구현
- 공개 문서에는 저장소 경로와 커밋 식별자를 싣지 않는다. 코드와 구현 세부도 가져오지 않는다.
- 직접 실행한 회귀 테스트:
  - `bash core/scripts/autopilot-start.test.sh` → 107 pass, 0 fail
  - `bash core/scripts/autopilot-next.test.sh` → 157 pass, 0 fail
  - `bash core/scripts/autopilot-gate.test.sh` → 36 pass, 0 fail
  - 합계 300 pass, 0 fail
- 테스트 뒤 checkout은 clean이었다.

이 결과는 **현재 checkout에서 큐 파싱·상태 판정·gate의 범위가 회귀 테스트를 통과했다**는 증거다. 다음을 증명하지는 않는다.

- 임의의 저장소와 임의의 agent에서 밤새 완주한다.
- 회사·개인 계정과 데이터 realm을 안전하게 분리한다.
- 여러 provider, 비용 원장, GPU worker를 지원한다.
- 판단 gate가 정확하다.
- 공개 제품에 코드를 재사용할 권리가 있다.

checkout 상위 두 단계에서 `LICENSE`, `COPYING`, `NOTICE`를 찾지 못했다. 사내 원격 저장소의 코드이므로 권리 확인 전에는 공개 CodeForge로 복사하거나 파생 구현하지 않는다. 아래 설계는 일반적인 상태 기계 원칙과 독립 구현만 취한다.

### CodeForge `/start`

- 검토 파일: [`skills/start/SKILL.md`](../../skills/start/SKILL.md)
- 검토 HEAD: `1779c8ac9638c755d341b16e708f7e44aaf15b75`
- 해당 checkout은 기존 미커밋 변경이 있어 읽기만 했다.

유용한 부분은 입력 분석, 저장소 탐색, acceptance 추출, 복잡도 분류, 계획·구현·검증 분리, 실제 명령 실행, 진행 상태 기록이다. 현재 `/start` 전체를 야간 실행기로 쓰기에는 다음 문제가 있다.

- 현재 형태는 모델이 따르는 산문형 skill이며 durable state machine 기능은 없다.
- `--auto`에서 LOW/MEDIUM을 자동 승인하는 규칙이 side effect 권한과 섞여 있다.
- `--skip-test`가 있어 검증된 완료와 단순 실행을 혼동할 수 있다.
- checkpoint와 `progress.md`는 좋은 사용자 projection이지만 lease·idempotency·동시성 정본은 아니다.
- commit·push·PR 생성 단계가 범용 야간 정책보다 넓다.
- LOW/MEDIUM/HIGH와 모델 routing은 권고이며 기계적으로 강제된 정책이 아니다.

따라서 `/start`는 없애지 않고 **Work Compiler**로 좁힌다. 직접 commit·push까지 밀어붙이는 대신, 실행 전에 불변 `WorkSpec`, `PolicySnapshot`, `VerificationRecipe`를 만든다.

### Codex Goal

OpenAI 공식 문서 기준으로 Goal은 objective, lifecycle, budget, progress를 보존하는 **thread-scoped completion contract**다. 완료는 파일·테스트·로그·benchmark 같은 증거로 판정하며, budget 소진은 완료가 아니다. 자동 continuation도 turn 종료, idle, 대기 중인 사용자 입력 없음 같은 안전한 시점에만 일어나고, 도구 호출이 없는 continuation 뒤에는 반복을 억제한다.

이 특성은 한 번의 agent 시도를 지속하는 데 적합하다. 프로젝트 전체 백로그, 다른 agent의 상태, 조직 권한, 전역 예산의 정본으로 쓰면 안 된다.

공식 근거: https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex

## 하네스킷에서 가져올 것과 버릴 것

| 항목 | 판정 | 이유와 적용 방식 |
|---|---|---|
| `RUNNING`, `PAUSED`, `STALLED`, `UNKNOWN`, `BLOCKED`, `AWAITING_CI`, `UNGATED` 구분 | 개념 채택 | 보이지 않는 상태, 대기, 실패를 모두 완료와 분리한다. 제품 schema로 독립 구현한다. |
| 큐가 없거나 깨졌거나 shape가 틀리면 중단 | 채택 | unreadable을 empty로 해석하지 않는 핵심 fail-closed 규칙이다. |
| 이전 run의 state를 새 run에 자동 채택하지 않음 | 채택 | 동일 문서·브랜치라도 `run_id`와 생성 시점이 다르면 다른 실행이다. |
| archive가 실패하면 다음 작업을 시작하지 않음 | 채택 | morning review에 필요한 유일 증거가 사라지는 것을 막는다. |
| CI pending과 fail 분리 | 채택 | 기다려야 할 때와 고쳐야 할 때를 구분한다. |
| retry 상한과 사유 기록 | 채택 | 같은 실패를 밤새 반복하지 않는다. |
| wake와 completion contract 분리 | 채택 | cron/loop는 깨우기만 하고, 완료 의미나 권한을 갖지 않는다. |
| 읽기 전용 review 병렬화, write/fix 직렬화 | 조건부 채택 | adapter capability와 worktree 격리가 증명된 작업만 병렬화한다. |
| 종료를 큐 소진으로만 판정 | 수정 | 제품은 큐 소진과 야간 시간창, 비용, token, 전력, deadline을 모두 확인한다. |
| 모든 작업을 stacked PR로 생성 | 수정 | repo policy가 허용할 때만 `draft-pr`을 선택한다. 기본 산출물은 patch/local commit이다. |
| Goal을 거는 행위가 실행 권한 | 폐기 | 지속 의도와 side effect 권한은 다르다. 별도 `RunPolicy`가 반드시 있어야 한다. |
| `ALL_DONE`을 최종 완료 조건으로 사용 | 폐기 | 큐 소진과 목표 달성을 혼동한다. gate fail을 기록한 뒤에도 큐가 비면 `ALL_DONE`이 될 수 있다. |
| GitHub·마일스톤 표·develop-pipeline 결합 | 폐기 | CodeForge core는 host-neutral schema와 adapter를 사용한다. |
| 셸·Markdown 표 파싱 구현을 이식 | 폐기 | 권리와 portability 문제가 있고 durable ledger에 부적합하다. |
| `gh` 부재 시 `unavailable` 기록 후 주행 종료 가능 | 수정 | 기록 자체는 유지하되 결과는 `REVIEW_REQUIRED`이며 `VERIFIED`가 될 수 없다. |

핵심 명칭도 바꾼다.

- `ALL_DONE` → `QUEUE_DRAINED`: 처리할 큐 항목이 더 없다는 뜻만 가진다.
- run outcome → `VERIFIED | REVIEW_REQUIRED | PARTIAL | FAILED | BLOCKED`
- queue 상태와 run outcome을 결합해 사용자에게 보여 주되, 내부 필드는 분리한다.

예를 들어 `QUEUE_DRAINED + PARTIAL`은 “밤에 할 수 있는 시도는 모두 했지만 일부만 성공”이다. 이를 `DONE`으로 축약하지 않는다.

## 최종 야간 실행 구조

```text
Ticket / Markdown / Chat / Backlog
                 │
        CodeForge Work Compiler
  repo rules · realm · risk · AC · language
                 │
  WorkSpec + PolicySnapshot + VerificationRecipe
             + LanguageProfile reference
                 │
          Trust Kernel + Ledger
  authority · budget · queue · lease · receipt
                 │
           Durable Sequencer
  ready → leased → running → verifying → outcome
       │              │              │
       │       Agent Session Adapter │
       │    Codex Goal / Claude skill│
       │              ├─ decision needed ─→ Decision Concierge
       │              │                     pane/thread/mobile
       │              │                     └─ DecisionReceipt
  OS scheduler ───── wake only ──────┘
  launchd/systemd/cron/Hermes
                 │
    Morning Brief / ForgeGlow / Inbox
```

### 1. Work Compiler: `/start`의 발전 방향

사용자는 매번 `/goal` 문구와 모델을 직접 고르지 않는다. 채팅, 이슈, 핸드오프 문서 중 하나를 넣으면 compiler가 다음을 만든다.

```yaml
work_spec:
  objective: "관찰 가능한 최종 상태"
  base_ref: "고정 SHA"
  scope: ["허용 경로"]
  acceptance: ["검사 가능한 조건"]
  realm: personal | company | customer | public
  risk: low | medium | high | prohibited
  side_effects_requested: [worktree_write, local_commit]
  blocked_stop: "사람에게 물어야 하는 조건"
  decision_policy: "의존 노드만 대기, 독립 노드는 계속"
  language_profile_ref: "모델·작업 평가로 고른 버전"
  output_locale: "ko-KR"
verification_recipe:
  commands: ["repo가 정한 실제 검사"]
  required_evidence: [diff, exit_code, test_log]
policy_snapshot:
  sources: [AGENTS.md, CLAUDE.md, repo policy]
  digest: "..."
```

자유 텍스트의 모호함, 서로 충돌하는 repo rule, 실행할 검증 명령 부재가 발견되면 `ELIGIBLE`로 넘기지 않는다. compiler가 출력한 모델 tier와 `LanguageProfile`은 추천일 뿐이며 router가 realm·예산·capability와 해당 모델의 평가 결과를 다시 검사한다.

### 언어 처리: 지시문과 사용자 문서를 분리

Work Compiler는 출처의 원래 언어와 식별자를 보존한 뒤 현재 작업에 필요한 지시, 제약, 예시, 출력 계약만 에이전트용 패키지로 만든다. 한국어판과 영어판 전체를 함께 넣지 않는다. 모델과 작업 유형에 맞는 표현은 상위 설계의 `LanguageProfile` 평가 결과로 고른다.

에이전트가 실행할 지시문과 사람이 읽을 결과물은 별도로 처리한다. 한국어 결과는 윤문과 보호 항목 검사를 거치고, 영어 결과는 한국어 문장 구조를 옮기지 않고 영어 독자의 목적에 맞게 작성한다. 이 단계는 사실이나 정책을 바꾸지 않으며 `output_locale`에 따라 표현만 조정한다.

`LanguageProfile`은 기능 성공률, tool argument 정확도, 정책 위반, 사람의 수정 시간, token·비용, latency를 함께 기록한다. 모델 revision이 바뀌면 같은 평가 세트로 다시 확인한다. 영어 강제와 평가 없는 자동 번역은 허용하지 않는다.

### 2. Goal Contract: agent 한 세션의 지속성

하나의 `WorkAttempt`마다 adapter가 해당 host의 지속 장치를 생성한다.

- Codex: `WorkSpec`과 선택된 에이전트용 패키지에서 thread-local Goal을 생성한다.
- Claude: `/start`의 분석 결과, handoff와 선택된 에이전트용 패키지를 attempt prompt로 전달한다.
- Goal을 지원하지 않는 agent: supervisor가 turn 결과를 받아 다음 turn을 명시적으로 시작한다.

Goal에는 objective, evidence, constraints, boundaries, iteration policy, blocked stop을 넣는다. product budget과 agent Goal budget은 별도다. Goal budget이 끝나면 `ATTEMPT_BUDGET_LIMITED`이며 작업 완료가 아니다.

스레드 Goal은 해당 시도의 context를 유지하는 수단이다. 전역 work item을 완료하거나 다른 session을 예약할 권한은 없다.

### 3. Durable Sequencer: Autopilot 교훈의 독립 구현

최소 상태 전이:

```text
DRAFTED → COMPILED → ELIGIBLE → QUEUED → LEASED
       → PREPARED → RUNNING → VERIFYING
       ├→ RETRYABLE → QUEUED
       ├→ WAITING_DECISION
       ├→ REVIEW_REQUIRED
       ├→ VERIFIED
       ├→ FAILED
       └→ BLOCKED
```

추가 상태 규칙:

- `UNKNOWN` 또는 ledger read error는 새 작업을 시작하지 않는 `INDETERMINATE`다.
- lease에는 owner, TTL, heartbeat, fencing token이 있다. 만료된 worker의 늦은 결과는 채택하지 않는다.
- 모든 전이는 `run_id`, `attempt_id`, `idempotency_key`, 이전 state version을 확인한다.
- retry는 동일 failure signature 두 번, 작업당 최대 3회, 모델 tier 상향 최대 2회에서 중단한다.
- archive/receipt commit이 성공하기 전에는 다음 작업을 lease하지 않는다.
- wake trigger는 `tick()`만 호출한다. 권한·완료·retry 결정을 바꾸지 못한다.
- queue가 소진되면 `QUEUE_DRAINED`를 기록하고 각 work outcome을 집계한다.

### 3A. Decision Concierge: 메인 coordinator의 비동기 판단 창구

worker가 판단이 필요한 지점을 만나면 현재 attempt 전체를 대화 입력 상태로 붙잡아 두지 않는다. sequencer는 결정에 종속된 node와 descendants만 `WAITING_DECISION`으로 전환하고 lease를 안전하게 정리한다. coordinator event loop와 다른 runnable node는 계속 실행한다.

realm별 지속형 Decision Concierge가 `DecisionRequest`를 별도 Herdr pane, 웹 thread 또는 모바일 채널로 보여 준다. Herdr adapter는 필요하면 요청마다 context capsule만 가진 짧은 세션을 열고, 답변 receipt가 반영되면 해당 세션을 닫는다. 요청에는 `decision_id`, `work_id`, `attempt_id`, `spec_digest`, 선택지·권장안·영향, blocked node IDs, expiry가 들어간다. 사용자의 답은 versioned `DecisionReceipt`로 원장에 기록되고 event로 메인 coordinator에 전달된다. 메인 세션에 자연어를 다시 복사하는 방식은 복구·감사 경로로 쓰지 않는다.

Concierge는 질문 전달과 답변 구조화만 담당한다. 작업 수정, 권한 확대, provider 변경은 할 수 없다. 여러 채널에서 답이 오면 첫 유효 receipt만 채택하고, stale version·권한 없는 응답·만료 응답은 거부한다. 답이 없을 때의 기본값은 no-action이다. 비긴급 질문은 묶고, 현재 critical path를 막는 요청만 즉시 알린다.

### 4. Trust Kernel: 실행 권한은 Goal과 분리

야간 실행 전에 사용자가 승인한 `RunPolicy`가 있어야 한다.

```yaml
run_policy:
  realm: personal
  repo_ids: ["..."]
  allowed_side_effects: [read, worktree_write, local_commit]
  denied_side_effects: [push, merge, deploy, external_message, secret_change]
  valid_from: "..."
  expires_at: "..."
  max_cost: "..."
  max_duration: "..."
  max_concurrency: 2
  model_tiers: [T0, T2, T3]
```

adapter에는 이 정책에서 줄인 최소 capability만 넘긴다. push·draft PR이 필요하면 repo policy와 사용자의 별도 승인 범위가 둘 다 있어야 한다. `AGENTS.md`, 회사 guard, 계정 realm은 실행기 앞의 강제 정책으로 적용한다. prompt에만 맡기지 않는다.

### 5. 검증과 아침 승인함

agent의 “완료했습니다”는 상태 전이 입력일 뿐이다. 신뢰 커널이 base SHA, diff, policy digest, 실제 검사 결과를 묶어 독립적으로 판정한다.

아침 화면은 다음 순서로 정렬한다.

1. `WAITING_DECISION`: 별도 Concierge에서 답이 오면 해당 node만 재개하는 질문
2. `ACTION_REQUIRED`: 권한·예산·모델 승격 요청
3. `REVIEW_REQUIRED`: 실행은 끝났으나 증거 부족 또는 외부 gate 미확인
4. `VERIFIED`: acceptance와 필수 검사를 통과한 후보
5. `FAILED/BLOCKED`: 실패 서명, 시도한 경로, 다음 해제 조건

최상의 자동 결과도 merge나 배포 완료가 아니다. `VERIFIED`는 검토 가능한 patch·commit·선택적 PR과 receipt가 준비됐다는 뜻이다.

## 모델·계정·24시간 실행 규칙

- local Qwen/GLM 등은 eval을 통과한 task class에만 사용한다.
- prompt language도 model·task별 eval을 통과한 `LanguageProfile`만 사용한다. 결과가 없으면 출처 언어를 유지한다.
- 같은 시도 중 provider를 몰래 바꾸지 않는다. fallback은 새 `Attempt`로 기록하고 context envelope를 다시 만든다.
- 회사 작업은 회사 realm에서 허용한 계정·장비·endpoint만 사용한다. 개인 GPU 사용은 회사 정책이 명시적으로 허용할 때만 가능하다.
- 무료 provider는 가격이 0이라는 이유만으로 선택하지 않는다. quota, data policy, tool capability, context, 관측 가능성이 unknown이면 unattended 대상에서 제외한다.
- 사용량·가격을 확인할 수 없으면 hard monetary budget 대신 요청 수·token·wall-clock 상한을 함께 건다.
- 낮에는 Herdr/ForgeGlow가 session과 상태를 보여 줄 수 있고, 밤에는 OS scheduler나 Hermes가 daemon을 깨울 수 있다. 어느 것도 판정 정본이 아니다.

## 구현 순서

### P0 — 참고 구현과 분리된 계약

1. `WorkSpec`, `RunPolicy`, `Attempt`, `CheckResult`, `Receipt`, `DecisionRequest`, `DecisionReceipt`, `ActionRequest` schema v0를 고정한다.
2. `QUEUE_DRAINED`와 work outcome을 다른 필드로 만든다.
3. 현재 `/start`의 intake·repo grounding을 compiler prototype으로 추출한다.
4. Autopilot 코드를 가져오지 않고 edge case를 black-box 요구사항과 새 테스트로 다시 작성한다.
5. `LanguageProfile`, `output_locale`, 기준 원문 revision을 schema에 넣고 언어별 비교 평가 harness를 만든다.

### P1 — 검증기 우선

1. patch/PR을 base SHA와 acceptance에 고정해 검증한다.
2. `pass | fail | error | skipped | unavailable`을 보존한다.
3. test 삭제·완화·미실행과 policy drift를 탐지한다.
4. receipt를 생성하고 ForgeGlow가 read-only로 읽게 한다.

### P2 — 단일 사용자 야간 runner

1. SQLite WAL ledger, lease, heartbeat, recovery, idempotency를 구현한다.
2. isolated worktree에서 patch/local commit까지만 허용한다.
3. Codex Goal adapter와 Claude adapter 각 1개를 붙인다.
4. launchd/systemd trigger, realm별 Decision Concierge와 `output_locale`을 따르는 static morning brief를 붙인다.
5. 한국어 윤문과 영어 자연 집필 renderer를 분리하고 원문의 사실·제약 보존을 검사한다.
6. 개인 저장소의 작은 백로그 50건으로 승인률, 검토 시간, 실패 반복, 비용을 측정한다.

### P3 — 외부 사용자와 팀 확장

1. adapter conformance suite와 capability negotiation을 공개한다.
2. 공개 문서는 자연스러운 영어 `README.md`와 별도로 집필한 한국어 `README.ko.md`에서 시작한다.
3. repo policy pack, realm, provider account binding을 제품 UI에 노출한다.
4. 두 번째 사용자부터 shared approval·org policy·audit를 Hub에 둔다.
5. managed runner는 local runner의 완주율과 수요가 확인된 뒤 추가한다.

## 구현 수락 기준

야간 runner alpha는 다음을 모두 만족해야 한다.

- daemon 재시작 뒤 동일 work를 중복 실행하지 않는다.
- 깨진 queue, 없는 state, 만료된 lease를 완료로 판정하지 않는다.
- `QUEUE_DRAINED`가 `VERIFIED`로 자동 승격되지 않는다.
- Goal 생성만으로 push·PR·merge·deploy 권한이 생기지 않는다.
- budget 소진, 도구 무호출, CI pending, CI failure가 서로 다른 상태로 남는다.
- 다른 realm의 credential, prompt, code, embedding을 router가 조회하지 못한다.
- 한·영 전체 사본을 같은 attempt에 기본으로 넣지 않으며 선택된 `LanguageProfile`과 기준 revision이 receipt에 남는다.
- 한국어 결과는 윤문·보호 항목 검사를 통과하고 영어 결과는 영어 독자를 위한 편집 기준을 통과한다.
- 실제 repo 검증 명령이 없거나 실행 불가하면 `VERIFIED`가 나오지 않는다.
- 모든 verdict에 base SHA, policy digest, model/provider, 비용·시간, evidence ref가 남는다.
- 같은 failure signature가 두 번 반복되면 자동 retry를 중단한다.
- 결정이 필요한 node만 `WAITING_DECISION`이 되고 coordinator와 독립 node는 계속 실행한다.
- `DecisionReceipt`가 request ID·spec version·허용 응답자와 일치하지 않으면 재개하지 않는다.
- 결정 요청이 만료되거나 답이 없으면 권한 확대나 외부 side effect 없이 안전하게 대기·종료한다.
- morning brief에서 사용자가 3분 안에 승인·질문 답변·폐기 결정을 할 수 있다.

## 최종 판정

하네스킷 Autopilot은 **좋다고 믿고 도입할 도구도, 나쁘다고 버릴 자료도 아니다.** 현재 범위의 상태 판정에는 테스트와 실주행 결함 이력이 있어 참고 가치가 높지만, 범용성·권한·realm·비용·라이선스 근거가 없다.

CodeForge는 그 구현을 종속성으로 삼지 않는다. `/start`의 작업 이해 능력, Codex Goal의 스레드 지속성, Autopilot이 드러낸 실패 패턴을 조합하되, 사용자가 소유하는 것은 독립 schema·신뢰 커널·원장·검증기다. 이 구분이 있어야 개인용 “나의 복제”에서 시작해 다른 개발자와 소규모 팀이 쓰는 공개 제품으로 확장할 수 있다.
