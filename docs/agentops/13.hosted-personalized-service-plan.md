# 완전관리형 개인화 에이전트 서비스 상세 계획

2026-10-21 · 설계 제안 반영 · 구현·출시·보안 인증 전

실행 순서의 정본은 [통합 개선 계획](../../plan/code-forge-final-improvement-plan-2026-10-18.md)이다. 이 문서는 최신 사용자 요구를 구현 가능한 조건으로 풀어 쓴다. [HTML 검토 자료](./codeforge-service-design-review-2026-10-21.html)의 그림·비용 계산기·출처를 함께 참고한다. HTML에 남은 ‘정본 미반영’ 등의 문구는 작성 당시 상태이며, 이 개정으로 아래 항목을 정본에 반영했다. 이번 개정에는 Claude 검수가 없다.

## 1. 제품 방향과 저장소

제품은 사용자의 승인된 판단 기준을 활용하면서 생성된 코드의 품질·검증·권한을 챙기는 개인화 계층을 지향한다. 개인화의 효과는 설명의 그럴듯함보다 실제 작업 결과와 사용자 교정 감소로 입증한다. 경쟁 우위와 유료 수요는 아직 가설이다.

CodeForge는 기존 이름·사용자·무료 독립 사용을 유지한다. 서버 가입을 강제하거나 기존 유용한 기능을 제거해 유료 전환을 유도하지 않는다. 관리형 제품은 공개 CodeForge artifact를 버전 고정해 소비한다. G0b에서 패키징·독립 설치·소비자 호환을 시험한 후 별도 제품 저장소를 결정하며, 새 core 저장소부터 만들 필요는 없다. 현재 작업은 저장소 생성·이름 변경·라이선스 변경을 포함하지 않는다.

Atelier는 작업실이라는 제품 이름 후보다. Library는 승인된 지식, Workbench는 실행 환경, Inspector는 독립 검증을 설명한다. 별도 서비스나 패키지 개수를 뜻하지 않는다. 기존 Blueprint는 원칙·정책, Smith는 정적 agent 컴파일, Bellows는 관찰 이벤트, Anvil은 사용자 접점, Whetstone은 사람의 학습 역할을 유지한다. Assayer의 테스트 작성과 Inspector의 최종 검증은 분리한다. 상표·도메인은 확정하지 않았다.

공개되는 것은 일반 규칙·형식·합성 예시다. 실제 개인 프로필·프롬프트·회사 문서·로그·키는 제품 저장소에도 넣지 않는다. 공개 pack에 회사 사례를 이름만 바꿔 복사하지 않고, 구조적 비밀까지 없는 합성 사례를 사용한다.

## 2. 관리형 첫 사용 경험과 배포

첫 고객 흐름은 가입 → 키·저장소 없는 샘플 작업 → 최소 권한 저장소 연결 → 작업 범위·비용 확인 → 격리 실행 → 독립 검증 → 보호된 preview와 diff → 명시적으로 승인한 PR·반영·배포다. BYOK와 로컬 설치는 선택 사항이다. 샘플도 무제한 익명 실행이 아니라 계정별 제한과 악용 방지를 적용한다.

초기는 제한된 스택과 템플릿만 지원한다. 작업 시 sandbox를 만들고 승인 대기에는 checkpoint 후 중지한다. E2B·Modal 등은 후보이며 자체 VM 군집을 먼저 구축하지 않는다. 공급자의 지역·격리·복구·가격·제한·데이터 처리 조건을 실증해야 한다.

비용과 책임은 세 가지로 나눈다.

| 범위 | 초기 제공 원칙 |
|---|---|
| 에이전트 실행 | 모델 호출과 격리 작업 시간에 상한·사용량 계량 적용 |
| 임시 preview | 인증·만료 TTL·공유 범위·중지/삭제 제공, 기본 공개 금지 |
| 상시 앱 hosting | DB·도메인·트래픽 포함 별도 비용. 초기에는 고객 계정 배포 adapter를 우선 검증 |

제어 서버와 비신뢰 코드 실행 환경을 분리한다. tenant별 저장소·cache·worker 접근을 격리하고, repo 범위가 제한된 설치 토큰과 짧은 수명의 비밀을 사용한다. 운영 배포 자격증명은 준비 worker에 상주시키지 않는다. CPU·메모리·시간·출력·egress·저장량·동시성·비용 상한을 강제한다. 예산을 예약하고 실제 사용량으로 정산하며 계량 지연과 이미 실행 중인 작업 비용도 포함한다. 재시도는 외부 결과 확인과 중복 방지를 통과해야 한다.

관리형 제품은 서버와 허용된 모델 제공자가 코드·프롬프트·메모리를 처리한다. 따라서 ‘로컬에서만 처리’, ‘외부 전송 없음’, ‘서버도 읽지 못하는 종단간 암호화’를 주장하지 않는다. 처리 지역·하위 처리자·보존 기간·지원 인력 접근·삭제 한계를 공개한다. 개인용 웹 인증으로 회사 데이터 접근이 허용되지는 않는다.

## 3. 필요한 맥락만 사용하기

장기 지식베이스를 유지하더라도 모든 세션에 전부 주입하지 않는다. 검색 전에 realm·source ACL·기기·작업 capability를 검사한다. 그 안에서 관련성·최신성·중복·예산에 따라 선택한다. ContextEnvelope에는 목표, 현재 상태, 강제 정책, 관련 승인 선호, 근거, 미해결 질문과 source/revision/digest를 담는다. 추가 조회에도 같은 권한 검사를 적용한다.

도구 결과와 응답용 토큰을 예약하고 낮은 관련성부터 제외한다. 정책·실패·미확인 사항을 압축 과정에서 없애지 않는다. 세션 인계는 결정·미해결 사항·참조를 전달하고 새 세션에서 권한을 다시 검사한다. 오래된 cache나 만료된 권한으로 원문을 복구하지 않는다.

회사 업무의 존재 자체도 기본 비공개다. 개인 세션은 회사 코드·설계·문서·임베딩을 검색할 수 없다. 회사 내부의 승인된 발행자가 별도로 허용한 최소 상태 projection만 외부에 전달한다. 예시 필드는 별칭·거친 상태·관측 시각·만료 시각이며, 필요 없으면 더 줄인다. 프로젝트·고객·작업명은 안전한 필드로 가정하지 않는다.

조직이 공개 대상·기기·TTL·정책 버전을 승인해야 하며 개인의 요청만으로 발행할 수 없다. 요약·임베딩은 원본 분류를 상속하고, LLM 요약만으로 비밀 등급을 낮추지 않는다. projection에는 원문 조회권이나 조직 실행 토큰을 넣지 않는다. 철회 시 cache를 무효화하되 이미 본 내용·스크린샷까지 회수할 수 있다고 약속하지 않는다.

## 4. 프롬프트와 메모리의 개선 루프

긴 사용자 요청은 유용한 근거지만 모든 문장이 영구 선호는 아니다. 일회성 작업 조건·프로젝트 정책·개인 선호를 구분하고, 후보 → 승인 → 개정/철회 상태를 유지한다. 사용자의 침묵이나 에이전트가 만든 위임문을 동의로 취급하지 않는다.

사용자 원문, Herdr 등으로 전달한 위임문, 실제 실행기에 전달된 prompt, runtime/model/tool 버전, 독립 결과, 사용자 교정을 Work/Attempt/parent ID로 연결한다. 작성자·출처·realm·profile/generator/policy digest·비용·동의·보존 기간을 기록한다. 이번 문서 작업에서 실제 로그를 수집하거나 수집기를 활성화하지 않았다.

두 흐름을 분리한다.

1. 메모리 흐름: 근거에서 규칙 후보를 추출하고 사용자 또는 조직의 권한 있는 승인 뒤 적용한다.
2. 생성기 흐름: 승인된 의도·정책·사례를 사용하는 prompt 생성기, 예시 선택, context 선택 전략을 평가하고 개선한다.

GEPA는 텍스트 기반 최적화 후보이며 모델 가중치 튜닝과 다르다. 매 요청마다 최적화하지 않는다. 초기부터 동의·출처·교정 연결을 마련하고, 평가 기반이 갖춰진 뒤 배치로 실행한다. 실제 downstream 작업의 검증 성공·사용자 수정·질문·지연·비용으로 판단한다. 생성기의 문장 품질이나 자기 평가는 최종 기준이 아니다.

train/validation/final holdout은 같은 작업의 재시도·파생 프롬프트가 섞이지 않도록 계보별로 분리하고 프로젝트·시간 일반화를 평가한다. 이전 문서의 30/50건은 수집 이정표일 뿐 보편적인 GEPA 요건이나 자동 승격 기준이 아니다. 작업 유형·위험·독립 평가에 맞는 표본 계획을 먼저 승인한다.

보안·권한·기능 비퇴행은 고정 통과 조건이다. 최적화 대상이 evaluator·정책·권한을 바꾸지 못한다. 후보 → shadow/canary → 승인 버전 → rollback 순서로 배포한다. 사전 허용된 저위험 승격도 범위와 되돌리기 조건을 기록하고 active skill을 무조건 덮어쓰지 않는다.

공통 의도와 모델별 adapter를 나누고 모델·버전·작업 조합별로 평가한다. 지원하지 않는 조합은 차단하거나 미지원으로 표시한다. 모델 변경 시 재평가하며 ‘어떤 모델에서도 항상 최적’이라고 보장하지 않는다.

일시적 작업 처리, 원문 장기 보관, 개인화 학습, 제공자의 데이터 이용은 별도 동의·계약 항목이다. 원문 수집은 기본 최소화하고 선택 동의를 받는다. 삭제는 원문 → 메모리 → 검색 index/eval → 생성기 후보까지 추적한다. 영향을 받은 버전은 철회·재생성하고 백업 삭제 지연 등 한계를 명시한다. 회사·다른 고객의 사례를 개인 또는 공용 학습에 자동 재사용하지 않는다.

## 5. 해킹 위험과 조직·폐쇄망

정보·기억·실행권을 한곳에서 연결하면 공격 표면이 커진다. 최소 context는 노출 범위를 줄일 뿐 안전을 보장하지 않는다. 웹 세션 탈취, 악성 저장소의 prompt injection, 메모리 오염, connector 탈취, cache 혼선, 공급망·관리자·단말 침해를 위협 모델에 넣는다.

동일 인물이라도 개인·조직의 인증·키·권한·저장소를 분리한다. 읽기·외부 전송·실행 권한을 구분하고 작업별 짧은 토큰, 민감 action 추가 인증, 세션/기기 철회, outbound 허용 목록을 적용한다. 2FA만으로 자료 반출이 정당화되지 않는다. Slack·Discord는 기본적으로 내용 없는 알림과 승인된 projection만 제공하고 자연어 질문으로 권한을 확대하지 못한다. 링크·오류·연속 질문·검색 개수에서도 정보가 새지 않는지 검사한다.

조직형은 조직 소유 BYOC 또는 설치형과 내부 IdP·기기 정책을 따른다. 폐쇄망은 모델·tokenizer·런타임·패키지·서명·신뢰 루트·SBOM·라이선스·오프라인 업데이트 묶음을 제공하고 내부 DNS/NTP/인증서·모니터링·백업을 준비한다. license check·telemetry·crash report·모델 다운로드까지 외부 호출이 없는지 시험한다. 장애 시 외부 모델로 자동 fallback하지 않는다. 오프라인 학습과 평가는 승인된 내부 모델만 사용한다. 회사 폰 접근은 조직이 승인한 경로에서만 제공한다.

## 6. 가격·수익 가설과 계약 검토

무료 OSS와 유료 운영 편의를 구분한다. 개인 구독은 기본료 + 제한된 포함 사용량 + 명시적 추가 구매를 권고한다. 팀은 공동 예산·관리 기능, 조직형은 도입·연간 지원을 검토한다. $29/$49/$99는 상품 가설이며 확정 가격이 아니다. 연결 기능만을 가정한 과거 저가 구독안을 관리형 무제한 실행 가격으로 사용하지 않는다.

원가는 모든 모델 호출(생성·추출·검증·재시도), 병렬 worker별 청구 시간 합계, preview·저장·전송·지원·결제 비용을 포함한다. GEPA 평가 비용은 별도 상각하되 일반 호출 비용과 중복 계산하지 않는다. 재사용 예상 횟수 × 검증 완료당 절감액이 평가 비용을 넘는지, 품질 제약을 지키는지 확인한다. 사용자 간 데이터 공유를 전제로 절감을 계산하지 않는다.

HTML의 USD 계산기는 가정 실험이다. 예시의 월 $49, 40작업, 작업당 15분, 전체 모델비 $0.35, 실행비 시간당 $0.23796 등은 조달 견적·시장 수요·수익 보장이 아니다. 실제 공급자 가격·지역·과금 단위·지원 노동·실패율을 유료 파일럿 전에 다시 확인한다. 무제한 요금제를 약속하지 않고 과도 사용 시 명시적 한도·추가 구매·중단을 제공한다.

출시 전에는 공급자 상업 이용 조건, 고객 코드와 생성물 권리, OSS 라이선스 의무, 개인정보 처리·국외 이전·하위 처리자, 삭제·보존, 사고 대응, 구독 해지·환불·재시도 과금, 지원 범위를 실제 관할과 계약에 맞게 검토한다. 개인용 모델 구독 토큰을 모아 서비스하지 않는다. 이 문서는 법률 의견이나 규정 준수 인증이 아니다.

## 7. 반영 추적과 출하 검사

| 최신 요구 | 정본 반영 위치 | 완료에 필요한 증거 |
|---|---|---|
| 기존 OSS 유지·별도 제품 가능성 | §2·G0b | 무가입 독립 설치와 pinned artifact 소비 실험, 책임 ADR |

GH에는 계정 복구·권한 회수·사고 대응 담당과 절차, 제한된 지원 조합, rate limit·악용 대응, 과금 이의 처리도 필요하다. 채굴·스팸·무허가 스캔을 차단한다. sandbox 실행 성공만으로 유료 출시하지 않는다.

권장 순서는 G0a baseline → G0b 계약·패키징·관리형 격리/원가 실험 → G1a/G2 핵심 검증 → GH 관리형 alpha·제한된 유료 파일럿이다. G1b/G3는 별도 멀티호스트·멀티런타임 출시 기준을 유지한다. 초기부터 학습 근거를 동의하에 수집하되 GL 최적화는 평가 준비 후, G4 조직/로컬 연결과 폐쇄망은 그다음이다. 로컬 개발용 실험과 고객에게 설치를 요구하는 제품 경험을 혼동하지 않는다.
