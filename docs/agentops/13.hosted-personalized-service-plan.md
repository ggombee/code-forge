# 개인 어시스턴트 서비스 계획

> 전체 그림은 **[서비스 한눈에 보기](./README.md)**, 구현 순서와 완료 조건은 **[통합 개선 계획](../../plan/code-forge-final-improvement-plan-2026-10-18.md)**을 따른다.

2026-10-25 개정 · 개인 어시스턴트의 지속적 개인화를 중심으로 재정리한 계획. 구현·출시 및 이번 개정의 교차 모델 검수는 아직 수행하지 않았다.

## 1. 제품 방향과 저장소

**여러 모델이 하나의 개인화 코어를 활용해, 함께 일할수록 사용자의 판단 기준과 작업 방식을 이해하는 개인 어시스턴트**를 만든다. 첫 적용 분야는 개발 작업이다. 사용자는 기존처럼 터미널에서 일하거나 웹·모바일에서 같은 어시스턴트와 이어서 작업한다.

범용성은 **CodeForge 설치나 개발 저장소 없이도 개인화 코어를 사용할 수 있는 경계**에서 확보한다. 기존 도구에 기억·판단 기준만 연결하는 사용과, 실행·검증·복구까지 서비스에 맡기는 사용을 구분한다. 전자는 관리형 작업 원장을 요구하지 않지만 기억 접근·전송·수정 권한과 비용 제한은 지킨다. 실제 연결 가능 범위는 호스트별로 검증하며 모든 앱의 대화를 자동 수집하거나 행동을 통제한다고 약속하지 않는다.

### 용어와 책임

| 용어 | 이 문서에서 뜻하는 것 |
|---|---|
| 개인 어시스턴트 | 사용자와 지속적으로 일하며 승인된 기억·판단 기준·진행 중인 일을 이어 가는 제품 경험 |
| 실행 에이전트 | Claude·Codex 등에서 현재 작업을 수행하는 실행 단위. 교체·재시작될 수 있음 |
| 서브에이전트 | 독립 조사나 검토 등에 필요한 경우 실행 에이전트가 위임하는 작업자 |
| 기억·프로필 | 승인된 선호·판단 근거와 적용 범위. 프로젝트 사실·현재 작업 상태와 구분해 보관 |
| CodeForge | 필요한 규칙·스킬·지식 구성·재사용 도구를 제공하는 기존 OSS |
| 개인화 코어 | 공통 기억·경험의 저장과 수명, 접근 권한·맥락·모델별 지시 구성, 결과 기반 개선 |
| 관리형 실행 모듈 | 작업을 맡겼을 때의 상태·실행 권한·예산·검증·복구 |

‘나만의 어시스턴트 하나’는 사용자에게 이어지는 작업 관계를 뜻한다. 단일 모델·영구 실행 프로세스·전용 서브에이전트 파일을 요구하지 않는다. 화면이나 지원 모델이 바뀌어도 허용된 기억과 작업 근거를 이어 주되, 모델별 능력 차이는 검증한다. 개인과 회사 영역은 같은 화면에서 접근하더라도 정보·권한을 합치지 않는다.

어시스턴트는 목표와 환경에 맞춰 필요한 스킬·도구를 선택한다. 기본 실행으로 충분하면 별도 프로필 파일이나 서브에이전트를 만들지 않는다. Smith는 필요한 지식·작업 구성을 돕는 선택 기능이며, 프로젝트마다 일반 역할을 일괄 생성하는 것을 제품 가치로 삼지 않는다.

기존 CodeForge는 가입 없이 쓸 수 있는 무료 OSS로 유지한다. 로컬에는 호스트별 플러그인·설정 묶음을 제공하고 관리형 제품은 검증된 모듈과 산출물을 사용한다. Claude 중심 본문을 모든 호스트에 강제하지 않는다. 제품 저장소 경계는 실증 후 정하며 Atelier는 미확정 이름 후보다. 개인 코딩 연습은 이미 독립된 `coding-practice`에서 유지하고 서비스의 필수 기능·의존성에서 제외한다.

기존 설정·수정 파일을 보존하며 허용된 호환 업데이트는 백업·검증 후 새 세션/작업 경계에 적용한다. 충돌과 복구 방법을 안내하고 기존 명령은 최소 두 릴리스 지원한다. 상세 전환 조건은 [통합 계획 §8](../../plan/code-forge-final-improvement-plan-2026-10-18.md#8-출시와-완료-판정)을 따른다.

## 2. 관리형 첫 사용 경험과 배포

### 처음부터 유용하고, 반복할수록 덜 설명한다

| 시점 | 사용자가 경험할 변화 | 확인할 결과 |
|---|---|---|
| 첫 사용 | 샘플 또는 연결한 프로젝트에서 일을 맡긴다. 기존 지침을 먼저 읽고 꼭 필요한 질문만 한다 | 긴 성향 설문·자료 업로드 없이 첫 결과를 얻음 |
| 첫 교정 | “앞으로 이 프로젝트에서는 새 의존성을 추가하기 전에 기존 방법을 찾아줘”처럼 기준을 알려 준다 | 저장한 내용·적용 범위를 확인하고 다음 관련 작업에 반영 |
| 반복 사용 | 관련 기준과 이전 결정을 먼저 고려하고 실제 작업 방법·검사·보고를 조정한다 | 같은 교정·불필요한 질문·재작업이 줄어듦 |
| 기준 변경 | “이번만 예외야” 또는 “앞으로는 이렇게 해줘”라고 말한다 | 일회 예외와 지속 변경을 구분하고 오래된 기준을 수정·철회 |
| 화면·실행기 변경 | 터미널·웹·모바일에서 같은 작업을 이어 간다. 지원 실행기 교체는 확인된 인계 시점에 수행한다 | 새 화면·세션에서 전체 사정을 다시 설명하지 않아도 됨 |

이는 목표 경험이며 사용 기간만으로 성능이 좋아진다고 보장하지 않는다. 첫 작업부터 기본 모델의 능력을 활용하고, 반복 사용에서 개인화의 추가 효과를 확인한다.

### 작업 흐름과 접점

목표 전달 → 필요한 근거 선택 → 작업·질문 → 독립 검사 → 변경 내용·미확인·비용 확인 → 허용된 반영과 실제 결과 확인으로 이어진다. 조사·검사만 요청하면 그 결과를 반환한다. 구현 요청을 PR·배포 권한으로 확대하지 않으며, 이미 유효하게 허용한 범위는 반복 확인하지 않는다.

터미널에서도 기존처럼 대화하고 코드 작업을 한다. 요청·진행 확인·질문 답변·승인·취소·재개를 웹·모바일과 같은 작업에 연결한다. 관리형 여부는 사용 화면이 아니라 누가 작업 상태·권한·예산·검증·복구를 관리하는지로 구분한다. 기존 로컬 세션의 관리형 편입과 로컬 장비 원격 제어는 명시적 연결과 별도 지원 범위를 따른다.

가입 후 키·저장소 없는 제한된 샘플을 체험하고, 실제 작업에는 최소 권한으로 저장소를 연결한다. BYOK와 로컬 설치는 선택 사항이다. 로컬 OSS의 직접 실행은 가입 없이 유지한다. 관리형 서비스는 한 실행 에이전트만 사용해도 같은 관리 계약을 따른다. 기존 `/start`, `/test`, `/handoff`의 전체 절차를 중첩해 두 번째 실행·승인 루프를 만들지 않는다.

### 마이크 음성 지시

웹·모바일은 누르고 녹음 → 전사 확인·수정 → 전송부터 제공한다. 새 목표·후속 지시·질문 답변을 같은 작업에 연결하고 텍스트 입력도 유지한다. 마이크 거부·중단·전사 실패·중복 전송을 처리한다. 기존 로컬 Whisper·단축키 입력은 보존하며 실시간 대화·상시 녹음·음성 응답은 후속 선택 기능이다.

음성은 입력 수단이다. 실제 반영의 음성 승인을 제공하려면 정확한 작업·변경 버전·동작에 사용자 확인을 연결하고 오인식·재생·만료·중복을 검증해야 한다. 단순한 ‘네’를 다른 작업의 승인이나 화자 인증으로 사용하지 않는다.

음성 처리 위치·제공자·보존·삭제를 안내하고 동의를 받는다. 원본 음성은 최소 보존하며 전사·선택 후처리·개인화 이용을 구분한다. STT·후처리·전송/저장·재시도 비용을 계량한다. 첫 음성 요청은 GH, 기존 로컬 장비 호환은 G3에서 검증한다.

### 실행 환경과 비용

초기는 제한된 스택과 템플릿을 지원한다. 작업은 격리된 환경에서 실행하고 승인 대기에는 상태를 저장한 뒤 중지한다. E2B·Modal 등은 실행 환경 후보이며 지역·격리·복구·데이터 처리·원가를 실증한 뒤 선택한다.

| 범위 | 제공 원칙 |
|---|---|
| 어시스턴트 작업 | 모델·STT·격리 작업의 사용량과 비용 상한 적용 |
| 임시 미리보기 | 인증·만료·공유 범위·중지/삭제 제공, 기본 공개 금지 |
| 완성된 앱의 상시 운영 | DB·도메인·트래픽 등 별도 비용. 초기에는 고객 계정 배포 연결부터 검증 |

제어 서버와 비신뢰 코드 실행 환경을 분리한다. 고객별 저장소·cache·worker를 격리하고 저장소 범위를 제한한 짧은 토큰을 사용한다. 준비 worker에 운영 배포 자격증명을 상주시켜 두지 않는다. CPU·메모리·시간·출력·네트워크·저장량·동시성·비용 상한을 집행한다. 예산 예약·정산에는 계량 지연과 진행 중인 호출을 포함하고, 재시도 전에 외부 결과와 중복 여부를 확인한다.

관리형 경로에서는 서버와 허용된 모델 제공자가 코드·프롬프트·기억을 처리한다. 처리 지역·하위 처리자·보존·지원 인력 접근·삭제 한계를 공개한다. 로컬 전용 처리나 서버도 읽지 못하는 종단간 암호화를 주장하지 않는다.

## 3. 필요한 맥락만 사용하기

### 공통 기억 기반에서 모델별 지시로

프로젝트 지식·승인된 판단 기준·작업 경험은 세션 밖의 지속 가능한 비공개 저장 기반에서 함께 관리한다. 모델별 대화 기록을 모으는 것에 그치지 않고 출처·적용 범위·버전·수정/철회 상태를 유지한다. 기존 승인 자료는 원본을 연결하고, 허용된 실행 경로에서 받은 관측 결과와 교정을 반영한다. 제공자의 모든 과거 대화나 내부 기억에 자동 접근할 수 있다고 가정하지 않는다.

코어는 목표를 받으면 관련 기억과 근거를 선택하고, 사용자가 중요하게 보는 기준을 해당 모델의 지시·도구 사용 방식으로 구성한다. 지원 모델은 그 지시로 실행하고 결과를 코어에 돌려준다. ‘하나의 저장 기반’은 개인화의 정본을 뜻한다. 공개 코드 저장소와 분리하고 개인·회사 영역은 별도 접근 권한과 저장 경계를 유지한다. 저장 방식은 실증 후 정하되 실제 기억의 지속 저장·복원은 첫 제품에 포함한다.


기억이 많아져도 매번 전부 읽지 않는다. 자료 접근 권한을 먼저 확인하고 현재 목표와 관련된 최신 지침·선호·근거만 선택한다. 실제 전달 내용에는 출처와 버전을 남기고, 정책·실패·미확인 사항을 압축 과정에서 없애지 않는다. 도구 결과와 응답에 쓸 토큰을 확보하고 세션 인계·추가 조회 때도 권한을 다시 확인한다.

개인 선호, 프로젝트 정책, 현재 작업 상태는 다른 자료다. 개인의 일반 선호는 프로젝트의 강제 정책을 덮지 않는다. 현재의 명시적 작업 지시는 허용 범위에서 오래된 선호보다 우선하며 일회 예외를 전체 선호 변경으로 기록하지 않는다. 변하는 코드 사실은 원문에서 확인한다.

회사 업무의 존재 자체도 기본 비공개다. 개인 세션이 회사 코드·문서·기억·임베딩을 먼저 읽은 뒤 가리는 방식을 쓰지 않는다. 조직이 승인한 경우에만 별칭·거친 상태·관측 시각·만료 등 최소 정보를 허용된 화면에 표시한다. 발행 권한·대상·기기·TTL·정책 버전을 확인하고 요약·임베딩에도 원본 분류를 적용한다. 원문 조회권과 실행 토큰은 함께 보내지 않는다. 철회하면 cache를 무효화하되 이미 본 내용까지 회수할 수 있다고 약속하지 않는다.

## 4. 프롬프트와 메모리의 개선 루프

### 개인화의 기본 동작은 첫 제품에 포함한다

어시스턴트는 **사용자 지시·교정 → 기억 범위 확인 → 다음 관련 작업에 적용 → 실제 결과와 재교정 확인 → 유지·수정·철회**를 반복한다. 단순한 말투 외에 구현 선택, 설명 깊이, 질문이 필요한 시점, 검증·보고 방식이 사용자의 기준에 맞아야 한다. 선호를 따르는 것과 사실·품질 판단을 구분하고 근거 있는 반론도 제시한다.

| 입력 | 처리 |
|---|---|
| “앞으로 이렇게 기억해 줘” | 사용자가 지정한 허용 범위에 저장하고 반영 내용을 알림. 같은 저장 요청을 다시 승인받지 않음 |
| “이번 작업만 이렇게 해 줘” | 현재 작업 조건으로 사용. 장기 기억으로 자동 승격하지 않음 |
| 반복 행동에서 추정한 선호 | 근거·적용 범위를 갖춘 후보로 제시. 일괄 검토나 사전 허용한 좁은 갱신 정책을 사용하고 침묵을 동의로 취급하지 않음 |
| 외부 문서·도구 출력·서브에이전트 제안 | 작업 근거로만 사용. 사용자의 기억·권한 변경 지시로 취급하지 않음 |
| 수정·삭제·기억 끄기 | 새 작업에 반영하고 관련 cache·파생 자료를 무효화. 진행 중 작업도 다음 행동 전에 관련 변경을 확인하며 이미 실행된 효과는 별도 보고 |

기억에는 내용·사용자/영역·적용 대상·출처·승인 근거·버전·최근 확인 시점·수명 상태를 연결한다. 같은 기억의 동시 수정은 충돌을 감지해 조정한다. 사용자는 무엇을 기억하는지, 왜 적용했는지 확인하고 고치거나 내보내고 삭제할 수 있다. 모든 판단에 설명을 붙이지 않고 결과를 바꾼 기억이나 사용자가 요청한 근거를 짧게 보여 준다.

오래된 선호·서로 충돌하는 기준·잘못된 일반화를 발견하면 적용을 보류하거나 범위를 좁힌다. 중복 기억은 근거를 보존해 통합하고 바뀐 사실을 재확인한다. 검색에 쓰이지 않았다는 이유만으로 중요한 기준을 지우지 않으며, 저장·검색·정리 비용을 함께 추적한다. 새로운 환경에서 관련성이 없는 기억은 읽지 않는다. 기억을 끈 경우에도 기본 작업은 가능해야 한다. 사용 기간·저장량·동의 없는 행동 관찰을 개인화 성과로 계산하지 않는다.

### Reflexion: 작업 경험을 다음 행동으로 연결한다

Reflexion은 결과 피드백을 언어로 정리해 다음 시도에 활용하는 방식이다. 모델 가중치 학습을 전제하지 않는다. 이 원리를 개인화 코어의 **실행 → 검사·교정 → 반성 후보 → 다음 관련 작업 적용 → 효과 확인**에 활용한다. 원 논문의 성과를 장기 개인화나 다른 모델의 동일 결과 보장으로 옮겨 주장하지 않는다. [Reflexion 원 논문](https://arxiv.org/abs/2303.11366)

반성 후보에는 관측 결과·원인 가설·다음 행동·적용 조건·근거를 남긴다. 모델의 자기평가를 확인 사실로 취급하지 않는다. 현재 작업의 가설은 바로 시험하되 장기 교훈은 근거·권한·검증 또는 사용자 확인을 거친다. 반복 실패나 중요한 교정이 있을 때 선택적으로 수행하고 추가 호출·재시도에 비용 한도를 적용한다. 매 응답 뒤 긴 반성문을 생성하지 않는다.

이 흐름은 사용자를 흉내 내는 말투보다 판단과 작업 결과의 개선을 겨냥한다. 사용자의 기준이 틀렸거나 결과와 충돌하면 근거를 제시하고, 과도한 일반화·오래된 교훈은 수정·철회한다. 반성으로 실행 권한이나 검사 통과 기준을 변경하지 않는다.

### 오래 쓸수록 좋아지는지 검증한다

비교 기준은 기본 기억 기능까지 잘 설정한 기존 도구+프로젝트 지침+CI다. 같은 CodeForge에서 개인화 적용 여부와 단순 피드백/Reflexion을 비교해 실행 기반의 효과와 개인화의 효과를 나눈다. 양쪽에 동등하게 허용된 과거 정보를 제공하고 수동 설정·기억 관리 노동도 비용에 넣는다.

과거 작업에서 얻은 기억으로 이후의 유사하지만 새로운 과제를 수행한다. 미래 교정·정답을 기억에 미리 넣지 않고 모델·버전·과제 난도·정보 차이를 기록한다. 동일한 문제를 반복해 외운 결과만으로 일반화 성과를 주장하지 않는다. 반복 교정·불필요한 질문·원치 않는 선택, 수용한 결과당 검토·재작업 시간, 품질·총비용·지연을 사용자와 작업 유형별로 추적한다.

잘못 배운 선호, 일회 예외, 선호 변경·삭제, 새 프로젝트, 모델 교체, 회사/개인 경계를 별도 회귀 사례로 둔다. 소수의 장기 사용 사례는 초기 근거이며 보편적 성능 향상이나 최적성을 증명하지 않는다.

### 자동 최적화는 효과를 확인한 뒤 확장한다

G2/GH에는 공통 기억의 저장·선택 적용·수정·철회와 근거 기반 반성의 최소 흐름이 포함된다. G3에서는 같은 기억과 판단 기준을 Claude/Codex 양쪽에 전달해 결과를 검증한다. GL에서는 그 위에 지침 생성·예시 선택·맥락 선택 전략의 평가와 개선을 더한다. GEPA는 후보 기법이며 매 요청에 실행하거나 모델 가중치 학습과 혼동하지 않는다.

직접 요청·위임문·실제 전달문·실행 버전·결과·사용자 교정을 Work/Attempt/parent ID로 연결한다. 실행에 필요한 처리, 원문 장기 보관, 개인화 평가, 제공자 데이터 이용의 동의·계약을 구분한다. 사용자별·프로젝트별·시간별 평가를 나누고 재시도·파생 과제가 학습과 최종 평가에 섞이지 않게 한다. 과거 30/50건은 수집 이정표이며 자동 승격 기준이 아니다.

생성기가 검사 기준·권한을 바꾸지 못하게 하고 보안·품질 비퇴행을 통과한 후보만 제한 시험 → 허용된 승격 → 복구 가능한 버전으로 배포한다. 호스트·모델별 직접 적재와 특화 본문은 [통합 계획 §3](../../plan/code-forge-final-improvement-plan-2026-10-18.md#3-멀티모델-지원의-정확한-범위)에서 별도로 검증한다. 파일을 늘리거나 번역하는 것 자체를 개인화로 계산하지 않는다. 제공자 자체 기억과 공통 기억의 중복·충돌도 검사하며 모든 모델에 같은 문장을 보내는 방식으로 일관성을 가정하지 않는다.

삭제는 원문·기억·검색 index·평가 자료·생성기 후보까지 추적한다. 영향을 받은 버전을 철회·재생성하고 백업 삭제 지연 등 한계를 알린다. 다른 고객이나 회사 자료를 개인·공용 학습에 자동 재사용하지 않는다. 공개 pack에는 일반 규칙·형식·합성 예시만 두며 개인 자료와 키를 넣지 않는다.

## 5. 해킹 위험과 조직·폐쇄망

정보·기억·실행권을 한곳에서 연결하면 공격 표면이 커진다. 최소 context는 노출 범위를 줄일 뿐 안전을 보장하지 않는다. 웹 세션 탈취, 악성 저장소의 prompt injection, 메모리 오염, connector 탈취, cache 혼선, 공급망·관리자·단말 침해를 위협 모델에 넣는다.

동일 인물이라도 개인·조직의 인증·키·권한·저장소를 분리한다. 읽기·외부 전송·실행 권한을 구분하고 작업별 짧은 토큰, 민감 action 추가 인증, 세션/기기 철회, outbound 허용 목록을 적용한다. 2FA만으로 자료 반출이 정당화되지 않는다. Slack·Discord는 기본적으로 내용 없는 알림과 승인된 projection만 제공하고 자연어 질문으로 권한을 확대하지 못한다. 링크·오류·연속 질문·검색 개수에서도 정보가 새지 않는지 검사한다.

조직형은 조직 소유 BYOC 또는 설치형과 내부 IdP·기기 정책을 따른다. 폐쇄망은 모델·tokenizer·런타임·패키지·서명·신뢰 루트·SBOM·라이선스·오프라인 업데이트 묶음을 제공하고 내부 DNS/NTP/인증서·모니터링·백업을 준비한다. license check·telemetry·crash report·모델 다운로드까지 외부 호출이 없는지 시험한다. 장애 시 외부 모델로 자동 fallback하지 않는다. 오프라인 학습과 평가는 승인된 내부 모델만 사용한다. 회사 폰 접근은 조직이 승인한 경로에서만 제공한다.

## 6. 가격·수익 가설과 계약 검토

### 사업성 판정: 기능 조합만으로는 구매 이유가 약하다

2026-10-25 재검토. **범용 AI 개발 플랫폼으로 정면 경쟁할 근거는 아직 부족하다. 기존 프로젝트를 반복 관리하는 개발자의 재설명·수동 인계·재검토 부담을 줄이는 좁은 고객 문제부터 유료 수요를 검증한다.** 사업성 검토를 가격 계산만으로 대체하지 않는다. 아래 경쟁 기능은 공식 문서 확인 사항이고, 우리의 우위·약점과 고객 선택은 설계 판단이다. 경쟁사 실사용 비교나 고객 인터뷰·결제 검증은 이번 문서 검토에서 수행하지 않았다.

### 무엇을 팔고, 어디까지 직접 만드는가

**개인화 코어는 유망한 제품 가설이지만, 기억을 공유한다는 사실만으로 사업성이 확보되지는 않는다.** Letta와 기능 방향이 겹치고 Mem0 같은 기반도 존재한다. 독자 기억 엔진 구축보다 고객의 반복 설명·교정 비용을 줄이는 실제 경험과 지속 사용을 먼저 증명한다. 범용적인 내부 구조와 모든 직군을 동시에 대상으로 하는 출시는 별개다.

| 사업 방향 | 판단 |
|---|---|
| 기존 도구에 연결하는 개인 어시스턴트 | 우선 검증. 기존 작업 습관을 유지하며 교정·판단 기준을 이어 주는 효용에 과금할 수 있는지 확인. 별도 구독과 기억 관리 노동을 감수할 만큼 좋아야 함 |
| 관리형 실행 | 선택 확장. 무인 실행·검증·복구가 필요한 사용자에게 제공하고 실행 사용량을 구분. 개인화 이용에 서버 실행을 강제하지 않음 |
| 개발자용 기억 API/SDK | 내부 재사용 계약은 확보하되 독립 사업으로 동시 출시하지 않음. 별도 구매 수요와 기존 기억 플랫폼 대비 이득이 확인될 때 검토 |
| 조직·비개발 업무 | 개인/회사 경계와 분야 확장 가능성은 설계에 반영. 영업·보안·지원 부담 때문에 초기 시장을 동시에 확대하지 않음 |

기억 저장소·검색은 기존 제품이나 라이브러리의 재사용 후보로 비교한다. 채택 조건은 출처·범위·버전·삭제 전파·내보내기·운영 비용이며 특정 엔진의 자동 기억 판단에 제품 권한을 넘기지 않는다. 외부 엔진 교체가 가능해도 모델·호스트의 입력과 피드백 접근 한계는 남는다. 이를 해결하지 못하는 도구는 제한된 기억 전달만 지원한다고 표시한다.

기존 모델 구독을 유지하는 경로도 해당 호스트가 허용하는 인증·연동 방식 안에서 제공한다. 구독 재판매나 API 비용 면제를 가정하지 않는다. 기억 연결만 제공해도 추출·검색·반성·저장·지원 비용이 발생한다. **고객 가치 = 줄어든 설명·교정·검토 부담**, **기여이익 = 매출 − 모델·기억 처리·실행·저장·지원 등 변동비**를 따로 확인한다. 기억 용량·모델 수를 가치 지표로 대신하지 않는다.

파일럿에서는 기억 연결만으로 얻는 효과와 관리형 실행을 추가한 효과를 구분한다. 잘 설정된 기존 도구, 직접 경쟁 제품과 비교해 개선이 없으면 통합 플랫폼 구축을 확대하지 않고 유익한 연결 기능만 남긴다. 반복 사용은 있으나 지불 의사가 없다면 사용자 수만으로 유료 사업의 성공을 선언하지 않는다.

### 고객이 체감할 와우 포인트

제품의 가치 제안은 **“함께 일할수록 내 기준을 이해하고, 다음 일을 더 잘 돕는 개인 어시스턴트”**다. 첫 개발 작업에서는 반복 설명·교정·검토 부담이 줄어드는지 확인한다. 아래 장면은 목표 데모이며 아직 달성한 성과가 아니다.

1. **한 번의 교정이 다음 작업을 바꾼다.** 사용자가 승인한 판단 기준을 관련 작업에만 적용하고 무엇을 기억해 판단했는지 짧게 보여 준다. 다음 세션·다른 지원 실행기에서도 같은 교정을 되풀이하는지 측정한다. 기억 파일을 저장했다는 사실보다 반복 교정 감소가 가치다.
2. **돌아왔을 때 결정할 것만 남아 있다.** 터미널에서 맡긴 제한된 작업을 계속 수행하고, 막힌 질문·변경 후보·실제 검사·미확인·비용을 한곳에 보여 준다. 모바일 답변 후 같은 작업을 이어 간다. 필수 검사 통과만으로 모든 결함이 없다고 주장하지 않는다. 기존 도구 대비 고객의 검토 시간이 줄어야 의미가 있다.
3. **익숙한 도구를 유지해도 결과가 이어진다.** 지원 실행기를 바꿀 때 승인된 기준·결정·미해결 사항과 확인된 결과를 전달한다. 무손실 실시간 모델 교체를 약속하지 않고 명시적 checkpoint에서 시작한다. 한 모델만 쓰는 고객에게도 개인화 효과가 있어야 하며 교체 편의만으로 구매 이유를 설명하지 않는다.

첫 방문의 데모는 샘플의 문제 재현 → 최소 수정 → 전후 검사·미리보기·비용으로 즉시 결과를 보여 준다. 개인화는 이후 실제 반복 작업에서 증명한다. ‘AI들이 많이 일하는 모습’, 역할 수, 긴 사고 로그, 음성 입력만을 와우 포인트로 삼지 않는다.

### 첫 고객·강점·약점

초기 고객 가설은 **기존 저장소를 반복 관리하며 AI의 같은 실수와 검토 노동을 겪는 개인 개발자·소규모 개발팀**이다. 첫 지원 스택의 실제 작업부터 모집한다. 여러 도구를 쓰는 사람은 유력 후보지만 멀티모델 사용 자체를 고통이나 지불 의사로 간주하지 않는다. 비개발자의 범용 앱 제작과 기업 폐쇄망을 동시에 첫 시장으로 잡지 않는다.

잠재적 강점은 사용자의 승인된 판단 기준과 실제 작업 결과를 연결해 지속적으로 개선하고, 지원 도구가 바뀌어도 그 축적을 이어 주는 방향이다. 한 모델만 쓰는 사용자에게도 반복 교정이 줄어야 가치가 있다. 기존 무료 OSS는 체험 진입점 후보이며 어시스턴트의 효과를 대신 증명하지 않는다. **현재 유료 고객·활성 설치 규모·전환율은 확인하지 않았으므로 기존 사용자가 있다는 사실을 검증된 유통 채널로 계산하지 않는다.**

| 검토 관점 | 약점·실패 가능성 | 제품에서 확인할 것 |
|---|---|---|
| 사용자 경험 | 충분히 배우기 전에 이탈하거나 기억 관리가 새 노동이 됨 | 첫 작업의 가치, 반복 승인·질문 수, 기억 수정에 드는 시간 |
| 개인화 정확성 | 일회 선택을 성향으로 일반화하거나 오래된 기준을 고집함 | 예외·교정·철회 반영, 반례가 있는 새 작업에서의 결과 |
| 모델 간 일관성 | 같은 기억을 전달해도 해석·도구 능력·자체 기억이 다름 | 모델별 실제 전달과 행동 검증, 충돌·미지원 표시 |
| 학습 신뢰성 | 자기반성으로 잘못된 원인을 확신하고 반복함 | 외부 검사·사용자 교정·반례, 교훈 후보의 기각·복구 |
| 비용·운영 | 기억·검색·반성·호스트 호환과 지원 비용이 절감보다 큼 | 실패 포함 완료당 비용과 고객별 지원 노동, 불필요한 단계 제거 |
| 사업 방어력 | 공급자가 같은 경험을 제공하고 추가 구독을 대체함 | 기억 기능을 갖춘 기존 도구 대비 반복 효용·실제 갱신 |

독립 검증도 부실한 기준의 한계를 없애지 못하고 여러 모델의 합의가 정확성을 보장하지 않는다. 장기 기억은 지속적 개선의 기반이지만 잘못된 교훈을 퍼뜨리는 경로도 될 수 있다.

현재 입증된 기술적 독점이나 데이터 규모의 우위는 없다. 사용자가 허용한 프로젝트별 교정·수용 기준·실제 결과를 연결하고 반복 작업의 품질을 높이는 운영 경험은 축적 가능한 자산 후보다. 개인 데이터를 가둬 전환을 어렵게 하거나 고객 간 무단 공유를 방어력으로 삼지 않는다. export·삭제와 호환을 제공하면서도 계속 쓰는지 확인한다.

### 구현과 함께 진행할 사업 검증

아래 표본·기간은 작은 탐색 실험의 제안이며 PMF의 통계적 증명이나 자동 승격 점수가 아니다. 기존 기술 검증을 모두 끝낸 뒤 수요를 묻지 않는다.

| 단계 | 실제로 할 일 | 판단 근거 |
|---|---|---|
| 문제 확인 | 후보 고객 5~8명에게 최근 작업·교정·수동 인계·검토 사례를 요청. 기존 사용자 중 동의한 사람과 직접 접촉 가능한 개발자부터 시작 | 반복되는 구체적 문제와 현재 해결 비용. ‘있으면 쓰겠다’는 응답은 제외 |
| 비교 파일럿 | 동의한 3~5명과 약 2주간 한 작업 유형 비교. 기본 기억·프로젝트 지침·CI를 충분히 설정한 기준선과 CodeForge 후보 비교. 과거 정보로 이후 새 과제를 수행 | 완료율·중요 결함·반복 교정·사람의 검토/재작업 시간·전체 지연·실패 포함 비용. 같은 작업 재사용의 학습 효과를 줄이도록 유사 과제와 순서 교차 사용 |
| 지불 검증 | 실측 결과와 사용량 한도를 제시하고 제한된 유료 파일럿 제안 | 실제 결제·재사용·갱신 이유. 시간이 지나며 개인화 가치가 유지되는지 후속 관찰. LOI·관심 표명은 결제와 구분. 무단 연락이나 실제 결제는 이 문서 검토 범위 밖 |
| 유통 검증 | OSS 안내에서 자발적 체험으로 연결하고 공개 가능한 합성/동의 사례의 전후 결과로 모집 | 설치 수·별 수가 아닌 체험→반복 완료→유료 전환, 고객 획득·온보딩·지원 시간 |

핵심 제품 지표는 **사용을 거듭할 때 수용한 결과당 반복 설명·교정·검토·재작업 시간이 줄어드는가**다. 개인화 효과는 §4의 시간 순서 비교로 확인한다. 중요한 결함·정책 위반이 늘지 않아야 하며 실제 비용·지연·반복 사용을 함께 본다. 비교 전 고객이 의미 있다고 보는 개선 폭과 지불 가능한 비용을 정하고, 보기 좋은 사례만 남기지 않는다. 돈으로 환산할 때 고객 시간 절감의 가정값과 실제 매출을 구분한다.

유료 확장은 반복 사용·실제 지불과 `매출 − 모델/STT·worker·저장/전송·결제·변동 지원 비용`의 양립을 확인한 뒤 결정한다. 개발·유지보수·보안 운영의 고정 비용도 별도로 감당 가능한지 본다. 단순 토큰 절감이 지원 비용보다 작으면 사업은 성립하지 않는다.

기본 기억 기능을 가진 기존 도구와 차이가 없으면 개인화 방식과 고객군을 재검토하고 추가 실행 계층·관리형 범위를 줄인다. 무료 pack·좁은 도구로 남기는 선택도 열어 둔다. 효용은 있으나 지불이 없으면 고객군·제공 방식·가격을 재검토한다. 비싼 수작업 지원이 있어야 성공하면 이를 숨긴 SaaS 매출로 계산하지 않는다. 기술 완료와 유료 사업 확장을 별도 판단하며 현재 권고는 **작은 실증 진행, 범용 플랫폼 확대 투자는 보류**다.

### 가격과 원가 가설

무료 OSS와 유료 운영 편의를 구분한다. 개인 구독은 기본료 + 제한된 포함 사용량 + 명시적 추가 구매를 권고한다. 팀은 공동 예산·관리 기능, 조직형은 도입·연간 지원을 검토한다. $29/$49/$99는 상품 가설이며 확정 가격이 아니다. 연결 기능만을 가정한 과거 저가 구독안을 관리형 무제한 실행 가격으로 사용하지 않는다.

원가는 모든 모델 호출(생성·추출·검증·재시도), 병렬 worker별 청구 시간 합계, preview·저장·전송·지원·결제 비용을 포함한다. GEPA 평가 비용은 별도 상각하되 일반 호출 비용과 중복 계산하지 않는다. 재사용 예상 횟수 × 검증 완료당 절감액이 평가 비용을 넘는지, 품질 제약을 지키는지 확인한다. 사용자 간 데이터 공유를 전제로 절감을 계산하지 않는다.

제품 형태의 비용 비교에는 상시 기능 목록·선택 지침·도구 schema·중간 출력·추가 router·재시도와 cold/warm cache를 포함한다. plugin을 CLI나 MCP로 바꾸더라도 같은 내용을 같은 횟수로 모델에 보내면 절감을 주장하지 않는다. 모듈화의 배포·지원 비용과 한 번의 전환 비용도 따로 평가한다. 품질·권한·검증을 유지한 실제 완료당 총비용이 채택 기준이며, 현재 파일 크기나 공개 사례의 절감률을 이 서비스의 실측으로 사용하지 않는다.

기존 HTML 비용 계산기는 작성 당시 가정 실험이며 현재 견적·수요·수익 근거가 아니다. 실제 공급자 가격·지역·과금 단위·지원 노동·실패율을 유료 파일럿 전에 다시 확인한다. 무제한 요금제를 약속하지 않고 과도 사용 시 명시적 한도·추가 구매·중단을 제공한다.

출시 전에는 공급자 상업 이용 조건, 고객 코드와 생성물 권리, OSS 라이선스 의무, 개인정보 처리·국외 이전·하위 처리자, 삭제·보존, 사고 대응, 구독 해지·환불·재시도 과금, 지원 범위를 실제 관할과 계약에 맞게 검토한다. 개인용 모델 구독 토큰을 모아 서비스하지 않는다. 이 문서는 법률 의견이나 규정 준수 인증이 아니다.

GH에는 계정 복구·권한 회수·사고 대응, 지원 조합, 사용량 제한·악용 대응·과금 이의 처리가 필요하다. 격리 환경에서 코드가 실행됐다는 사실만으로 유료 출시하지 않는다.

구현 순서는 기존 변경 보존·안전성 → 한 작업의 실행과 기본 개인화 → 관리형 고객 경험이다. 멀티호스트 출시는 G1b/G3, 자동 최적화는 GL, 조직·로컬 장비 연결은 G4에서 별도로 검증한다. 상세 단계와 책임은 통합 계획을 따른다.
