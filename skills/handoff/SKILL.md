# Handoff

작업 도중 맥락이 압축되거나 세션·도구가 바뀌어도 다음 작업자가 같은 정본과 다음 행동에서 시작하게 한다. 대화 로그나 문서 계층을 늘리지 않고, 기존 자료를 가리키는 **활성 체크포인트 하나**만 유지한다.

## 핵심 원칙

- 활성 체크포인트는 하나다. 기존 문서가 있으면 별도 `progress.md`, `history.md`, `handoff.md`를 만들지 않는다.
- `intent`, `spec`, `plan`, `progress`는 역할을 이해하기 위한 말이지 필수 파일명이 아니다. 같은 역할의 외부 업무 시스템 업무, Story index, milestone, 계획 문서가 있으면 그것을 가리키고 새 파일로 복제하거나 이름을 바꾸지 않는다.
- 각 정보의 정본을 하나만 둔다. 체크포인트에는 상세 내용을 복사하지 않고 주소·경로·SHA와 현재 승인 상태만 남긴다.
- 다음 작업자가 바로 행동하는 데 필요하지 않은 조사 로그, 대화 전문, 시간순 일지, 일반 설명은 버린다.
- 이 스킬은 세션 인계만 맡는다. 구현·검토·commit·push·외부 시스템 변경 권한을 만들지 않는다.

## 1. 활성 체크포인트 찾기

**최근 대화에서 만든 파일보다 사용자가 이어 온 기존 정본이 우선이다.** 한 번 경로를 확인한 연속 작업은 그 절대경로를 다음 프롬프트에도 넘긴다. 파일이 없어지거나 작업이 바뀌지 않았다면 매번 새로 선정하지 않는다.

1. 사용자가 지정한 경로 또는 이전 시작 프롬프트의 활성 체크포인트를 먼저 연다. 파일명은 `README.md`일 수도 있다. `HANDOFF.md`/`PLAN.md`라는 이름만 찾지 않는다.
2. 경로를 모르면 저장소 안내와 현재 작업 계획에서 찾는다. Git worktree 안이라면 `git worktree list`로 원본 작업 트리도 확인한다. 로컬 계획은 원본 checkout에만 있고 feature worktree에는 없을 수 있다.
3. **gitignore된 로컬 계획도 반드시 검색한다.** 기본 `rg`나 `git ls-files`의 무결과는 “문서 없음”의 증거가 아니다. 원본 저장소의 `plan/`, `plans/`, 알려진 로컬 계획 디렉토리부터 `rg -l --hidden --no-ignore -g '*.md' '★ CURRENT' <디렉토리...>`처럼 내용으로 찾는다. `.git`, `node_modules`, 빌드 출력은 제외한다. 먼저 파일명만 받아 후보 문서만 읽고 전체 내용을 출력하지 않는다.
4. 그래도 못 찾으면 관련 세션의 시작 프롬프트·인계 기록에 남은 경로를 좁게 확인한다. 무관한 프로젝트나 전체 홈 기록을 훑지 않는다. 도구 오류·없는 디렉토리는 정상 무결과와 구분한다.
5. 현재 작업과 연결되는 후보 하나가 확인되면 질문 없이 사용한다. 여러 후보가 서로 다른 작업의 정본이거나, **사용자가 기존 문서를 갱신하라고 했는데 끝내 찾지 못하면**, 어느 문서인지 한 가지 질문으로 확인한다. 찾지 못했다는 이유로 새 문서를 만들지 않는다.
6. 기존 문서가 없다는 근거가 있고 새 지속 작업일 때만 저장소 관례에 따라 만든다. 관례도 없을 때만 작업 루트에 `HANDOFF.md` 하나를 만들고 신규 생성임을 알린다.
7. 기존 구조를 보존한다. `## ★ CURRENT`가 없을 때만 제목과 서문 다음에 짧게 추가한다. 실수로 중복 체크포인트를 만들었다면 유효 정보를 기존 정본에 합쳐 확인한 뒤 이번 작업이 만든 중복만 정리한다. 사용자 파일은 임의로 삭제하지 않는다.

## 2. 정본 포인터 확인

체크포인트를 쓰기 전에 현재 작업에 실제로 존재하는 자료만 다음 역할로 구분한다.

- **요청·의도 정본**: 무엇을 왜 하는지와 업무 범위를 가진 외부 업무나 문서
- **승인된 범위**: 요구사항·결정·안 할 것을 가진 Story, spec 또는 계약
- **현재 실행 입력**: 지금 구현할 task, milestone 또는 작은 계획
- **검증 근거**: 필요할 때만 여는 조사 부록, 테스트 결과 또는 PR

이 구분을 위한 새 문서를 만들지 않는다. 역할이 합쳐져 있거나 일부가 없으면 그대로 둔다. 다음 작업자의 혼동 가능성이 있을 때만 `CURRENT`의 `먼저 읽을 곳`이나 시작 프롬프트에 역할과 포인터를 짧게 표시한다.

## 3. 체크포인트 갱신

**인계 중인 작업에서는 clear 직전뿐 아니라 지시·결과를 주고받는 경계마다 갱신한다.** 전체 목적과 현재 실행 단위를 구분해 보존하고, 작업 일부를 검토하더라도 원래 후속 계획을 그 부분으로 바꾸지 않는다.

- **결과 수신**: 먼저 CURRENT를 읽고, 받은 구현 결과·검토 의견을 기존 지시 범위와 대조한다. “상대가 보고함 / 직접 확인함 / 아직 미확인”을 구분한다. 완료·미완료, 반례, 새 결정과 다음 행동을 갱신한 뒤 다음 지시를 작성한다. 결과를 받았다는 사실만으로 검토 통과나 전체 완료로 올리지 않는다.
- **지시 발신**: 대상 도구, 체크포인트 절대경로, 작업 트리·브랜치·기준 HEAD, 이번 범위·제외 범위·완료 조건·요청할 보고를 CURRENT에 먼저 반영하고 그 상태에서 프롬프트를 만든다. 프롬프트 작성/클립보드 복사는 상대의 수신·착수·완료가 아니다. 실행 권한도 새로 만들지 않는다.
- **실행 도중**: 범위·우선순위·기준 SHA가 바뀌거나 단계 완료·실패한 접근이 생기면 해당 항목을 갱신한다. 이전 대화의 기억이나 새 로그에만 남기지 않는다.

완료된 상세 이력은 Git·PR·milestone 등 정본을 가리키고, CURRENT에는 다음 작업자가 필요한 현재 값만 남긴다. 낡은 “바로 할 일”에 새 지시를 덧붙이지 말고 교체한다. 중요 미해결 결정과 전체 후속 순서를 함께 지우지 않는다.

기존 표현을 유지하며 다음 중 실제로 필요한 항목만 쓴다.

- 현재 목표와 실제 진행 상태
- 완료 결과와 검증 결과
- 확정된 결정과 재검토를 막는 데 필요한 짧은 이유
- 반복하면 안 될 실패·기각 방식
- 다음에 수행할 정확한 한 단계
- 사용자 판단이 필요한 항목 하나(있으면 `⚠️`)
- 정본 주소, 기준 SHA, 브랜치, 핵심 파일 경로
- 기존 사용자 변경과 commit·push 등 권한 주의사항

권장 형태는 아래와 같다. 기존 문서에 같은 역할의 필드가 있으면 그 형식을 따른다.

```markdown
## ★ CURRENT — 다음 세션 인계

- **현재 상태**: ...
- **완료·검증**: ...
- **확정한 결정**: ...
- **반복하지 않을 것**: ...
- **바로 할 일**: ...
- **확인 필요 ⚠️**: ...
- **먼저 읽을 곳**: ...
```

### 주기적 산출물·문서 점검

체크포인트를 갱신할 때 프로젝트에 정한 점검 주기의 도래 여부도 확인한다. 별도 주기가 없으면 **마일스톤·개선 묶음 인수 시, 또는 마지막 점검 후 7일이 지난 다음 작업 재개 시** 점검한다. 이는 활성 작업의 경계에서 수행하는 점검이며 백그라운드 예약 실행이나 자동 삭제를 뜻하지 않는다. 매 메시지마다 전체 산출물을 다시 읽지 않는다.

- 현재 작업이 소유한 문서·산출물과 기존 포인터만 확인한다. 개선이 실제로 검증·채택됐는지 구분하고, 최신 결정·실행 결과·남은 일로 CURRENT를 갱신한다. 미검증 후보나 다른 작업자의 자료는 완료·폐기 대상으로 올리지 않는다.
- 완료된 상세 이력은 기존 근거 위치를 가리키고, 중복 본문·폐기된 다음 지시는 현재 실행 입력에서 걷어낸다. 미해결 결정·실패 재현·롤백 근거는 보존한다. 별도 정리 문서나 새 활성 핸드오프를 만들지 않는다.
- 산출물은 유지·보관 후보·삭제 후보로 구분한다. 실제 이동·삭제는 아래 승인·소유권·증거 보존 조건을 따른다. 주기가 지났거나 개선안이 채택됐다는 사실 자체는 삭제 권한이 아니다.
- 기존 CURRENT의 정리 항목 한 줄을 교체해 `마지막 점검일 / 점검한 범위·결과 / 보류·승인 필요 / 다음 점검 조건`을 남긴다. 대기 중인 같은 승인 요청을 매번 반복하지 않는다. 실제 정리가 안 됐으면 점검 완료와 정리 대기를 구분한다.
- 다음 세션 지시에는 이 점검 상태가 있는 기존 체크포인트 경로만 전달한다. 상세 보관 정책·산출물 목록·프로젝트 고유 주기는 해당 프로젝트 정본에 두고 이 스킬이나 매 프롬프트에 복제하지 않는다.

### 단계 종료·clear 전 임시 자료 정리

단계가 끝나거나 중간 맥락 정리·clear를 준비할 때는 이전 지시를 계속 덧붙이지 말고 CURRENT를 현재 상태로 압축한다. 결과, 검증 근거와 한계, 잃어버리면 안 되는 결정과 이유, 미해결 사항, 다음 행동, 필요한 경로·SHA·PR만 남긴다. 전체 목표와 미완료 범위는 축소하지 않는다.

사용자가 정리를 승인한 범위에서는 요약 저장·재읽기 뒤 사용이 끝난 임시 자료를 정리한다. 정리 지시 자체가 없는 경우에는 삭제 대상만 제안한다.

- 이 작업이 만든 정확한 파일·폴더만 대상으로 삼는다. tmp 위치나 오래된 이름만으로 삭제하지 않는다. 다른 작업자 자료와 범위가 불명확한 항목은 보존한다.
- 삭제 전에 필요한 결과·결정이 체크포인트에 남았고 상세 근거는 커밋·PR·유지할 파일 등에서 다시 확인 가능한지 확인한다. 유일한 재현 자료나 미해결 실패 로그는 요약만 남기고 버리지 않는다. 체크포인트가 삭제될 경로만 가리키지 않게 한다.
- 미커밋·미푸시 작업, 진행 중인 PR/세션/서버가 쓰는 작업 트리, 사용자가 보관을 요청한 로그·프롬프트·첨부·원본 계획은 보존한다. 작업 트리는 Git 상태·원격 반영·실제 병합 여부와 사용 프로세스를 확인한 뒤 전용 제거 명령으로 정리하며 강제 삭제를 기본으로 쓰지 않는다.
- 완료 세션과 터미널 정리까지 요청받았다면 결과 보존 후 해당 세션 종료를 확인하고 빈 터미널도 닫는다. 다른 사용자 세션이나 살아 있는 확인용 서버를 함께 종료하지 않는다.
- 가능한 경우 복구 가능한 이동을 우선한다. 광범위한 tmp 삭제나 와일드카드 일괄 삭제는 하지 않는다. 제거한 대상·복구 가능 여부와 보존한 항목의 이유를 짧게 보고한다. 정리 실패를 완료로 적지 않는다.

이 절은 파일 정리 승인만으로 자동 clear·세션 종료·commit·push·원격 브랜치 삭제 권한을 만들지 않는다.

## 4. “핸드오프해줘”의 기본 동작

사용자가 `핸드오프해줘` 또는 같은 뜻의 짧은 요청만 해도 아래 전체를 요청한 것으로 처리한다. 프롬프트를 만들지, 복사할지 다시 묻지 않는다.

1. `git status`, 현재 브랜치와 활성 체크포인트의 `★ CURRENT`를 다시 확인한다.
2. 이번 세션에서 바뀐 결정·상태·다음 행동을 체크포인트에 반영하고, 위 임시 자료 정리 절차를 승인 범위에서 수행한다.
3. 다음 Claude 또는 Codex가 저장소를 다시 조사하지 않고 시작할 수 있는 자기완결적 프롬프트를 작성한다.
4. macOS에서 `pbcopy`를 사용할 수 있으면 프롬프트를 클립보드에 복사하고 성공 여부를 확인한다.
5. 복사할 수 없으면 프롬프트 전문을 답변에 제공한다.
6. 갱신한 체크포인트 경로와 복사 성공 여부를 사용자에게 알린다.

체크포인트가 git 추적 파일이면 갱신 내용을 먼저 보여 주고 승인받는다. 추적되지 않는 로컬 계획 파일이면 바로 갱신한다.

사용자가 명시적으로 요구하지 않으면 세션 종료, `/clear`, commit, push 또는 외부 시스템 변경은 하지 않는다.

## 5. 시작 프롬프트

프롬프트는 현재 작업에 필요한 구체값을 채워 짧게 작성한다. **항상 기존 체크포인트의 절대경로와 결과 보고·검토 수신 때 같은 문서를 갱신하라는 지시를 포함한다.** 다음 도구에 이 스킬이 없어도 그 지시만으로 인계 절차가 이어져야 한다. 비밀값, 전체 로그, 상세 정책·설계의 복사본은 넣지 않는다.

```text
<작업명>을 이어서 진행해.

작업 저장소: <절대경로>
세션 여는 폴더: <절대경로>

1. `git status --short --branch`와 현재 브랜치를 확인하고 기존 변경을 보존해.
2. <활성 체크포인트>의 `★ CURRENT`만 먼저 읽어.
3. 정본과 현재 실행 입력을 아래 순서로 읽어.
   - 요청·의도: <주소 또는 경로>
   - 승인된 범위: <경로>
   - 현재 실행 입력: <경로>
4. 끝난 설계를 다시 시작하지 말고 `<바로 할 일>`부터 진행해.
5. <검증 방식과 실행기>를 사용해.
6. 결과를 보고하거나 다음 검토를 받으면 같은 체크포인트의 CURRENT에 완료·근거·남은 문제·다음 행동을 먼저 갱신해. 별도 인계 파일은 만들지 마.

확인 필요: <보류 결정 또는 없음>
주의: <dirty worktree, 기준 SHA, 권한, 반복하지 않을 방식>
```

존재하지 않는 역할은 프롬프트에서 생략한다. 경로만으로 다음 행동이 분명하면 설명을 덧붙이지 않는다. 저장소 훅과 자동화는 세션을 연 폴더에 붙으므로, 그 폴더가 저장소 루트와 다르거나 실행 경로가 그 자동화에 기대면 반드시 적는다.

## 6. 구현 입력과 실행 경로

활성 체크포인트는 전체 맥락을 보존하지만 구현기의 직접 입력은 현재 단계의 작은 task 또는 milestone로 좁힌다. 완료 조건, 수정·제외 범위와 검사를 실행 입력에 둔다. 큰 통합 계획 전체를 구현기에 넘기지 않는다.

실행 경로는 이 스킬이 정하지 않는다. 저장소에 라우팅 규칙이 있으면 그 규칙이 정한 결과를, 없으면 이번 세션에서 사용자가 정한 결과를 체크포인트에 사실로 적는다. 저장소 전용 파이프라인·하네스·자동화는 이번 작업이 그 대상으로 판정됐을 때만 프롬프트에 적는다. 다음은 대상이 아니다.

- 그 저장소 밖의 작업
- 하네스·스킬·규칙·에이전트 문서 자체를 고치는 작업
- 라우팅 규칙이 직접 수정으로 판정한 ad-hoc 작업

저장소 훅과 자동화는 세션을 연 폴더에 붙는다. 저장소 관례가 작업 폴더 위치를 강제하면 그 경로를 그대로 적는다.

저장소 전용 실행기는 현재 환경에서 실제로 사용할 수 있고 사용자 권한과 보안 정책에 맞을 때만 사용한다. hook, permission mode 또는 전용 런타임이 없으면 실행한 것처럼 말하지 말고, 같은 완료 조건을 지키는 직접 구현이나 실행 프롬프트로 전환한다.

저장소별 정본 계층과 라우팅 규칙은 그 저장소가 이미 문서로 갖고 있다. 이 스킬에 복제하지 않고 그 저장소의 안내를 읽어 따른다.

## 7. 완료 확인

- **실제로 수정한 기존 파일을 다시 읽어** 활성 경로와 CURRENT 갱신을 확인한다. 검색·초안 작성만 하고 “갱신 완료”라고 보고하지 않는다.
- 이번 작업에서 알려진 체크포인트 후보와 새로 만든 파일을 대조해 활성 정본이 하나인지 확인한다.
- `★ CURRENT`와 시작 프롬프트의 체크포인트 절대경로·작업 트리·HEAD·이번 범위·다음 행동이 같은지 대조한다.
- 전달받은 결과와 직접 확인한 결과가 구분돼 있고, 전체 후속 목표가 현재 작은 작업으로 축소되지 않았는지 확인한다.
- 정본 상세가 중복 저장되거나 불필요한 새 문서 계층이 생기지 않았는지 확인한다.
- 현재 실행 입력이 작은 단위이고 완료 조건을 포함하는지 확인한다.
- 사용자 판단이 필요한 결정이 한 번에 하나씩 드러나는지 확인한다.
- 핸드오프 요청이면 프롬프트 작성과 클립보드 복사 결과까지 반드시 보고한다.
